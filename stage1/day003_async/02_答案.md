## 第 1 题 · 三个真并发，两个假的

### 判据

五个形状只有一行差别，判据也只有一条：

> **这段里的每一个等待，有没有把控制权交出去？**

| 形状 | 登记动作 | 交不交控制权 | 耗时应然 | 实测 | 并发吗 |
|---|---|---|---|---|---|
| 1 `gather(job, job)` | `gather` 一次登记两个 | 两个都交 | 0.20 | 0.20s | ✅ |
| 2 `await` + `await` | 没登记，走到才跑 | 两个都交，但**一个完了才轮到下一个** | 0.20+0.20 | 0.40s | ❌ |
| 3 `create_task` + `await` | `create_task` 登记甲，后面那个 `await` 是别人的活 | 都交 | max(0.2, 0.1) | 0.20s | ✅ |
| 4 `gather(sleepy, sleepy)` | `gather` 一次登记两个 | **都不交**（`time.sleep`） | 0.20+0.20 | 0.41s | ❌ |
| 5 `gather(to_thread, to_thread)` | `gather` 登记两个 | 交（挪去别的线程） | 0.20 | 0.21s | ✅ |

**假的那两个是 2 和 4。** 而 4 是唯一一个**你写了 gather 却完全没并发**的——
这题真正要抓的就是它。

### 两个坑，各自错在哪一步

**形状 2 看起来最"干净"，所以最容易被当成正确答案。**
两行 `await` 挨着写，每一行单看都没毛病。它慢不是因为哪一行写错了，
是因为**这两行之间没有一次登记动作**。第二节的结论在这里反着用：
`await` 只负责"当场等完"，它不产生并发。想让它们同时开始，
中间必须有一句 `create_task` 或者外面套一个 `gather`。

**形状 4 看起来最"像对的"，因为它和形状 1 只差函数体里的一行。**
把 `job` 和 `sleepy` 并排放：

```python
async def job(name, sec):
    await asyncio.sleep(sec)      # 这一行把线程交出去 → 0.20s


async def sleepy(name, sec):
    time.sleep(sec)               # 这一行不交 → 0.41s
```

`gather` 在两个形状里干的活**一模一样**：都把两个任务登记上了。
区别是登记完之后，循环切给第一个，第一个不肯回来。

### 返回顺序那一列，五个都在说同一句话

```
形状 3  -> 0.20s | 返回 ['甲', '插队']
```

`插队` 只睡 0.1，甲睡 0.2，**插队一定先醒**，可返回列表里甲在前。
第四节的结论在 `create_task` 上照样成立：**返回顺序跟着登记的先后，不跟着完成的先后。**
五个形状没有一个返回 `[乙, 甲]` 或 `[插队, 甲]`，这不是巧合。

## 第 2 题 · `wake_two`

### 参考实现（并发版）

```python
import asyncio
import time


async def wake(name, sec):
    print(f"   {name} 闭眼")
    await asyncio.sleep(sec)
    print(f"   {name} 睁眼")
    return name


async def wake_two():
    t1 = asyncio.create_task(wake("甲", 0.3))
    t2 = asyncio.create_task(wake("乙", 0.1))
    return await asyncio.gather(t1, t2)


async def main():
    start = time.perf_counter()
    res = await wake_two()
    print(f"花掉 {time.perf_counter() - start:.2f}s | 返回 {res}")


asyncio.run(main())
```

真实输出：

```
   甲 闭眼
   乙 闭眼
   乙 睁眼
   甲 睁眼
花掉 0.30s | 返回 ['甲', '乙']
```

**我写的是两行 `create_task` 再 `gather` 这两个 task。**
你也可以一行 `create_task` 都不写，直接 `gather(wake("甲", 0.3), wake("乙", 0.1))`，
`gather` 内部替你登记。两种都对，输出一个字不差。

**第三节那个"谁先印闭眼"的问题在这里会重演一次**：
`t1 = create_task(...)` 那一行执行完，甲**还没印**"甲 闭眼"。
印它的是紧接着的 `create_task` 之后、程序走到 `gather` 时才发生的调度。
所以你看到的仍是甲在乙上面——因为 `t1` 比 `t2` 先登记。

### 串行版（把 `wake_two` 换成这个）

```python
async def wake_two():
    a = await wake("甲", 0.3)
    b = await wake("乙", 0.1)
    return [a, b]
```

```
   甲 闭眼
   甲 睁眼
   乙 闭眼
   乙 睁眼
花掉 0.40s | 返回 ['甲', '乙']
```

### 这两份输出唯一的差别不在最后那行

```
并发： 花掉 0.30s | 返回 ['甲', '乙']
串行： 花掉 0.40s | 返回 ['甲', '乙']
```

**返回列表完全一样。** 结果对不对，判不出有没有并发——
能判的只有**耗时**和**那四行闭眼/睁眼的先后**。

这一条是今天最实用的一句：以后你看到「四个请求都 200 回来了，肯定是并发了吧」，
现在你知道这句话什么都没说。

## 第 3 题 · 三段 0.40 / 1.00 / 0.91，改一行之后 0.70

### 三段各怎么算

四个长度互不相同：`0.4`、`0.1`、`0.2`、`0.3`。

| 段 | 四个函数各是什么 | 怎么算 | 实测 |
|---|---|---|---|
| A | 四个 `await asyncio.sleep` | **最长那个** = 0.40 | 0.40s |
| B | 四个 `time.sleep` | **求和** = 0.4+0.1+0.2+0.3 | 1.00s |
| C | 甲 melt、乙 order、丙 melt、丁 order | 按住线程的那几个**求和**，其余叠进去 | 0.91s |

B 段是第六节那个实验的四倍版：`gather` 一句都没帮上忙，0.4+0.1+0.2+0.3 = 1.00。

**C 段的 0.90 = 甲(0.4) + 丙(0.2) + 丁(0.3)。**
甲和丙都是 `melt`，它们摞起来；乙那 0.1 落在丙按着线程的那 0.2 里，白睡。
丁排在丙后面，**它 0.60 才开始数自己的 0.3**。

### 只改一行之后

把 C 段的 `melt("丙", 0.2)` 换成 `order("丙", 0.2)`：

```
C 两个各带一半             : 0.70s
比值 C 除以 A              : 1.76
```

**0.70 = 甲的 0.4 + 后面三个人同时数完的最长那个 0.3。**
丙不再是阻塞的之后，乙丙丁三个人的起跑线全落在 `t = 0.40` 这一个时刻上，
于是要么一起 0.50 醒、要么 0.60 醒、要么 0.70 醒。
最慢的那个（丁，0.3）定了结束时间。**这就是第二节 B 段，只是前面多压了 0.4 秒。**

### 想亲眼看到那个时间线，给四行都插上打印

```python
async def order(name, sec):
    print(f"   {name}(order) 拿到线程 t={time.perf_counter() - T0:.2f}")
    await asyncio.sleep(sec)
    print(f"   {name}(order) 跑完     t={time.perf_counter() - T0:.2f}")
    return name
```

（`melt` 同样加两行，`main` 开头 `T0 = time.perf_counter()`。）
原版 C 段跑出来：

```
   甲(melt)  拿到线程 t=0.00
   甲(melt)  跑完     t=0.41
   乙(order) 拿到线程 t=0.41
   丙(melt)  拿到线程 t=0.41
   丙(melt)  跑完     t=0.61
   丁(order) 拿到线程 t=0.61
   乙(order) 跑完     t=0.61
   丁(order) 跑完     t=0.91
```

**倒数第三行是这份表里最值得停一下的地方**：
乙说好 0.51 醒，它 0.61 才"跑完"。
**闹钟到点不等于轮到你。** 那 0.1 秒的差距，就是丙按着线程不放的那段时间。

## 第 4 题 · `batch_slow.py` 参考实现

```python
import asyncio
import time


def chop(name, sec):
    time.sleep(sec)
    return name


async def make_coffee(name, sec):
    print(f"   {name} 开始冲")
    await asyncio.sleep(sec)
    print(f"   {name} 冲好了")
    return name


async def serial():
    start = time.perf_counter()
    await make_coffee("甲", 0.3)
    await make_coffee("乙", 0.3)
    await make_coffee("丙", 0.3)
    return time.perf_counter() - start


async def concurrent():
    start = time.perf_counter()
    await asyncio.gather(
        make_coffee("甲", 0.3),
        make_coffee("乙", 0.3),
        make_coffee("丙", 0.3),
    )
    return time.perf_counter() - start


async def order_demo():
    res = await asyncio.gather(make_coffee(2, 0.3), make_coffee(0, 0.1), make_coffee(1, 0.2))
    print("返回顺序:", res)


async def threaded():
    start = time.perf_counter()
    await asyncio.gather(
        asyncio.to_thread(chop, "甲", 0.2),
        asyncio.to_thread(chop, "乙", 0.2),
    )
    print(f"两个 to_thread 花掉 {time.perf_counter() - start:.2f}s")


async def main():
    s = await serial()
    print()
    c = await concurrent()
    print()
    print(f"串行 {s:.2f}s | 并发 {c:.2f}s | 比值 {c / s:.2f}")
    print()
    await order_demo()
    print()
    await threaded()


if __name__ == "__main__":
    asyncio.run(main())
```

### 直接跑它的真实输出

```
   甲 开始冲
   甲 冲好了
   乙 开始冲
   乙 冲好了
   丙 开始冲
   丙 冲好了

   甲 开始冲
   乙 开始冲
   丙 开始冲
   甲 冲好了
   乙 冲好了
   丙 冲好了

串行 0.90s | 并发 0.30s | 比值 0.33

   2 开始冲
   0 开始冲
   1 开始冲
   0 冲好了
   1 冲好了
   2 冲好了
返回顺序: [2, 0, 1]

两个 to_thread 花掉 0.20s
```

**第一段和第二段的六行是同一个 `make_coffee` 印的**，
差别只在外面是逐个 `await` 还是 `gather`。
「开始冲」和「冲好了」在第一段严格交替（一个彻底完蛋才轮到下一个），
在第二段先全部"开始"、再全部"好了"。
**这六行的排列就是今天全部内容。**

### 第三段那六行：要求 5 的验收点

```
   2 开始冲      ← 0.3s，最慢
   0 开始冲      ← 0.1s，最快
   1 开始冲      ← 0.2s
   0 冲好了      ← 完成的先后是 0、1、2
   1 冲好了
   2 冲好了
返回顺序: [2, 0, 1]   ← 却是传入的先后
```

**我把最慢的 `2` 放在第一个传进去，让"完成顺序"和"传入顺序"完全不同。**
如果你在这里返回了 `[0, 1, 2]`，你八成是自己一个一个收集了，红在第 4 项。

### 跑 `check.py` 的真实输出

```
✓ 1. 脚本跑得通（退出码 0）
✓ 2. 输出三行可解析（三行都在）
✓ 3. 行为 · 并发生效（串行 0.90s → 并发 0.30s，比值 0.33）
✓ 4. 行为 · gather 返回传入顺序（[2, 0, 1]）
✓ 5. 写法 · async 里没有阻塞调用（async 内无 time.sleep；chop() 是阻塞函数，被 threaded() 交给线程）
✓ 6. 写法 · asyncio.run 只在最外层（asyncio.run 只在最外层的开关里）

── 以下 3 项机器判不了，你自己批 ──
  □ 第 1 题：五个形状你都是先写下猜测再跑的，而且至少有一个猜错了
  □ 第 2 题：你的 wake_two 是关着教案写的，而且你亲手把它改回串行跑过一次
  □ 第 3 题：三段耗时你都是先算再跑的；只改一行之后那版的新耗时你写下来了

Day 3 过关：6/6 项自动检查通过，3 项需你自批
```

（秒数那行可能是 `0.91s` 或 `0.31s`，正常。）

### 三个最可能被写错的地方

**1. `chop` 写成 `async def`。** 它里面的 `time.sleep` 立刻变成第六节那个病。
**但只有第 5 项会红**（我撞过：5/6 通过）——
因为你那三趟测量用的是 `make_coffee`，`chop` 慢不慢不影响它们。
**这一种红最阴**：数字全对，只是你写的那个阻塞函数根本没被搬走。
要求 6 要的就是一个**你不动它的 `def`**：`to_thread` 的全部意义是
"这个东西我改不了，所以我把它搬走"。

**2. 比值算反。** `c / s` 是 0.33，`s / c` 是 3.0。
第 3 项查的是 `比值 ≤ 0.6`，写成 3.00 会红在比值那一格，
而你的串行并发两格都是对的——**这种红最容易被误以为"我并发没做好"**。

**3. `main` 写好了，开关里却没写 `asyncio.run(main())`。**
脚本一行都不印，**而退出码是 0**，所以第 1 项是绿的。
红的是 2、3、4、6 四项（我撞过：2/6 通过）：

```
✗ 2. 输出三行可解析 —— 缺：串行/并发/比值那行…；顺序那行…；to_thread 那行…
✗ 3. 行为 · 并发生效 —— 那行耗时没印出来，第 2 项就没能解析——先看第 1、2 项的报错
✗ 6. 写法 · asyncio.run 只在最外层 —— 开关里面没有 asyncio.run —— 整个脚本的入口应该长这样：if __name__ == "__main__":
```

第 6 项那一句直接把入口抄给你了。而第 2、3 项那两串"缺"都是同一件事的重复：
**什么都没印。** 这就是第 1 题形状 1 的反面：**协程是张票，没人替你去兑换，它就永远不跑。**

## 今天可带走的四句

1. **`async def f()` 只是造一张票**；`await` 是当场等完，`create_task` / `gather` 才是登记。
   **并发来自登记，不来自 `await`。**
2. **`gather` 的返回跟着传入，打印跟着完成。** 两者可以完全不同，而且这往往是你要的。
3. **一个 `time.sleep` 伤害的不是它自己，是排在它后面的所有人。**
   改不动就 `to_thread`，但它**要和 `gather` 一起用**才有并发。
4. **`asyncio.run` 只能出现在最外层。** 协程里面再调它，`RuntimeError`。

四句合成一句：

> 看到 async 代码，先问**这几个等待是同一段墙上时间里同时发生，还是一个等完才轮到下一个**；
> 再问**有没有哪一行写着等，却死活不交出线程**。
