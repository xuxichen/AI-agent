# Day 3 · 参考答案

> 今天所有知识点都指向一句话：**并发来自「登记」，不是来自 `await`。**
> `create_task` / `gather` 是登记，`await` 是取结果。

---

## 第 1 题 · 0.30s 与 0.15s

A 逐个 `await`：第一个 `await slow()` 就地把控制权交出去并**等它完成**，
第二个才开始。两次 0.15s 相加 = 0.30s。

B `create_task`：两行 `create_task` 连续执行，**登记的那一刻两个协程都在循环里了**，
它们的 `asyncio.sleep` 同时开始倒计时。后面两个 `await` 只是去取已经差不多完成的结果。

关键：**B 里的 `create_task` 两行之间没有任何 `await`**，所以它们是一次性全登记进去的。
如果你在中间插一个 `await`，就退化成 A 了。

## 第 2 题 · 参考实现

```python
import asyncio
import time

import httpx
from fastapi import FastAPI

app = FastAPI()


@app.get("/slow/{i}")
async def slow(i: int):
    await asyncio.sleep(0.2)      # 必须是 asyncio.sleep
    return {"i": i}


async def main():
    transport = httpx.ASGITransport(app=app)
    async with httpx.AsyncClient(transport=transport, base_url="http://local") as client:
        t0 = time.perf_counter()
        for i in range(3):
            await client.get(f"/slow/{i}")
        serial = time.perf_counter() - t0

        t0 = time.perf_counter()
        res = await asyncio.gather(*[client.get(f"/slow/{i}") for i in (2, 0, 1)])
        concurrent = time.perf_counter() - t0

    print(f"串行 {serial:.2f}s | 并发 {concurrent:.2f}s | 比值 {concurrent / serial:.2f}")
    print("返回顺序:", [r.json()["i"] for r in res])


asyncio.run(main())
```

**为什么用 `ASGITransport` 而不是起 uvicorn**：它把 FastAPI 应用直接接在 httpx 上，
请求走的是**真实的 ASGI 协议栈**（路由、参数解析、`async def` 调度全都经过），
但不需要开端口、不需要第二个进程、不会有端口占用问题。
这是我实测过的：串行 **0.61s**、并发 **0.20s**、比值 **0.33**、顺序 `[2, 0, 1]`。

`async with` 必须**包住两次请求**：`AsyncClient` 退出时会关掉连接池，
如果你在 `async with` 外面用 `client`，会撞上 `Event loop is closed`。

**`res` 是 Response 列表，不是 JSON 列表**——所以要 `r.json()["i"]`。
这点和 JS 的 `fetch` 一样：`Promise.all` 给你的也是 Response，得再 `.json()`。

## 第 3 题 · 三个要点背后的机制

```
main 正常结束
RuntimeWarning: coroutine 'slow' was never awaited
退出码 0
```

`slow()` 返回的是一个 **coroutine 对象**，它是个惰性容器，装着「待执行的代码 + 参数」。
没人 `await` 它 → 没人把它交给事件循环 → 函数体一行都没跑。

warning 出现在 `main 正常结束` **之后**，因为它是在那个 coroutine 对象被**垃圾回收**时发出的——
对象没人引用了，CPython 回收它，发现它从没被 await 过，才抱怨一句。

**这就是它危险的地方**：抱怨发生在 GC 时，位置不确定，输出在 stderr，
在日志刷屏的生产环境里你根本看不见。而退出码是 0，CI 也不会拦你。

JS 那边：`slow()` 一调用 Promise 就开始跑了，所以 `我被执行了` 会打印。
Node 对未处理的 rejection 默认**让进程非零退出**（`--unhandled-rejections=throw`，v15 起的默认值），
比 Python 严格得多。

**给你的纪律**：在 Python 里看到 `async def` 的调用点，眼睛要自动检查前面有没有 `await`
（或者有没有被 `create_task` / `gather` 接住）。这是从 JS 转过来最需要重建的一个肌肉记忆。

## 第 4 题 · 异常语义对照

| | 崩溃版 | 收集版 | 结果形状 |
|---|---|---|---|
| Python | `gather(...)` | `gather(..., return_exceptions=True)` | 异常实例**直接**混在结果列表里 |
| JS | `Promise.all` | `Promise.allSettled` | 统一包成 `{status, value}` / `{status, reason}` |

```
默认: ZeroDivisionError
return_exceptions: ['ZeroDivisionError', 'int']
```

**Python 这个设计的代价**：`res[0]` 可能是数据也可能是异常，类型不统一。
你必须写：

```python
results = await asyncio.gather(*tasks, return_exceptions=True)
ok = [r for r in results if not isinstance(r, Exception)]
failed = [r for r in results if isinstance(r, Exception)]
```

漏掉这一步，异常对象会被当成正常数据传给下游——
比如 Day 9 你并发调 3 次大模型，其中一次超时，
你把 `APITimeoutError` 对象塞进了 `messages` 列表，然后在拼接 prompt 时才炸，
报错位置离真正的原因隔了十万八千里。

**还有一个坑**：`gather` 默认模式下第一个异常抛出时，**其余任务不会被取消**，
它们还在后台跑。要取消得用 `asyncio.TaskGroup`（3.11+），它保证任一失败就取消全部。
本仓库是 Python 3.13，Day 6 会用 `TaskGroup` 对照一次。

## 第 5 题 · 费曼任务参考措辞

> 1. Python 里调用 `async def` 函数**不执行函数体**，只返回一个 coroutine 对象——
>    它像一张待办的工单，装着代码和参数，但没人去做。
> 2. 工单要交给事件循环才会被执行，交的方式有三种：`await` 它、
>    `asyncio.create_task()` 包它、或者扔进 `asyncio.gather()`。
> 3. JS 正相反：`f()` 一调用，Promise 的 executor **立即同步执行**，
>    `await` 只决定「我在哪一行等结果」，不决定「跑不跑」。

同事反问「那 Python 怎么让它立刻开始跑」时的答案：`asyncio.create_task(slow())`。

再补一句能显示你理解了本质：**所以 Python 的 `await` 承担了两个职责——启动 + 等待**，
而 JS 的 `await` 只承担等待。这就是为什么 Python 里漏写 `await` 是「什么都没发生」，
JS 里漏写 `await` 只是「顺序不受控」。

## 第 6 题 · 阻塞调用的杀伤力

把端点改成 `time.sleep(0.2)` 后，实测比值从 **0.33 涨到 0.99**
（`串行 0.61s | 并发 0.61s`）。`check.py` 会报 **3 项 ✗**：第 3（比值）、第 5（源码里有 `time.sleep`）、
第 6（端点没 `await asyncio.sleep`）——一处病因，三项显形，和 Day 2 同一个道理。

**为什么结果还是对的**：`time.sleep` 只是占着线程不放，它最终还是返回了，
`{"i": i}` 照样生成。三个请求依次被阻塞、依次完成，`gather` 照样按传入顺序收集。
**功能完全正确，只有耗时退化成串行。**

这就是它比崩溃更难发现的原因：单元测试全过、返回值全对、日志无异常。
只有在你压测或者用户抱怨慢的时候才暴露。

### 加分题：必须调阻塞函数怎么办

```python
@app.get("/slow/{i}")
async def slow(i: int):
    await asyncio.to_thread(time.sleep, 0.2)   # 丢给线程池
    return {"i": i}
```

`asyncio.to_thread(fn, *args)` 把 `fn` 扔到**默认线程池**执行，
立刻返回一个可 await 的对象——事件循环的主线程被释放了，其他协程能继续跑。
所以并发恢复了。

**实测数字**（本机，同一台机器同一份代码只改了这一行）：

| 端点里写什么 | 串行 | 并发 | 比值 |
|---|---|---|---|
| `await asyncio.sleep(0.2)` | 0.61s | 0.20s | **0.33** |
| `time.sleep(0.2)` | 0.61s | 0.61s | **0.99** |
| `await asyncio.to_thread(time.sleep, 0.2)` | 0.62s | 0.21s | **0.34** |

第三行值得看两秒：线程切换的开销只让比值从 0.33 变成 0.34。
**在 I/O 等待面前，线程开销可以忽略**——所以不要为了「更纯」而回避 `to_thread`。

**你以后会大量用到这一招**，因为 Python 生态里同步库远多于异步库：

| 场景 | 阻塞调用 | 包法 |
|---|---|---|
| Day 15 Embedding | `model.encode(texts)` | `await asyncio.to_thread(model.encode, texts)` |
| Day 18 文档切分 | 读大文件 + 正则 | `await asyncio.to_thread(split, path)` |
| Day 16 Chroma | `collection.query(...)` | 同上 |

**判断标准很简单**：这个函数会不会让当前线程停下来等？
会 → 在 async 里必须 `to_thread`。不会（它自己就是协程）→ 直接 `await`。

**注意 `to_thread` 不是万能**：CPU 密集型任务丢进线程池**不会变快**，
因为 CPython 有 GIL，同一时刻只有一个线程在执行字节码。
它只解决「I/O 等待时不要占着主线程」。真要并行算，得用 `ProcessPoolExecutor`。
这也是计划里 Day 3「并发与并行」那半句的答案：**asyncio 给你并发，不给你并行。**
