# Day 3 · await 不会让代码变快

> 计划里这一天是「异步编程：asyncio 基础、协程、事件循环、并发与并行」。
> 你写过 JS，`async/await` 语法对你不是新知识——所以本日只讲**两边语义真的不同的地方**，
> 以及 Python 特有的两种「写了 async 但一点没并发」的失败模式。

---

## 今日问题

这两段代码都用了 `await`，耗时差一倍：

```python
# A：0.30s
async def a():
    await slow()      # 0.15s
    await slow()      # 0.15s

# B：0.15s
async def b():
    t1 = asyncio.create_task(slow())
    t2 = asyncio.create_task(slow())
    await t1
    await t2
```

**A 明明也是 async，为什么没有并发？`await` 这个词到底在做什么？**

---

## 学习目的

一句话：**`await` 不是「让它异步执行」，而是「在这里交出控制权，等它完成再回来」。**

`await x` 会**当场等 x 跑完**。所以 A 里的两个 `await` 是串行的——
并发来自 `create_task`（或 `gather`），它把协程**登记到事件循环**上，
登记的那一刻它就开始跑了，后面的 `await` 只是去取结果。

JS 完全一样：`await f(); await g();` 也是串行的，
要并发得 `const [a, b] = await Promise.all([f(), g()])`。
差别在于 JS 里 `f()` **一调用就开始跑**（Promise 是立即执行的），
而 Python 里 `slow()` 只**创建一个 coroutine 对象，什么都不跑**——这是下面第一个坑的根源。

---

## 学习内容

### 一、忘了 await：Python 比 JS 更安静地失败

```python
async def main():
    slow()            # 没有 await
asyncio.run(main())
```

实测输出（本机）：

```
<stdin>:5: RuntimeWarning: coroutine 'slow' was never awaited
RuntimeWarning: Enable tracemalloc to get the object allocation traceback
```

**没有异常，程序正常退出码 0**，只有一行 warning。
JS 里对应的错误是 `UnhandledPromiseRejection`，Node 会**直接让进程非零退出**。
Python 这里宽容得多——这在 Day 9 你调用大模型 API 时会变成真 bug：
忘了 `await`，请求压根没发出去，你只看到一行容易被刷屏盖掉的 warning。

### 二、gather 的两个语义：顺序与异常

**顺序**——实测传入 `(2, 0, 1)`：

```python
res = await asyncio.gather(f(2), f(0), f(1))
print(res)        # [2, 0, 1]
```

返回顺序 = **传入顺序**，不是完成顺序。即使 `f(0)` 最先跑完，它也排在第二个位置。
JS 的 `Promise.all` 语义相同。这条能让你放心地用下标对应请求。

**异常**——这是与 JS 分歧最大的一处：

```python
async def bad(): raise ZeroDivisionError
async def ok():  return 1

await asyncio.gather(bad(), ok())
# ZeroDivisionError 直接向外抛，整个 gather 崩掉

await asyncio.gather(bad(), ok(), return_exceptions=True)
# [ZeroDivisionError(), 1]   ← 异常被当成结果放进列表
```

对照 JS：`Promise.all` 对应第一种，`Promise.allSettled` 对应第二种。
但 `allSettled` 返回的是 `{status, value/reason}` 包装对象，
Python 的 `return_exceptions=True` **直接把异常实例塞进结果列表**——
所以你必须自己 `isinstance(r, Exception)` 判断，否则会把异常当正常结果往下传。

### 三、阻塞调用会杀死整个事件循环

```python
async def bad():
    time.sleep(0.3)      # 不是 await asyncio.sleep
```

实测：整个循环被卡住 0.31s，**其他协程一个都跑不了**。

原因：事件循环是**单线程**的。`time.sleep` 不交出控制权，它就把这唯一的线程占着。
这跟 JS 里在 async 函数中写 `while(Date.now() - t < 300){}` 是同一件事。

Day 9 之后你会反复撞上这个：`requests.get()`、`open().read()` 大文件、
CPU 密集的文本切分——**全都是阻塞的**。放进 async 函数里，你的并发就归零了。
出路有两条，Day 6 会用到第一条：

```python
await asyncio.to_thread(blocking_fn, arg)     # 丢到线程池
```

### 四、asyncio.run 只能在最外层

```python
async def inner(): asyncio.run(other())       # 在协程里再 run
```

实测报错：

```
RuntimeError: asyncio.run() cannot be called from a running event loop
```

`asyncio.run()` 的职责是**新建一个事件循环、跑到结束、关掉它**。
已经在循环里了，就没有「新建」的余地。

对你的直接影响：FastAPI 的路由函数本身就在循环里跑，
所以**路由里永远不能写 `asyncio.run`**，只能 `await`。
这是从「写脚本」切到「写服务」时最容易带过去的坏习惯。
