## 一、`async def` 的函数，调用它的时候它不跑

这是 Python 和你的 JS 经验**真正分岔**的地方。JS 里你写 `f()`，`f` 的函数体立刻就执行了；
Python 里 `async def` 的函数被调用时，**函数体一行都不执行**。

先看这个文件里唯一一个新东西：`asyncio`。它是 Python 自带的异步工具包，
`import asyncio` 之后，今天你会用到它里面四个名字：
`run`、`sleep`、`create_task`、`gather`。一个一个来。

### ① 建文件

```bash
cd stage1/day003_async
cat > code/python/01_first_coroutine.py <<'PY'
import asyncio


async def slow():
    print("   slow 的函数体在跑")
    await asyncio.sleep(0.2)
    return 42


print("=== A 只调用，不交给 asyncio.run ===")
thing = slow()
print("thing 是什么 :", thing)
print("thing 的类型 :", type(thing))

print()
print("=== B 同一个 slow()，交给 asyncio.run ===")
result = asyncio.run(slow())
print("asyncio.run 还回来的 :", result)
PY
```

`async def slow():` 和你昨天写的 `def slow():` 只差两个字母，
但它造出来的东西**不是函数**——它是一个「协程工厂」：调用它得到一张票，不是得到一个结果。

`type(x)` 你昨天在第二节用过（`type(add.__defaults__[0])` 那个形状），它印出 x 是什么类型。

### ② 先猜再跑

猜两件事，写下答案再跑：

1. A 段那三行 `print` 里，会不会夹着一行 `   slow 的函数体在跑`？
2. `type(thing)` 会印出 `<class 'function'>` 吗？

```bash
uv run python code/python/01_first_coroutine.py
```

跑完 `cd ../..` 回仓库根。

### ③ 真实输出

```
=== A 只调用，不交给 asyncio.run ===
thing 是什么 : <coroutine object slow at 0x10a78a440>
thing 的类型 : <class 'coroutine'>

=== B 同一个 slow()，交给 asyncio.run ===
   slow 的函数体在跑
asyncio.run 还回来的 : 42
<sys>:0: RuntimeWarning: coroutine 'slow' was never awaited
```

`0x10a78a440` 是内存地址，你机器上一定不一样，**这个正常**（昨天第五节讲过：地址永远别拿来做比较）。

### ④ 逐行对上

**A 段没有那行「slow 的函数体在跑」。**
`thing = slow()` 只是把 `slow` 的函数体**打包成一个对象**交给你，一个字节都没执行。
`thing` 拿着的是那张票：`<coroutine object slow at 0x...>`，类型 `<class 'coroutine'>`。

**B 段那行印出来了，而且是在 `asyncio.run 还回来的 : 42` 之前。**
`asyncio.run(x)` 的职责很窄：**新建一个事件循环，把 x 这个协程跑到结束，然后把循环关掉**。
它是今天唯一一个「把协程变成结果」的动作。你昨天学的 `def` 函数是直接返回结果的，
协程不是——**协程必须被一个循环驱动**。

**最后一行的警告是给 A 段那张票的。**
`coroutine 'slow' was never awaited` 读作「有一个叫 slow 的协程，你造了它，但从来没跑它」。
注意两件事：

1. 它印在**整个文件的最末尾**，不是印在 A 段那三行中间——因为 Python 是在**程序快退出时**才发现这张票还在手上。
2. **退出码是 `0`。** 我量了：

```bash
uv run python code/python/01_first_coroutine.py > /dev/null; echo "退出码=$?"
```

```
退出码=0
```

也就是说：**忘了 `await` 不会让你的程序失败，它只会让你的程序安静地什么都不做。**
这一条你今天要先记下形状，第七节会让你看到它在真实代码里长什么样。

## 二、主现象：`await` 是当场等，`create_task` 才是并发

今天全部的东西都从这一节长出来。

### ① 建文件

```bash
cd stage1/day003_async
cat > code/python/02_serial_vs_concurrent.py <<'PY'
import asyncio
import time


async def slow(label):
    print(f"   {label} 开始")
    await asyncio.sleep(0.2)
    print(f"   {label} 结束")
    return label


async def serial():
    start = time.perf_counter()
    await slow("a")
    await slow("b")
    await slow("c")
    print(f"串行：逐个 await 花掉 {time.perf_counter() - start:.2f}s")


async def with_tasks():
    start = time.perf_counter()
    t1 = asyncio.create_task(slow("a"))
    t2 = asyncio.create_task(slow("b"))
    t3 = asyncio.create_task(slow("c"))
    print("三个 create_task 已经登记完，还没 await 任何一个")
    await t1
    await t2
    await t3
    print(f"并发：三个 task 花掉 {time.perf_counter() - start:.2f}s")


async def main():
    print("=== A 逐个 await ===")
    await serial()
    print()
    print("=== B 先登记三个 task，再逐个 await ===")
    await with_tasks()


asyncio.run(main())
PY
```

`import time` 是 Python 自带的计时工具，`time.perf_counter()` 读一下秒表。

输出里那个 `{time.perf_counter() - start:.2f}` 是新写法，拆开看：

| 部分 | 意思 |
|---|---|
| `{ ... }` | 昨天学过的 f-string 挖空，JS 的 `${...}` |
| `: .2f` | 冒号后面是格式说明：**留 2 位小数的浮点数** |

所以 `f"{0.19843:.2f}"` 得到 `'0.20'`。今天所有秒数都用这个写法，省得你去看八位小数。

### ② 先猜再跑

三件事：

1. A 段的六行「开始 / 结束」，会印成 `a开始 a结束 b开始 b结束 c开始 c结束`，
   还是 `a开始 b开始 c开始 a结束 b结束 c结束`？
2. B 段那行「三个 create_task 已经登记完」，会出现在第一个「a 开始」**之前**还是**之后**？
3. B 段的花费，比 A 段大还是小？

```bash
uv run python code/python/02_serial_vs_concurrent.py
```

跑完 `cd ../..`。

### ③ 真实输出

```
=== A 逐个 await ===
   a 开始
   a 结束
   b 开始
   b 结束
   c 开始
   c 结束
串行：逐个 await 花掉 0.60s

=== B 先登记三个 task，再逐个 await ===
三个 create_task 已经登记完，还没 await 任何一个
   a 开始
   b 开始
   c 开始
   a 结束
   b 结束
   c 结束
并发：三个 task 花掉 0.20s
```

秒数你可能是 `0.61s` / `0.21s`，那是正常的。**要成立的是：B 那一行明显小于 A 那一行。**

### ④ 逐行对上

**A 段是 6 行严格交替的。**
`await slow("a")` 的意思是：「跑到 a 结束，我才回来」。
所以 b 只能在 a 完全结束之后才开始——**三个 0.2 秒摞起来 = 0.60s**。

**B 段最上面那行位置很关键。**
「三个 create_task 已经登记完，还没 await 任何一个」印在了所有「开始」**之前**。
这说明 `asyncio.create_task(...)` 干的事**只是登记**：它把协程交给事件循环，
在登记的那一刻，函数体还是**一行都没跑**（这和第一节 `slow()` 什么都不印是同一件事）。

**然后 a、b、c 三个「开始」连着印出来，三个「结束」再连着印出来。**
为什么？第一个 `await t1` 让出了控制权，循环终于可以干活了：
它切到 a，a 印「开始」然后睡（把控制权交回来）；循环切到 b，b 印「开始」然后睡；
切到 c，同理。**三个都已经开始睡了，才开始有人醒。**
所以 0.20s，不是 0.60s。

**这里有个你必须盯住的点**：`await t1` / `await t2` / `await t3` **也是排着等的**，
和 A 段形状一样，为什么这里就并发了？
——因为 `t1 t2 t3` 是**已经登记好的任务**，`await` 它们只是去取结果；
A 段里 `await slow("a")` 的 `slow("a")` 是张刚造的票，**跑它和等它被合并成了同一个动作**。

一句话：**`await` 从来不会让事情变并发，它只是「我在这里等」。让它并发的是 `create_task`。**

## 三、`await` 期间，循环去跑了谁

上一节你看到 `await` 会把控制权交出去。这一节把「交给谁」看清楚。

### ① 建文件

```bash
cd stage1/day003_async
cat > code/python/03_what_await_yields.py <<'PY'
import asyncio
import time


async def nap(name, sec):
    print(f"   {name} 躺下")
    await asyncio.sleep(sec)
    print(f"   {name} 起来")


async def main():
    start = time.perf_counter()
    t = asyncio.create_task(nap("邻居", 0.1))
    await nap("我", 0.3)
    print(f"我自己起来了。总共过了 {time.perf_counter() - start:.2f}s")
    await t
    print(f"两个都起来了。总共过了 {time.perf_counter() - start:.2f}s")


asyncio.run(main())
PY
```

`nap` 只有一件事：躺下、睡 `sec` 秒、起来。我给它一个名字参数，是为了让输出能说是谁在睡。

### ② 先猜再跑

这四个字谁先谁后，写下你的顺序：`我 躺下`、`邻居 躺下`、`我 起来`、`邻居 起来`。

再猜一遍第二行——**`我 躺下` 和 `邻居 躺下`，哪一行在上面？**

```bash
uv run python code/python/03_what_await_yields.py
```

跑完 `cd ../..`。

### ③ 真实输出

```
   我 躺下
   邻居 躺下
   邻居 起来
   我 起来
我自己起来了。总共过了 0.30s
两个都起来了。总共过了 0.30s
```

### ④ 对上

这四行是这个文件的全部价值，逐条看：

**第 1、2 行：`我 躺下` 在 `邻居 躺下` 前面。**
`t = asyncio.create_task(nap("邻居", 0.1))` 登记完，**邻居还没躺下**。
程序继续往下走，走到 `await nap("我", 0.3)`：这一句先跑 `nap` 的函数体（印「我 躺下」），
再跑到 `await asyncio.sleep(0.3)` 才**第一次交出控制权**。
控制权一交出去，循环立刻切给邻居，于是「邻居 躺下」这时才印。
——和第二节那个「登记完，还没 await 任何一个」是同一个机制，你现在看过两遍了。

**第 3、4 行：`邻居 起来` 在 `我 起来` 前面。**
邻居只睡 0.1，我睡 0.3。**我在睡我的 0.3 秒的时候，循环把邻居叫醒、让他跑完了。**
这就是 `await` 的全部含义：**我在这里等，但循环没闲着，它去跑别的东西了。**

**最后两行都是 0.30s。**
`await t` 那一步**什么都没等**，因为等我醒过来时，邻居早就跑完了。
`await` 一个已经完成的 task，花掉的真实时间是 0。

现在你可以回答今日问题了：
**第二条命令的 0.2 秒没有消失，是三个 0.2 秒占了同一段墙上的时间。**
每个 `slow()` 都睡了完整的 0.2，一秒都没少——只是它们同时睡。

> **今天唯一一个术语现在可以给了**：这一整套「一个循环 + 一堆任务，谁交出控制权就切给下一个」
> 就叫**事件循环**（event loop）。它不是某个对象的名字，它就是 `asyncio.run` 帮你建起来的那个东西。
> **它只有一个线程。** 这句话第六节要用来解释一件很疼的事。

## 四、`gather`：完成顺序和返回顺序不是一回事

`create_task` 三次再 `await` 三次太啰嗦。`asyncio.gather(...)` 是它的打包版，
你以后 90% 的异步代码用的就是它。它有一个你必须先看到的性质。

### ① 建文件

```bash
cd stage1/day003_async
cat > code/python/04_gather_order.py <<'PY'
import asyncio
import time


async def work(sec, label):
    await asyncio.sleep(sec)
    print(f"   {label} 睡够了（{sec}s）")
    return label


async def main():
    start = time.perf_counter()
    print("=== 传入顺序：甲 0.3、乙 0.1、丙 0.2 ===")
    res = await asyncio.gather(work(0.3, "甲"), work(0.1, "乙"), work(0.2, "丙"))
    print("谁先睡够谁先印，所以完成的先后是 乙 丙 甲")
    print(f"gather 还回来的列表 : {res}")
    print(f"三个一起花掉 {time.perf_counter() - start:.2f}s")


asyncio.run(main())
PY
```

`work(sec, label)` 第一个参数睡多久、第二个是自己的名字。我把「睡多久」放前面，
是为了让传入顺序 `(0.3, 0.1, 0.2)` 和名字顺序 `(甲, 乙, 丙)` **故意不一致**——
待会儿你才能看出返回顺序到底跟着谁。

### ② 先猜再跑

`res` 会是 `['甲', '乙', '丙']`（传入顺序）还是 `['乙', '丙', '甲']`（完成顺序）？

```bash
uv run python code/python/04_gather_order.py
```

跑完 `cd ../..`。

### ③ 真实输出

```
=== 传入顺序：甲 0.3、乙 0.1、丙 0.2 ===
   乙 睡够了（0.1s）
   丙 睡够了（0.2s）
   甲 睡够了（0.3s）
谁先睡够谁先印，所以完成的先后是 乙 丙 甲
gather 还回来的列表 : ['甲', '乙', '丙']
三个一起花掉 0.30s
```

### ④ 对上

**打印的顺序是完成顺序：乙、丙、甲。** 因为谁睡够谁就当场印一行。
**返回的列表是传入顺序：`['甲', '乙', '丙']`。**
`gather` 把结果按「你在第几个位置交给它」排好，第一个位置放甲的结果，以此类推。

这条性质很重要，因为它意味着：**你可以放心用下标去对应任务。**
`res[0]` 永远是甲的返回值，哪怕甲是最后一个跑完的。
你在 JS 里用 `Promise.all` 得到的就是这个行为，**这里一模一样**。

**`三个一起花掉 0.30s`**：三个任务的耗时是 0.3、0.1、0.2，加起来是 0.6，
但只花了 0.3——**等于最慢的那一个**。这也是一模一样的 `Promise.all` 语义。

> `gather` 在内部做的就是你第二节手写的动作：把每个协程登记成任务，然后挨个收结果。
> 你现在两种方式都见过了，以后写 `gather`，脑子里放第二节那张「三个开始连着印」的画面就行。

## 五、JS 对照：`Promise` 一出生就在跑，协程不会

第四节开头我说「这里和 JS 一模一样」，那是 `gather` 的**返回顺序**。
真正不一样的是**第一节的机制**：你的 JS 里，函数被调用就是会跑。

这个文件把两边摆在同一屏上。

### ① 建文件

```bash
cd stage1/day003_async
cat > code/js/05_promise_is_eager.js <<'JS'
function sleep(sec, label) {
  console.log(`   ${label}：函数体第一行，一调用就印`);
  return new Promise((resolve) => setTimeout(() => resolve(label), sec * 1000));
}

async function sectionA() {
  console.log("=== A 只调用，不 await，它已经在跑了 ===");
  const p = sleep(0.1, "甲");
  console.log("p 是什么 :", p);
  console.log("现在才去等它 :", await p);
}

async function sectionB() {
  console.log("=== B 三个 sleep 连着调用，还没 await ===");
  const all = [sleep(0.3, "甲"), sleep(0.1, "乙"), sleep(0.2, "丙")];
  console.log("上面三行如果已经印完，说明三个都在计时了");
  const res = await Promise.all(all);
  console.log("Promise.all 返回 :", res);
}

async function main() {
  await sectionA();
  console.log();
  await sectionB();
}

main();
JS
```

这个文件里有三样你熟的东西：`new Promise(...)` 一造出来就开始计时、
`setTimeout(fn, 100)` 是 100 **毫秒**（所以我把秒乘了 1000）、
`Promise.all` 等一组 Promise。今天的对照全靠它们。

### ② 先猜再跑

第一节 Python 的 A 段，`thing = slow()` 之后**什么都没印**。
这里 `const p = sleep(0.1, "甲")` 之后，`甲：函数体第一行，一调用就印` 会不会印出来？

```bash
node code/js/05_promise_is_eager.js
```

跑完 `cd ../..`。

### ③ 真实输出

```
=== A 只调用，不 await，它已经在跑了 ===
   甲：函数体第一行，一调用就印
p 是什么 : Promise { <pending> }
现在才去等它 : 甲

=== B 三个 sleep 连着调用，还没 await ===
   甲：函数体第一行，一调用就印
   乙：函数体第一行，一调用就印
   丙：函数体第一行，一调用就印
上面三行如果已经印完，说明三个都在计时了
Promise.all 返回 : [ '甲', '乙', '丙' ]
```

### ④ 两边对上

| | Python | JS |
|---|---|---|
| 调用之后、`await` 之前 | **函数体一行都没跑**，手里是一张票 `<coroutine object ...>` | **函数体第一行已经印出来了**，手里是 `Promise { <pending> }` |
| 三个连着你调用三个 | 三个都不跑（第二节的 B 段，登记行在最上面） | 三个都**已经**在跑（上面三行连着印完） |
| 想拿结果 | 必须 `asyncio.run` 或 `await` | `await`，或者 `.then` |
| 等一组、保持传入顺序 | `asyncio.gather(...)` | `Promise.all(...)` |

**这就是那一个字的差别**：`Promise` 是**急**的（eager），造出来就跑；
`coroutine` 是**懒**的（lazy），你不驱动它，它永远不动。

所以第一节那行 `coroutine 'slow' was never awaited` 的警告，在 JS 里根本没有对应物——
JS 里你忘了 `await`，事情**照样做了**，只是你没等它；
Python 里你忘了 `await`，事情**压根没做**，而且退出码还是 0。

> **移植代码时最容易带过来的一条**：你在 JS 里习惯的
> `const p = doSomething(); const q = doOther(); await p; await q;` 是并发的。
> 在 Python 里同样的形状**不并发**，因为 `doSomething()` 只是造了张票。
> Python 要写成 `asyncio.create_task(...)` 或者干脆 `gather(...)`。

## 六、阻塞调用会把整个循环按死

第三节给过那句话：**事件循环只有一个线程**。这一节你亲眼看到它值多少钱。

### ① 建文件

```bash
cd stage1/day003_async
cat > code/python/06_blocking.py <<'PY'
import asyncio
import time


async def using_sleep(name, sec):
    await asyncio.sleep(sec)
    return name


async def using_time_sleep(name, sec):
    time.sleep(sec)
    return name


async def run_three(fn, label):
    start = time.perf_counter()
    await asyncio.gather(fn("甲", 0.2), fn("乙", 0.2), fn("丙", 0.2))
    print(f"{label} gather 三个各 0.2s，花掉 {time.perf_counter() - start:.2f}s")


async def main():
    print("=== A 三个 await asyncio.sleep ===")
    await run_three(using_sleep, "await asyncio.sleep :")
    print()
    print("=== B 三个 time.sleep，别的都一样 ===")
    await run_three(using_time_sleep, "time.sleep         :")


asyncio.run(main())
PY
```

两个函数只差**一行**：一个是 `await asyncio.sleep(sec)`，一个是 `time.sleep(sec)`。
`run_three` 收一个**函数**当参数（`fn`），这是昨天第五节你就会的「函数是个对象，能当参数递」。

### ② 先猜再跑

A 段是 0.20s（第二节的结论）。**B 段呢？它同样用了 `gather`，三个任务同样登记好了。**

B 会比 A 明显大，还是会跟 A 差不多？

```bash
uv run python code/python/06_blocking.py
```

跑完 `cd ../..`。

### ③ 真实输出

```
=== A 三个 await asyncio.sleep ===
await asyncio.sleep : gather 三个各 0.2s，花掉 0.20s

=== B 三个 time.sleep，别的都一样 ===
time.sleep         : gather 三个各 0.2s，花掉 0.62s
```

### ④ 对上

**B 段的 `gather` 一句都没生效。** 0.2 × 3 = 0.6，它就是 0.62。

原因在第三节那句话上。`gather` 把三个任务登记好，这没错；
循环也确实去跑了第一个——但第一个里面是 `time.sleep(0.2)`，
**这一行不交出控制权**。它就是霸着那个唯一的线程睡觉。
循环被它按住了 0.2 秒，才终于能切给第二个，第二个再按住 0.2 秒。

> **`await` 是「我等，你们谁都可以先走」；`time.sleep` 是「我不走，你们谁都别想走」。**
>
> 判断标准只有一条，你今天已经能自己说出来：
> **一个 async 函数里，凡是会让这一行原地停住、又不写 `await` 的调用，都是阻塞调用。**

对照你熟的一侧：JS 里如果你在 `async function` 里写一个 `while (Date.now() - t < 200) {}`
的死循环，整个页面卡住、按钮点不动——**同一件事**，Node 的循环也是单线程的。

**这就是为什么「我全改成 async 了」不等于「我并发了」。**
第七节给出路。

## 七、出路：`asyncio.to_thread` 把阻塞的丢给别的线程

第六节那个 `using_time_sleep` 如果是**别人的库**（读文件、老代码、CPU 活），你改不了它里面那行。
出路不是把它改成 `async`——是**把它挪出这个线程**。

### ① 建文件

```bash
cd stage1/day003_async
cat > code/python/07_to_thread.py <<'PY'
import asyncio
import time


def blocked_work(name, sec):
    time.sleep(sec)
    return name


async def one_by_one():
    start = time.perf_counter()
    await asyncio.to_thread(blocked_work, "甲", 0.2)
    await asyncio.to_thread(blocked_work, "乙", 0.2)
    await asyncio.to_thread(blocked_work, "丙", 0.2)
    print(f"逐个 await to_thread     : {time.perf_counter() - start:.2f}s")


async def together():
    start = time.perf_counter()
    await asyncio.gather(
        asyncio.to_thread(blocked_work, "甲", 0.2),
        asyncio.to_thread(blocked_work, "乙", 0.2),
        asyncio.to_thread(blocked_work, "丙", 0.2),
    )
    print(f"gather 三个 to_thread    : {time.perf_counter() - start:.2f}s")


async def main():
    print("=== blocked_work 是个普通函数，里面是 time.sleep，一个字都没改 ===")
    await one_by_one()
    await together()


asyncio.run(main())
PY
```

**注意 `blocked_work` 是 `def`，不是 `async def`。** 它里面那行 `time.sleep` 一个字都没改。
这正是第六节说的「改不了别人」的情形。

`asyncio.to_thread(函数, 参数1, 参数2)` 读作：
「把这个**普通函数**连同它的参数交给**另一个线程**去跑，跑完了回来告诉我，
这期间我这个线程空出来了，循环可以去做别的」。
它交出去的是一个**函数对象**（没有括号），参数跟在后面——
昨天第五节 `w(my_func)` 里你干的就是同一件事：把函数当值递。

### ② 先猜再跑

两段的区别只有一个：A 段是**逐个 `await`**，B 段是 `gather`。
`blocked_work` 里的 `time.sleep` 在两段落里**完全一样**。

问：A 段会比 B 段快、慢、还是差不多？

先把这个想清楚再跑：**A 段是 `await to_thread(...)` 三行排着写**，
用第二节的结论判断它。

```bash
uv run python code/python/07_to_thread.py
```

跑完 `cd ../..`。

### ③ 真实输出

```
=== blocked_work 是个普通函数，里面是 time.sleep，一个字都没改 ===
逐个 await to_thread     : 0.61s
gather 三个 to_thread    : 0.20s
```

### ④ 对上

**A 段 0.61s：`to_thread` 救不了排着等的写法。**
`await asyncio.to_thread(...)` 里的 `await` 还是那个意思——**当场等它完成再回来**。
等完一个才登记下一个，所以三个 0.2 还是摞起来。
这跟第二节 A 段是同一个错，只不过慢的原因从「不交出控制权」换成了「老老实实等」。

**B 段 0.20s：三行 `to_thread` 交给 `gather`，三个线程同时睡。**
`gather` 先把三个都登记，然后才一起等——于是 0.2 秒里发生了三件事。

**`blocked_work` 里那个 `time.sleep` 从头到尾没被改过一个字。**
它还是阻塞的，只不过它阻塞的是**别人的线程**，你的循环没被按住。

> **两条出路，今天你已经全见了：**
> 1. 能改的：把 `time.sleep` 换成 `await asyncio.sleep`（第六节 A 段）。
> 2. 改不了的：`await asyncio.to_thread(那个函数, 参数...)`，**并且要和 `gather` 一起用才有并发**。
>
> 光用第 2 条而忘了 `gather`，你会得到 0.61s，然后怀疑 `to_thread` 是假的。

## 八、`asyncio.run` 只能出现在最外层

### ① 建文件

这个文件是今天**唯一会红着退出**的实验，跟 Day 2 第六节那次一样，故意造一个错。

```bash
cd stage1/day003_async
cat > code/python/08_nested_run.py <<'PY'
import asyncio


async def inner():
    return 1


async def outer():
    print("outer 已经在一个跑着的循环里了")
    result = await asyncio.run(inner())
    print("这一行永远到不了 :", result)


asyncio.run(outer())
PY
```

它做的就是你今天第一节就会的动作，只多了一件事：**在 `outer` 里面又调了一次 `asyncio.run`**。

### ② 先猜再跑

先猜：它会印出「这一行永远到不了」吗？报错还是正常退出？

```bash

```

跑完 `cd ../..`。

### ③ 真实输出

```
outer 已经在一个跑着的循环里了
Traceback (most recent call last):
  File ".../code/python/08_nested_run.py", line 14, in <module>
    asyncio.run(outer())
    ~~~~~~~~~~~^^^^^^^^^
  ...（中间三帧是标准库内部的调用链，你今天不用读）...
  File ".../code/python/08_nested_run.py", line 10, in outer
    result = await asyncio.run(inner())
                   ~~~~~~~~~~~^^^^^^^^^
  File ".../asyncio/runners.py", line 192, in run
    raise RuntimeError(
        "asyncio.run() cannot be called from a running event loop")
RuntimeError: asyncio.run() cannot be called from a running event loop
<sys>:0: RuntimeWarning: coroutine 'inner' was never awaited
退出码=1
```

### ④ 对上

**先看你唯一需要记住的那一行**：

```
RuntimeError: asyncio.run() cannot be called from a running event loop
```

读作「`asyncio.run()` 不能从一个正在跑的循环里被调用」。
它的职责（第一节）是**新建一个循环**；可现在**已经有一个在跑了**，没有「新建」的余地。

**`line 14` 和 `line 10` 谁是谁**：14 是文件最后那句 `asyncio.run(outer())`（第一次、合法的那次），
10 是 `outer` 里面那句嵌套的 `asyncio.run(inner())`（第二次、闯祸的那次）。
traceback 从下往上读：**最后一行是结论，上面是从外到里每一层在干哪一行**。

**「这一行永远到不了」没印**——因为 `asyncio.run` 在 `await` 之前就抛了，
`result` 压根没被赋值。

**最后那行警告是 `inner()` 的票**：
`inner()` 造出来了，但 `asyncio.run` 死在前面，所以它跟第一节一样「never awaited」。

**这一条对你真正的影响**（今天不下结论，只留一句）：
`asyncio.run` 是**脚本**该用的东西——一个文件跑一次，最外层一次。
以后你写任何「已经有一个循环在替你跑」的东西，里面**只能 `await`，不能 `run`**。

- **第 2 块**：**改一个已有的键 = 覆盖；写一个从没有的键 = 新增**。`user` 从三项变成四项，没报任何错。
  JS 里 `obj.color = "red"` 就是这个行为，一模一样。
- **第 3 块**：`for it in items` 每轮拿到的是**整条 dict**，所以 `it["name"]` 的意思是「这一条的 name」。
  明天每个端点里那个 `for`，全部含义就是这一行。
- **第 4 块**：`find(99)` 把整个 list 走完了都没 `return`，落到最后那句 `return None`。
  **「找不到」在这套写法里是一个正常的返回值，不是错误。** 记住这句，明天第七节要用。
- **第 5 块**：`bad["price"]` **当场崩**，`KeyError: 'price'`。这是 JS 和 Python 今天最要紧的一条差别：

| 键不存在时 | JS | Python |
|---|---|---|
| 读 | `obj.price` → `undefined`，程序继续跑 | `obj["price"]` → **`KeyError`，整个程序停在这行** |
| 写 | `obj.x = 1` 多出一项 | `obj["x"] = 1` 多出一项，一样 |

明天你会在**一个 HTTP 请求里**再撞一次这个 `KeyError`，而且它以 **500** 的形式出现。
那时候你能认出 `~~~^^^^^^^^^` 底下那行 `KeyError: 'price'` 说的就是今天第 5 块，这块地基就算补到了。

**取值只有 `d["键"]` 这一种写法。** 想写 `d.price`（点号）是不行的——dict 上点号取不到东西：

```
AttributeError: 'dict' object has no attribute 'price'
```

点号是昨天 `@dataclass` 那种**实例**才有的，dict 没有。
