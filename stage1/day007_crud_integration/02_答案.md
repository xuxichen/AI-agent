## 第 1 题 · 数据去哪了

```
版本 A：POST → 201 完整资源体，随后 GET /notes → 200 []
版本 B：POST → 201 完整资源体，随后 GET /notes → 200 [那条数据]
```

**版本 A 里每一步都是对的**：

1. `dep_store()` 新建了一个 `{}`，交给处理函数
2. 处理函数把 `Note` 写进去了 —— 写成功了，那个字典里真的有这条数据
3. 函数 `return note`，`response_model=NoteOut` 正常过滤，FastAPI 序列化出 201 和完整响应体
4. 请求结束，Day 6 学的 exit stack 关闭，`dep_store` 的生成器退出
5. 那个 `{}` 没有任何别的引用了 → 被垃圾回收

**第 2 步写入的对象和第 5 步被回收的对象是同一个。** 数据不是「丢了」，是**从来没被放到能活过请求的地方**。

这就是为什么它是本周最阴险的 bug：
错误发生在「你以为已经完成的事」上，而且**全链路 2xx**。
没有异常、没有日志、没有 500。你只能靠「POST 之后 GET 一下」这个动作发现它。

**推广成一条纪律**：任何需要跨请求存活的状态（缓存、计数器、连接池、会话表），
都必须挂在**生命周期比一次请求长**的对象上——模块级变量、`app.state`、或者外部存储。
`yield` 依赖交出的是**访问权**，不是**所有权**。

## 第 2 题 · 参考实现

```python
"""Day 7 · 笔记 CRUD 服务（Week 1 整合）"""
import itertools

from fastapi import APIRouter, Depends, FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field


# ---- 三个模型：就是 Day 5 那三个，一字未改 ----
class NoteIn(BaseModel):
    title: str = Field(min_length=1, max_length=50)
    tags: list[str] = []


class Note(BaseModel):
    id: int
    title: str
    tags: list[str] = []
    owner: str = "secret-owner"


class NoteOut(BaseModel):
    id: int
    title: str
    tags: list[str] = []


# ---- 存储：模块级，所以活得比一次请求长 ----
store: dict[int, Note] = {}
_ids = itertools.count(1)


def dep_store():
    """交出模块级 store。依赖只提供访问权，不负责创建。"""
    yield store


def get_or_404(note_id: int, s: dict[int, Note]) -> Note:
    if note_id not in s:
        raise HTTPException(status_code=404, detail=f"note {note_id} not found")
    return s[note_id]


router = APIRouter(prefix="/notes", tags=["notes"])


@router.post("", status_code=201, response_model=NoteOut)
def create_note(payload: NoteIn, s=Depends(dep_store)):
    note = Note(id=next(_ids), **payload.model_dump())
    s[note.id] = note
    return note


@router.get("", response_model=list[NoteOut])
def list_notes(s=Depends(dep_store)):
    return list(s.values())


@router.get("/{note_id}", response_model=NoteOut)
def read_note(note_id: int, s=Depends(dep_store)):
    return get_or_404(note_id, s)


@router.put("/{note_id}", response_model=NoteOut)
def update_note(note_id: int, payload: NoteIn, s=Depends(dep_store)):
    old = get_or_404(note_id, s)
    s[note_id] = Note(id=note_id, owner=old.owner, **payload.model_dump())
    return s[note_id]


@router.delete("/{note_id}", status_code=204)
def delete_note(note_id: int, s=Depends(dep_store)):
    get_or_404(note_id, s)
    del s[note_id]


app = FastAPI()
app.include_router(router)


if __name__ == "__main__":
    client = TestClient(app)

    def show(method: str, path: str, **kw):
        r = client.request(method, path, **kw)
        print(f"{method:6} {path:13} → {r.status_code} {r.text if r.content else '（空响应体）'}")

    show("GET", "/notes")
    show("POST", "/notes", json={"title": "a"})
    show("GET", "/notes")
    show("GET", "/notes/1")
    show("PUT", "/notes/1", json={"title": "b", "tags": ["x"]})
    show("GET", "/notes/99")
    show("PUT", "/notes/99", json={"title": "z"})
    show("DELETE", "/notes/1")
    show("GET", "/notes/1")
    show("DELETE", "/notes/1")
    show("POST", "/notes", json={"title": ""})
    show("GET", "/notes/abc")
    print("\nopenapi paths:", sorted(app.openapi()["paths"]))
```

四处值得注意的写法：

1. **`get_or_404` 抽出来了**：GET/PUT/DELETE 三个端点的「找不到就 404」完全一样，
   写三遍就是三处将来会不一致的地方。
2. **`Note(id=note_id, owner=old.owner, **payload.model_dump())`**：
   PUT 时 `owner` 从旧记录里拿，不从请求体拿——`NoteIn` 里压根没有 `owner`，
   所以用户改不了归属。这是 Day 5 三模型分工的实际收益。
3. **`itertools.count(1)`**：不用 `next_id = next_id + 1`（实测
   `UnboundLocalError: cannot access local variable 'next_id' where it is not associated with a value`）。
   也不用 `counter = [0]` 那种绕法——`count` 是标准库为这件事准备的。
4. **集合端点是 `""` 不是 `"/"`**，原因见第 4 题。

## 第 3 题 · 状态码盘点

| 场景 | 码 | `detail` 形状 | 为什么 |
|---|---|---|---|
| `GET /notes` 空库 | **200** `[]` | 无 | 集合这个资源存在，只是没有成员。404 是「URL 没有对应资源」 |
| `POST` 合法 | **201** | 无 | 创建了新资源，必须带上服务端生成的 `id` |
| `POST` 空 title | **422** | **列表** | Pydantic 校验失败，`string_too_short` @ `["body","title"]` |
| `GET /notes/abc` | **422** | **列表** | 路径**匹配上了**，是 `abc → int` 转换失败，`int_parsing` @ `["path","note_id"]` |
| `GET /notes/99` | **404** | **字符串** | 路径和类型都对，资源不存在 |
| `DELETE` 存在 | **204** 空体 | 无 | 删掉了，没有内容需要返回 |
| `DELETE` 已删 | **404** | **字符串** | 今天的契约是「找不到就 404」，见第 5 题 |
| `POST /notes/` | **201** 但先 **307** | —— | FastAPI 的 `redirect_slashes`，多一次网络往返 |

**`GET /notes/abc` 是 422 而不是 404，这一条最能检验你懂不懂 Day 4。**
路由 `/notes/{note_id}` 匹配成功了（它匹配任何一段路径），
失败发生在**参数转换阶段**——`note_id: int` 收到 `"abc"`。
如果你把 `note_id` 的类型注解去掉，它就会变成字符串 `"abc"` 收下来，
然后你的 `if note_id not in store` 判断成立，返回 404。**同一份代码，注解写与不写，错误码从 422 变 404。**

`POST /notes/` 那个 307 值得单独记一下：
`r.history` 是 `[(307, 'http://testserver/notes')]`。请求最终成功了，
所以你的测试会绿——但生产环境里每次调用都多一次往返，而**测试发现不了**。

## 第 4 题 · 那个致命的斜杠

**1. 405 和 404 的区别是什么？看 `detail` 的形状能判断吗？**

- **404**：这个 URL **压根没有注册**过任何方法
- **405**：URL **注册了**，但你用的方法没注册（`/notes` 只有 `get`，你发了 `post`）

`detail` 的形状**判断不了这两者的区别**——两个都是字符串：

```
404 → {"detail":"Not Found"}
405 → {"detail":"Method Not Allowed"}
```

形状只能区分「字符串 = 框架/你抛的 HTTPException」和「列表 = Pydantic 校验失败」这一层。
再往里就得**读 `detail` 的文字**。所以三者的分流是：

| `detail` | 含义 | 该查什么 |
|---|---|---|
| **列表** | 参数不合法（422） | 查传的值和类型注解 |
| **字符串 `"Not Found"`** | 路径没注册（404） | 查拼写、prefix、注册顺序 |
| **字符串 `"Method Not Allowed"`** | 路径注册了、方法没有（405） | 查这个路径上到底挂了哪些方法 |

405 其实是**好消息**：它说明你的 URL 拼对了，只是方法配错了。比 404 更容易修。

**2. 为什么这种写法在文档阶段就能被前端同事发现？**

因为 `openapi.json` 是**注册表**（Day 4 的结论）。集合端点写成 `"/"` 之后，
文档里明明白白列着三条路径：

```
/notes            → 只有 get
/notes/           → 只有 post
/notes/{note_id}  → delete, get, put
```

前端同事照着文档生成客户端代码，`POST /notes` 直接 405。
**错误在联调第一天就暴露了，而不是上线之后。** 这是 OpenAPI 自动生成的真实价值——
不是「有文档很爽」，而是**文档不可能和实现不一致**，因为它们出自同一份注册表。

反过来，如果你手写文档，`"/"` 这种错误很可能一直藏着。

### 对照实验：为什么五个检查全绿却还是错的

把 POST 和 GET 的集合端点**都**改成 `"/"`，`check.py` 只报 1 个 ✗：

```
✓ 1. 完整用户旅程     ✓ 2. DELETE     ✓ 3. store 存活     ✓ 4. 422     ✓ 5. 模型边界
✗ 6. 路由组织的形状 —— 应有 /notes 和 /notes/{note_id}，实际 ['/notes/', '/notes/{note_id}']
```

**五个发真请求的检查全部通过**，因为 `POST /notes` 拿到 307 之后，
`TestClient`（底层是 httpx）**自动跟着重定向**发到 `/notes/`，
请求最终成功、响应体正确、断言通过。测试看不到中间那次 307。

而这个服务**确实是错的**：它的 URL 是 `/notes/` 不是 `/notes`，
每个真实客户端每次调用都多一次网络往返。

**这对 check.py 设计的启示（今天第二重要的收获）：**

> **发请求的测试只能验「能不能跑通」，验不了「路径对不对」。**
> 客户端库的容错行为（跟随重定向、自动重试、默认 header）会**主动掩盖**服务端的设计错误。

所以一套验收需要两类断言：

| 类型 | 验什么 | 例子 |
|---|---|---|
| **动态**（发请求） | 行为对不对 | 第 1–5 项：状态码、响应体、数据存活 |
| **静态**（读注册表/源码） | 结构对不对 | 第 6 项：`app.openapi()["paths"]`、AST 里的装饰器 |

Day 4 的第 6 项（查路由注册顺序的行号）、Day 6 的第 5、6 项（查中间件定义顺序、查 `finally`）
都是同一类。**它们不是多余的重复检查，而是唯一能看到「客户端容错掩盖了什么」的那双眼睛。**

具体到今天：第 6 项读的是 `app.openapi()`——**注册表**。
注册表不撒谎，因为它就是 FastAPI 内部那张表的直接导出（Day 4）。
而 `TestClient` 的响应经过了 httpx 的一层加工，加工过程会把真相磨平。

**一条可以带走的纪律**：写验收时，凡是「客户端库会自动兜底」的地方
（重定向、重试、编码转换、默认值填充），都要额外加一条**直接检查声明/注册表**的断言。

## 第 5 题 · 费曼任务参考措辞

> 1. 不违反。**幂等约束的是服务端状态，不是响应码。**
> 2. 删一次之后那条记录没了；再删十次，记录**还是**没了——状态收敛到同一个结果，
>    所以 DELETE 是幂等的。
> 3. 「重复请求要不要返回同一个码」是**另一个独立的决定**，404 和 204 两种都有人用，
>    规范没有强制。
> 4. 选型看客户端：**面向重试的**（消息队列消费者、K8s 控制器）选 204，
>    因为它们的逻辑是「不成功就一直重发」，404 会让它们把已经完成的删除当成失败无限重试；
>    **普通 CRUD** 选 404，和 GET/PUT 保持一致，代码里只有一条错误处理路径。

反问「那 PUT 一个不存在的 id 该 404 还是该创建」的答案：

**取决于你把 PUT 定义成什么语义**，两种都合法：

- 「整体替换这个已存在的资源」→ 不存在就 **404**（今天的契约）
- 「把这个 id 的状态设成这个样子」（upsert）→ 不存在就 **201 创建**

关键在于**必须写进文档**，因为客户端的重试逻辑完全依赖这个约定。
如果客户端以为是 upsert 而服务端返回 404，它的重试会一直失败；
如果客户端以为会 404 而服务端悄悄创建了资源，就会出现一堆没人认领的孤儿记录。

**这就是「幂等」这个词在实际工作里的样子：不是背规范，是把约定写下来并守住。**

## 第 6 题 · 测试互相污染

**1. 会造成什么问题？**

具体场景：`test_create_then_list` 先跑，往 `store` 里塞了 1 条；
接着 `test_empty_store_returns_empty_list` 跑，它断言 `GET /notes == []`——
**但它看到了上一条测试留下的数据，红了。**

更坏的情况是**顺序依赖**：单独跑第二个测试是绿的，全量跑就红。
于是你开始怀疑测试框架、怀疑并发、怀疑人生，
而真正的原因只是「上一个测试没清理」。
`pytest -p no:randomly` 能复现、`pytest-randomly` 能掩盖——**掩盖不等于修好**。

**2. 解法**

`check.py` 里那个 `reset()` 就是最小解法：

```python
def reset() -> None:
    mod.store.clear()
```

每项检查开头调一次，让所有检查都从空库开始。
在生产测试里，这件事用 **pytest fixture** 做，而不是靠每个测试函数记得调用：

```python
@pytest.fixture(autouse=True)
def clean_store():
    store.clear()
    yield
    store.clear()      # 前后都清，防止测试自己的残留影响下一个
```

`autouse=True` 意味着**不需要每个测试去声明它**——防线要放在不容易忘的地方
（Day 5 的同一条纪律）。

**3. 多进程下还成立吗？**

**不成立。** `uvicorn --workers 4` 起的是 4 个**独立进程**，
每个进程 import 一遍 `crud_api.py`，于是有**4 份互不相干的 `store`**。

后果比测试污染严重得多：

```
POST /notes  → 落到 worker A → A 的 store 里有了 id=1
GET  /notes  → 落到 worker B → B 的 store 是空的 → 200 []
GET  /notes  → 又落到 worker A → 200 [id=1]
```

**同一个客户端连续三次请求，看到的数据在闪烁。** 状态码全是 2xx，日志干干净净。

所以内存字典**只能用于开发和单进程部署**。这是今天这个模板的**已知边界**，
不是缺陷——但你要在代码里写下来：

```python
# 开发用内存存储。多 worker / 重启 / 多实例部署都必须换成 Redis 或数据库，
# 否则每个进程各存一份，客户端会看到数据闪烁。
store: dict[int, Note] = {}
```

**换成真数据库时，改动范围只有 `store` 和 `dep_store`**——
五个端点的处理函数一个字都不用动。这就是把存储藏在依赖后面的收益，
也是 Day 6「依赖注入」在真实项目里的用途。
