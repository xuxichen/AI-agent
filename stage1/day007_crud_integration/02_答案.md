## 第 1 题 · 参考实现（整份，可直接覆盖）

```bash
cd stage1/day007_crud_integration
cat > code/python/hw01_todos_fixed.py <<'PY'
import json

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI()


class TodoIn(BaseModel):
    title: str = Field(min_length=2)
    done: bool = False


class TodoOut(BaseModel):
    id: int
    title: str
    done: bool


DB_FILE = "todos.json"


def save():
    with open(DB_FILE, "w") as f:
        json.dump(todos, f, ensure_ascii=False, indent=2)


try:
    with open(DB_FILE) as f:
        todos = json.load(f)
except FileNotFoundError:
    todos = [
        {"id": 1, "title": "写作业", "done": False},
        {"id": 2, "title": "买牛奶", "done": True},
    ]
    save()


def find_biggest():
    biggest = 0
    for it in todos:
        if it["id"] > biggest:
            biggest = it["id"]
    return biggest


@app.get("/todos")
def list_todos():
    return todos


@app.get("/todos/{tid}")
def read_todo(tid: int):
    for it in todos:
        if it["id"] == tid:
            return it
    raise HTTPException(status_code=404, detail="没有这个 id")


@app.put("/todos/{tid}", response_model=TodoOut)
def update_todo(tid: int, payload: TodoIn):
    for it in todos:
        if it["id"] == tid:
            it["title"] = payload.title
            it["done"] = payload.done
            save()
            return it
    raise HTTPException(status_code=404, detail="没有这个 id")


@app.delete("/todos/{tid}", status_code=204)
def delete_todo(tid: int):
    n = 0
    for it in todos:
        if it["id"] == tid:
            todos.pop(n)
            save()
            return None
        n = n + 1
    raise HTTPException(status_code=404, detail="没有这个 id")


@app.post("/todos", response_model=TodoOut, status_code=201)
def create_todo(payload: TodoIn):
    data = payload.model_dump()
    data["id"] = find_biggest() + 1
    todos.append(data)
    save()
    return data
PY
```

和你自己写的文件 diff 一下，重点看四处：

1. `save()` 和自举 `try` 的**位置**（在模型之后、端点之前；`save` 定义在 `try` 之前，教案三 ③ 第 2 问）。
2. 三个写端点（PUT / DELETE / POST）里**各有一行 `save()`**，都在改动生效之后、`return` 之前。
3. `data["id"] = find_biggest() + 1`——不是 `len(todos) + 1`。
4. DELETE 装饰器上有 `status_code=204`，**没有** `response_model`；函数体结尾是 `raise 404`，不是 `return None`。

## 第 2 题 · 4 处问题

| # | 位置 | 现象（真跑验证过） | 修法 | 教案 |
|---|---|---|---|---|
| 1 | `@app.delete("/todos/{tid}")` 装饰器：**漏了 `status_code=204`** | DELETE 成功回 **200 + body `null`**（该是空 body 的 204） | 装饰器补 `status_code=204` | 二 ②、⑥ |
| 2 | `delete_todo` 结尾是 **`return None`**，不是 `raise HTTPException(404, ...)` | 重复 DELETE 也回 200 + null（该是 404——契约 A） | 循环外改成 `raise` | 二 ⑦ |
| 3 | `create_todo` 里 `data["id"] = len(todos) + 1` | 删过中间 id 后 POST，新 id 撞车：GET /todos/2 永远返回旧的那条，新的成死数据 | 换成 `find_biggest() + 1` | 二 ⑧ |
| 4 | **整个文件缺落盘**：没有 `import json`、没有 `DB_FILE`/`save()`/自举 `try`，端点里也没有 `save()` 调用 | POST/PUT/DELETE 当时都成功，**重启后全部还原成种子两条** | 教案三 ③ ⑤ 的整套搬过来 | 三 ③、⑤ |

验证点真跑输出（:8792）：

```
$ curl -s -X DELETE /todos/1
null [200]
$ curl -s -X DELETE /todos/1
null [200]
$ curl -s -X POST -H content-type:application/json -d {"title":"买菜"} /todos
{"id":2,"title":"买菜","done":false} [201]
$ curl -s /todos
[{"id":2,"title":"买牛奶","done":true},{"title":"买菜","done":false,"id":2}] [200]
$ curl -s /todos/2
{"id":2,"title":"买牛奶","done":true} [200]
```

（重启后）

```
$ curl -s /todos
[{"id":1,"title":"写作业","done":false},{"id":2,"title":"买牛奶","done":true}] [200]
```

逐行对上表看：

- 第一行和第二行**都是 `null [200]`**——第 1 处（该 204）和第 2 处（该 404）同时在 DELETE 上现形。
  `null` 是 `return None` 被序列化的结果（Day 6 那个 `/strict` 讲过：200 + None → null）。
- 第三行：删掉 id 1 后 `len` = 1，POST 的新 id = 2——**撞上还活着的买牛奶**。
- 第四行：列表里两条 id=2；第五行 `GET /todos/2` 返回**先匹配到的买牛奶**，
  新 POST 的买菜从此 GET/PUT/DELETE 都够不着（教案二 ⑧ 的死数据，一字不差地重演）。
- 重启后回到种子两条——**买菜没了**，因为整个文件没有任何落盘代码（第 4 处）。

判分提醒：第 2 处和第 1 处容易被人当成同一个问题——不是。第 1 处是「成功时回什么码」，
第 2 处是「失败时动不动手」；删掉第 1 处（补 204）后 DELETE 成功回 204 了，重复 DELETE 依然
是 `null [200]`，直到你修第 2 处。两处都要改。

## 第 3 题 · 反查表答案

| # | 现象 | 哪天哪节 | 一句话机制 |
|---|---|---|---|
| 1 | `/items/abc` → 422，`loc` 是 `["path","item_id"]` | Day 4 第二节 ④ | 路径参数的类型校验发生在**进函数之前**；422 的 body 是框架默认的 `detail` 列表，没人接管它（Day 6 故意的） |
| 2 | 少必填字段 → 422 `missing` | Day 5 第二节 | `ItemIn` 的字段没默认值就是必填；`input` 是**整个 body**，因为模型还没建出来 |
| 3 | `/items/99` → `{"code":404,"msg":"没有这个 id"}` | Day 6 第二、四节 | `raise HTTPException(404)` 把「没找到」从 500 修成 404；`on_http` 把响应体改成你的形状。**洞**从 Day 4 第七节（200 说谎）开始 |
| 4 | 任意 2xx/4xx 响应都有 `x-process-time` | Day 6 第六节 | 中间件后半段（`call_next` 之后）对每个**正常完成**的请求都执行；404/422 不算崩，所以也加得上 |
| 5 | `?size=99` → 400 | Day 6 第七节 ④ + 第四节 | 分页是 `Depends` 依赖函数；依赖里 `raise HTTPException(400)`，形状照旧走 `on_http` |
| 6 | POST 成功，重启后没了 | Day 4 第八节 + 今天三 ① | 数据存在**进程的 list** 里；进程一死，list 随进程没。落盘前这是必然，不是 bug |
| 7 | POST 成功，落盘后重启还在 | 今天三 ⑥ | 启动时 `json.load` 把文件读回 `items`；写操作后 `save()` 同步文件。**数据在进程外** |
| 8 | DELETE 第一次 204，第二次 404 | 今天二 ⑦ | 幂等约束的是**状态**（删十次还是没这条），不是响应码；契约 A：找不到就 404，和 GET/PUT 同一条错误路径 |
| 9 | `chmod 444` 后 POST → 500，终端 `[崩了]` + `[兜底]` | 今天三 ⑧（保险丝是 Day 6 四、六节装的） | `save()` 写不进 → `PermissionError` 冒到中间件 → `[崩了]` → 原样 `raise` → `[兜底]` 变成 `{"code":500,...}`。500 = 服务器自己的错（磁盘/权限），不是请求的错 |
| 10 | `POST /items/1` → 405，body 是字符串 | Day 4 第四节 | 路径 `/items/{item_id}` 在、方法 POST 没注册。**读 body 分流**：字符串 detail → 路径/方法层；列表 → 校验层；你的 code/msg → 业务层 |

最容易混的三格，单独说：

- **第 4 格和第 9 格是一对**：第 4 格是「正常请求，中间件后半段一定走」；第 9 格是「崩掉的请求，
  后半段不走、`[崩了]` 替它喊」。Day 6 第六节那句「崩掉的请求只过一半」就是这两格的边界。
- **第 6 格和第 7 格是同一个 POST**，差别只在有没有落盘代码——所以「重启就恢复原样」的怪问题，
  第一怀疑就是没落盘（今天三 ⑧ 的口诀）。
- **第 8 格和第 2 格（第 2 题的）是同一件事的两个方向**：契约 A 下重复 DELETE 是 404；
  把「找不到也 204」写成代码（不 raise），重复 DELETE 就变 200——404 恰恰是「幂等成立」的证据，
  不是幂等失败。
