## 第 1 题 · 先预测：数据去哪了

**做什么**：**不要运行**。下面两个版本，各自跑「POST 一条 → GET 列表」，
预测第二次的响应。

```python
# 版本 A
def dep_store():
    yield {}

# 版本 B
store: dict[int, Note] = {}

def dep_store():
    yield store
```

两版的处理函数都是 `s[n.id] = n; return n`，都声明了 `status_code=201`。

```
版本 A：POST 返回 ___，随后 GET /notes 返回 ___
版本 B：POST 返回 ___，随后 GET /notes 返回 ___
```

**验收结果**（本机实测）：

```
版本 A：POST → 201 {"id":1,"title":"t","tags":[]}，随后 GET /notes → 200 []
版本 B：POST → 201 {"id":1,"title":"t","tags":[]}，随后 GET /notes → 200 [{"id":1,"title":"t","tags":[]}]
```

**过关标准**：你预测对了 A 的 `200 []`，**并且能说出为什么 POST 是成功的**。

关键是这句：版本 A 里数据**确实被写进去了**，写进了依赖当场新建的那个 `{}`，
处理函数正常返回、`response_model` 正常过滤、状态码 201 一切正常。
只是那个字典**随请求结束被回收**了——Day 6 学过，`yield` 依赖活到 exit stack 关闭为止。

**这是本周最值得记住的一类 bug：全程 2xx，没有任何报错可查。**

## 第 2 题 · 主产物：`crud_api.py`

**做什么**：在 `stage1/day007_crud_integration/` 下新建 `crud_api.py`，满足这份契约。

**三个模型**（就是你 Day 5 写的那三个，**一字不改抄过来**——这本身就是今天的结论之一：换存储不动模型）：

| 模型 | 字段 |
|---|---|
| `NoteIn` | `title: str = Field(min_length=1, max_length=50)`、`tags: list[str] = []`，**不得有 `id`** |
| `Note` | `id: int`、`title: str`、`tags: list[str] = []`、`owner: str = "secret-owner"` |
| `NoteOut` | `id: int`、`title: str`、`tags: list[str] = []`，**不得有 `owner`** |

**存储与依赖**：

- 模块级 `store: dict[int, Note] = {}`（**必须叫 `store`**，`check.py` 要清空它）
- 模块级计数器，写法随你（`itertools.count(1)` / `counter = [0]` / `global`），
  但**不要**在函数里写 `next_id = next_id + 1`
- `dep_store()`：`yield` 依赖，交出 `store`

**路由**：`router = APIRouter(prefix="/notes", tags=["notes"])`，然后 `app.include_router(router)`

| 方法 | 路径 | 状态码 | 声明 | 找不到时 |
|---|---|---|---|---|
| POST | `""` | `201` | `response_model=NoteOut` | —— |
| GET | `""` | 200 | `response_model=list[NoteOut]` | 空库返回 `[]` |
| GET | `"/{note_id}"` | 200 | `response_model=NoteOut` | `404` `{"detail": f"note {note_id} not found"}` |
| PUT | `"/{note_id}"` | 200 | `response_model=NoteOut` | 同上 `404` |
| DELETE | `"/{note_id}"` | `204` | **不写** `response_model` | 同上 `404` |

末尾 `if __name__ == "__main__":` 用 `TestClient` 跑一遍完整旅程，每行打印
`方法 路径 → 状态码 响应体`。

**验收结果**：

```bash

uv run python stage1/day007_crud_integration/check.py
```

旅程必须是这个形状（本机实测，`id` 从 1 开始）：

```
GET    /notes      → 200 []
POST   /notes      → 201 {"id":1,"title":"a","tags":[]}
GET    /notes      → 200 [{"id":1,"title":"a","tags":[]}]
GET    /notes/1    → 200 {"id":1,"title":"a","tags":[]}
PUT    /notes/1    → 200 {"id":1,"title":"b","tags":["x"]}
GET    /notes/99   → 404 {"detail":"note 99 not found"}
PUT    /notes/99   → 404 {"detail":"note 99 not found"}
DELETE /notes/1    → 204 （空响应体）
GET    /notes/1    → 404 {"detail":"note 1 not found"}
DELETE /notes/1    → 404 {"detail":"note 1 not found"}
```

`check.py` 6 项全部 ✓，最后一行 `Day 7 过关：6/6 项自动检查通过，2 项需你自批`。

**如果你看到的不是这样**：

| 症状 | 原因 |
|---|---|
| 第 1 项红：POST 不是 201 | `status_code=201` 漏写了（默认是 200） |
| 第 2 项红：DELETE 不是 204，或响应体不空 | `status_code=204` 漏写；或你 `return` 了东西 |
| 第 2 项红：重复 DELETE 是 204 而不是 404 | 你没写「找不到就 404」那个判断。这是另一种设计选择，见第 5 题 |
| 第 1、2、3 项**一起红** | **store 建在依赖函数里了**，就是第 1 题的版本 A。第 2 项报的是「DELETE 应为 204，实际 404」，别被它带偏去查 `status_code` |
| 第 4 项红：`/notes/abc` 是 404 而不是 422 | 路径参数没标 `int`，`note_id` 被当成字符串了 |
| 第 5 项红：响应里有 `owner` | `response_model=NoteOut` 漏写了 |
| **6 项全红**，第 1 项说 `实际 405` | 集合端点写了 `"/"` 而不是 `""`（第 4 题） |
| 只有第 6 项红 | 集合端点**两个都**写了 `"/"`——比上面那种更隐蔽，第 4 题的对照实验 |
| import 就炸：`AssertionError: Status code 204 must not have a response body` | DELETE 端点声明了 `response_model` |

**验收结果**（本机实测）：

| 场景 | 码 | `detail` 的形状 |
|---|---|---|
| `GET /notes`，空库 | **200** `[]` | 无 detail |
| `POST /notes` 合法 | **201** | 无 detail |
| `POST` 空 title | **422** | **列表**（`string_too_short` @ `["body","title"]`） |
| `GET /notes/abc` | **422** | **列表**（`int_parsing` @ `["path","note_id"]`） |
| `GET /notes/99` | **404** | **字符串** |
| `DELETE` 存在 | **204** 空体 | 无 detail |
| `DELETE` 已删 | **404** | **字符串** |
| `POST /notes/` | **201**，但先 **307** 重定向到 `/notes` | —— |

**过关标准**：8 行至少对 6 行，且这两条必须对：

1. **空库是 `200 []` 不是 404** —— 集合存在，只是没成员。404 是「这个 URL 没有对应资源」
2. **422 的 `detail` 是列表，404 的是字符串** —— Day 4 的秒判依据，今天你亲手验了四次

最后一行那个 307 值得看一眼：`r.history` 是 `[(307, 'http://testserver/notes')]`。
请求成功了，但**多了一次网络往返**。

## 第 5 题 · 费曼任务：DELETE 幂等吗

**做什么**：向同事解释——**「你重复 DELETE 同一条记录返回 404，这违反 REST 的幂等性吗？」
不超过 4 句。**

```
1.
2.
3.
4.
```

**验收结果**——对照这 4 条：

1. 说清**幂等约束的是服务端状态，不是响应码**
2. 论证状态确实收敛：删一次记录没了，再删十次**还是**没了
3. 承认「响应码是否也该幂等」是**另一个独立决定**，404 和 204 两种都合理
4. 给出选型依据：**面向重试的客户端**（消息队列消费者、K8s 控制器）选 204，
   普通 CRUD 选 404（和 GET/PUT 行为一致，只有一条错误处理路径）

**自测**：同事反问「那 PUT 呢？PUT 一个不存在的 id 该 404 还是该创建」，你要能答：
**取决于 PUT 的语义定义**。如果 PUT 是「整体替换这个资源」，不存在就 404（今天的契约）；
如果是 upsert 语义，就该 201 创建。两种都有人用，**但必须写进文档**，
因为客户端的重试逻辑完全依赖这个约定。
