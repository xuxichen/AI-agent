## 今日问题

你要写一个能跑通的笔记 CRUD 服务。它会**全部返回 2xx**，一个报错都没有——

```
POST /notes   → 201 {"id": 1, "title": "t", "tags": []}
GET  /notes   → 200 []
```

数据没了。**没有任何异常、没有任何日志、没有任何红色输出。** 为什么？

第二个问题：你按 REST 规范写「DELETE 是幂等的，重复删应该返回 204」，
但实测重复 DELETE 返回 **404**。到底谁错了？

## 学习内容

### 3.1 五种码，两种响应体形状

全部本机实测（`TestClient`，离线）：

| 请求 | 码 | 响应体 | `detail` 的形状 |
|---|---|---|---|
| `POST /notes` 合法 | **201** | `{"id":1,"title":"a","tags":[]}` | —— |
| `DELETE /notes/1` | **204** | `b''`（**空的，连 `{}` 都没有**） | —— |
| `GET /notes` 空库 | **200** | `[]`（**空列表，不是 404**） | —— |
| `GET /notes/99` | **404** | `{"detail":"note 99 not found"}` | **字符串** |
| `POST /notes` 空 title | **422** | `{"detail":[{"type":"string_too_short",...}]}` | **列表** |

**秒判依据（Day 4 学的，今天继续用）**：`detail` 是**字符串** → 框架或你抛的 `HTTPException`；
`detail` 是**列表** → Pydantic 校验失败。看一眼响应体就知道该去查路由还是查数据。

两个容易写错的点：

- **204 不能声明 `response_model`。** 实测 FastAPI 启动即炸：
  `AssertionError: Status code 204 must not have a response body`
- **`r.json()` 在 204 上会抛异常**，因为没有响应体可解析。测试里要用 `r.content == b""`。

### 3.2 DELETE 幂等吗

规范说幂等。你的实现返回 404。矛盾吗？**不矛盾。**

> **幂等约束的是服务端状态，不是响应码。**
> 删一次之后记录没了；再删十次，记录**还是**没了。状态收敛 → 幂等成立。

但**响应码是否也应该幂等**，是另一个决定，两种都合理：

| 选择 | 重复 DELETE 返回 | 谁在用 | 代价 |
|---|---|---|---|
| **A. 找不到就 404** | `404` | 大多数 CRUD 教程、FastAPI 默认写法 | 客户端重试时会看到「失败」，得自己判断 404 也算成功 |
| **B. 找不到也 204** | `204` | 严格 REST、面向重试的基础设施 | 客户端分不清「删掉了」和「本来就不存在」 |

**今天的契约用 A**，因为它和 GET/PUT 的行为一致（都是找不到就 404），代码里只有一种错误处理路径。
但你要知道 B 存在，并且在**给重试型客户端（消息队列消费者、K8s 控制器）写 API 时选 B**。

### 3.3 store 挂在哪里 —— 今天的主菜

这就是开头那个问题的答案。三种写法，**只有一种能存住数据**：

```python
# ✗ 写法一：建在依赖函数里
def dep_store():
    yield {}              # 每个请求一个新字典，请求结束就被丢掉

# ✗ 写法二：建在处理函数里
@router.post("")
def create(p: NoteIn):
    store = {}            # 更糟，连一次请求都跨不过

# ✓ 写法三：模块级，依赖只负责「把它交出去」
store: dict[int, Note] = {}

def dep_store():
    yield store           # 交出去的是同一个对象
```

**为什么写法一的杀伤力最大**：`POST` 会返回 **201 和完整的资源体**，
你在依赖交出的那个字典里确实写进去了，函数正常返回，`response_model` 正常过滤——
**每一步都是对的**。只是那个字典在请求结束时（Day 6 学的 exit stack 关闭）被回收了。

这是 Day 6「依赖生命周期」的直接后果：**依赖的返回值活多久，由依赖自己决定**。
`yield` 出来的东西活到请求结束，不长不短。想要活过请求，就得挂在**比请求更长命的东西**上
（模块、`app.state`、数据库连接池）。

顺带两个实测：

- **同一个 `app` 的两个 `TestClient` 共享 store**：`c3.post(...)` 之后 `c4.get("/notes")` 读得到。
  说明 store 挂在 app/模块上，不挂在客户端上——这直接导致**测试之间互相污染**（第 6 题）。
- **计数器不能在函数里自增**：`next_id = next_id + 1` 实测
  `UnboundLocalError: cannot access local variable 'next_id' where it is not associated with a value`。
  用 `itertools.count(1)`，或者 `counter = [0]` 改 `counter[0]`（Day 2 的作用域坑）。

### 3.4 APIRouter 的 prefix 与那个致命的斜杠

`prefix="/notes"` 之后，集合端点的路径该写 `""` 还是 `"/"`？实测：

| 集合端点写法 | `openapi` 里的 paths | `POST /notes` | `POST /notes/` |
|---|---|---|---|
| POST `""` + GET `""` | `['/notes', '/notes/{note_id}']` | **201** | 201，但**先 307 重定向**到 `/notes` |
| POST `"/"` + GET `""` | `['/notes', '/notes/', '/notes/{note_id}']` | **405** | 201 |
| POST `"/"` + GET `"/"` | `['/notes/', '/notes/{note_id}']` | 201（**靠 307**） | 201 |

第 2 行（两个端点劈到两个 URL）有两处坏：

1. **集合被劈成两个 URL**：`GET` 在 `/notes`，`POST` 在 `/notes/`。文档里三条路径，前端照着调必然踩。
2. **`POST /notes` 返回 405**，`{"detail":"Method Not Allowed"}`——注意 `detail` 是**字符串**，
   所以它是「路径匹配上了、方法不对」，不是 404（路径压根不存在），也不是 422（参数不对）。
   **404 / 405 / 422 三者的分流就是这么读的。**

而 `""` 那一行的尾斜杠请求虽然也成功，但多了一次 **307 往返**
（`history: [(307, 'http://testserver/notes')]`）。生产环境里这是一次额外的网络来回。

**纪律：`prefix` 之后的集合端点写 `""`，单项端点写 `"/{note_id}"`。**

**第 3 行比第 2 行更危险。** 它不报 405，功能全对，你的测试套件会 **5/6 全绿**——
因为 `TestClient` 拿到 307 会**自动跟随重定向**，把真相磨平了。
只有去读 `app.openapi()` 那张注册表，才能看到路径已经变成 `/notes/`。
这是今天第二个主菜，第 4 题会让你亲手复现。

最后一件事：`APIRouter(tags=["notes"])` 里的 tags **只出现在 operation 级别**，
`app.openapi()` 的顶层**根本没有 `tags` 这个键**（实测 `'tags' in spec` → `False`）。
想让 Swagger UI 的分组带上描述，得显式写 `FastAPI(openapi_tags=[{"name": "notes", "description": "..."}])`。

### 3.5 本周回顾：六个坑在 CRUD 里显形的位置

| Day | 那天的坑 | 今天在哪里会再咬你一次 |
|---|---|---|
| 1 | 环境分层：装在哪、谁说了算 | `uv run` 而不是 `python`——不然 import 不到 fastapi |
| 2 | 定义时求值 vs 调用时求值 | `tags: list[str] = []`（Pydantic 替你隔离）；`next_id` 自增的作用域 |
| 3 | 阻塞调用毁掉并发 | 今天全同步没问题；Day 12 起接 LLM 时，一个同步 HTTP 调用就够拖垮整个 worker |
| 4 | 路由注册顺序优先，不是精确优先 | `/notes/{note_id}` 若写在 `/notes/mine` 前面，`mine` 会被当成 `note_id` 去转 int → 422 |
| 5 | `response_model` 是出口过滤器 | `owner` 会不会漏出去；`NoteIn` 里有 `id` 的话用户能覆盖别人的记录 |
| 6 | 依赖的生命周期 | **今天的主菜**：store 放依赖里就存不住数据 |

### 3.6 代码模板（原计划的「整理代码模板」）

```

  GET    ""            200 + response_model=list[XxxOut]
  GET    "/{id}"       200 + response_model=XxxOut，找不到 404

```

## 费曼任务

向同事解释：**「我的 POST 返回 201 而且响应体完全正确，但下一个 GET 拿到空列表，
可能是什么原因？」不超过 4 句。**

必须包含：

1. 数据确实写进去了，只是写进了**一个随请求结束就消失的对象**
2. 说清那个对象为什么消失——依赖 `yield` 出来的东西活到请求结束（Day 6）
3. 给出修法：状态要挂在**比一次请求更长命**的地方
4. 点出这个 bug 的阴险之处：**全程 2xx，没有任何报错可查**

预案：同事反问「那我把 store 做成全局变量，多个 worker 会不会各存一份」——
你要能答：**会**，进程之间不共享内存，所以内存字典只能用于开发和单进程；
真上多 worker 就得换 Redis / 数据库。这是这个模板的**已知边界**，不是缺陷。
