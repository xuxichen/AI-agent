## 二、两个新动词：`PUT`（改）和 `DELETE`（删）

Day 4 你见过它们的 405。今天让它们真正干活。

先记住一个对照，今天整节都靠它：

> `POST /items`——在**列表**里加一条（集合的动作，目标不存在）。
> `PUT /items/2`——**把 2 号整个换掉**（单个资源的动作，目标必须已存在）。
> `DELETE /items/2`——**把 2 号删掉**（单个资源的动作，目标必须已存在）。

PUT 和 DELETE 都是「目标必须已存在」——**目标不在，就是 404**。和 GET /items/99 一个待遇。
这是今天第二节的主线。

### ① 先猜三件事

1. 对一个**不存在的 id** 打 `PUT /items/99` 或 `DELETE /items/99`，会回什么？404？还是 204（DELETE 成功码）？
2. `DELETE /items/2` 打两次——第一次成功删掉之后，第二次打什么？
3. `PUT` 的 body 是不是也要过 `ItemIn` 那套校验（名字至少 2 个字符、价格不能是负数）？

先写下来，后面一条条对。

### ② 在 `app.py` 里加两个函数（终端 A）

`Ctrl+C` 关掉服务，打开 `code/python/app.py`。找到 `read_item` 这个函数
（`GET /items/{item_id}` 那个），在它**结束之后、`list_items` 开始之前**，插进下面两段：

```python
@app.put("/items/{item_id}", response_model=ItemOut)
def update_item(item_id: int, payload: ItemIn):
    for it in items:
        if it["id"] == item_id:
            it["name"] = payload.name
            it["price"] = payload.price
            return it
    raise HTTPException(status_code=404, detail="没有这个 id")


@app.delete("/items/{item_id}", status_code=204)
def delete_item(item_id: int):
    n = 0
    for it in items:
        if it["id"] == item_id:
            items.pop(n)
            return None
        n = n + 1
    raise HTTPException(status_code=404, detail="没有这个 id")
```

逐行读一遍，三个新东西之外全是旧的：

- `@app.put` 和 `@app.delete` 就是 `@app.get` / `@app.post` 的兄弟。**路径参数、body 参数、注解、
  返回 dict 被 `response_model` 过滤……全都一样**，只有动词不同。
- `update_item` 里没有一行新语法：遍历、比 id、改两个键、`return`。找不到就 `raise HTTPException(404, ...)`——
  和 `read_item` 一模一样。**PUT 的成功码不用写**：默认 200。
- `delete_item` 里有一个新词：`items.pop(n)`。读作「把 items 里第 n 个元素弹出来（删掉）」。
  前面那个 `n` 是计数器，`for` 每走一圈 `n = n + 1`——第几个元素 id 对上了，就 `pop` 第几个。
  `pop` 完**列表真的少一个**，这是 DELETE 和 GET/PUT 最大的不同：它在改数据。
- `status_code=204`：DELETE 成功的码。204 的意思是「**成了，但没话说**」——没有响应体，
  所以函数 `return None`（没什么可返回的）。这个码的规矩在 ⑦ 里细讲。
- 找不到怎么办？循环走完没删到 → `raise HTTPException(status_code=404, detail="没有这个 id")`。
  和 GET、PUT 同一句、同一个码。

> **注意第 9 条的坑**：`create_item` 里那句 `data["id"] = len(items) + 1` 先别动——
> ⑧ 会让你亲手看它坏掉的样子，再换掉。

七条四个结局，和你的猜测对一下：

| 打什么 | 状态码 | 原因 |
|---|---|---|
| `PUT /items/1`，body 合法 | **200**，回来整条新数据 | 找得到 → 改 → 返回。`response_model=ItemOut` 过滤 |
| 紧接着 `GET /items/1` | **200**，和 PUT 的返回一字不差 | PUT 真的改了内存里的那条 |
| `PUT /items/99`，body 合法 | **404** `{"code":404,"msg":"没有这个 id"}` | 循环走完没找到 → 那句 `raise`。**body 校验先过了才轮到它** |
| `PUT /items/abc` | **422**，`loc` 是 `["path","item_id"]` | `abc` 不是 int，路径参数校验先拦下——函数根本没进去 |
| body 里 `name` 只有 `"x"` | **422** `string_too_short` | body 校验（`ItemIn`）拦下——比 404 那步更早 |
| body 里 `price` 是 `-1` | **422** `greater_than_equal` | 同上，`Field(ge=0)` |

**顺序看清楚**：路径参数校验（422）→ body 校验（422）→ 函数体（404 还是 200 由这里决定）。
所以「`PUT /items/99` 回 404」的前提是 body 合法——body 不合法，99 根本轮不到被找。

PUT 和 POST 的 body 校验是**同一个模型**：`payload: ItemIn`。没有第二套「更新专用的校验规则」——
今天 PUT 就是「全量替换」：body 里给什么字段，那条就变成什么；缺字段直接 422，不存在「只改名字、价格保持不变」的写法（那是 PATCH 的活，今天的禁令表里有它）。

### ④ DELETE 的四种结局（接着在终端 B 打）

```bash
curl -s -w ' [%{http_code}]\n' -X DELETE http://127.0.0.1:8782/items/2
curl -s -w ' [%{http_code}]\n' http://127.0.0.1:8782/items
curl -s -w ' [%{http_code}]\n' -X DELETE http://127.0.0.1:8782/items/2
curl -s -w ' [%{http_code}]\n' -X DELETE http://127.0.0.1:8782/items/abc
```

真跑：

```
 [204]
[{"id":1,"name":"pen2","price":4},{"id":3,"name":"box","price":10}] [200]
{"code":404,"msg":"没有这个 id"} [404]
{"detail":[{"type":"int_parsing","loc":["path","item_id"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"abc"}]} [422]
```

四行，注意两个细节：

1. **第一行成功那条，`[204]` 前面是空的**——204 没有响应体。对比第 9 条 POST 的 201，
   201 带着完整的 `{"id":...}` 回来，204 什么都没有。**201 是「成了，给你看新货」；
   204 是「成了，没货可给」。**
2. **第二行**：删完 2 号，列表里只剩 1 号和 3 号——`pop` 真的把那条从内存里拿掉了。
3. **第三行**：同一个 `DELETE /items/2` 再打一次，404。**第一次删掉了，第二次没有可删的**——
   这就是你 ① 里猜的第二题，下面 ⑦ 专门讲。
4. **第四行**：`DELETE /items/abc` → 422，和 PUT、GET 的 abc 同一个形状——路径参数校验对三个动词一视同仁。

### ⑤ 405 组：路径在，动词没注册（接着打）

```bash
curl -s -w ' [%{http_code}]\n' -X PUT -H 'content-type: application/json' -d '{"name":"pen2","price":4}' http://127.0.0.1:8782/items
curl -s -w ' [%{http_code}]\n' -X DELETE http://127.0.0.1:8782/items
curl -s -w ' [%{http_code}]\n' -X POST -H 'content-type: application/json' -d '{"name":"pen2","price":4}' http://127.0.0.1:8782/items/1
```

真跑：

```
{"detail":"Method Not Allowed"} [405]
{"detail":"Method Not Allowed"} [405]
{"detail":"Method Not Allowed"} [405]
```

三条全 405。**405 的 body 是字符串**——`{"detail":"Method Not Allowed"}`。
这是 Day 4 那张 16 条表里的第 11、12 条的翻版，机制完全没变：

> `PUT /items`（列表上 PUT）——`/items` 这个路径注册了 `GET` 和 `POST`，没有 `PUT`。
> `DELETE /items`——同理，没有 `DELETE`。
> `POST /items/1`——`/items/{item_id}` 注册了 `GET` / `PUT` / `DELETE`，没有 `POST`。

**404 / 405 / 422 的三分流，今天凑齐了第二次**：

| 现象 | body 形状 | 读法 |
|---|---|---|
| 404 | `{"code":404,"msg":"没有这个 id"}`（你的形状） | 路径**在**、方法**在**，但**数据里没有**——函数自己 `raise` 的 |
| 405 | `{"detail":"Method Not Allowed"}`（字符串） | 路径**在**，方法**不在**——根本没进函数 |
| 422 | `{"detail":[...列表...]}` | 进去了，但**参数/body 校验没过**——函数没开始跑 |

一眼看 body 就能分：**字符串 detail → 路径或方法层面；列表 detail → 校验层面；你的 code/msg → 业务层面。**

### ⑥ 204 的完整长相：头、空体、以及一个会让你启动即炸的写法

先看 204 的完整响应头。刚才那条成功 DELETE 的响应，把 `-w` 换成 `-D -` 看原始头：

```bash
curl -s -D - -o /dev/null -X DELETE http://127.0.0.1:8782/items/1
```

真跑（日期、耗时必然不同，结构必须一样）：

```
HTTP/1.1 204 No Content
date: Wed, 09 Sep 2026 09:29:23 GMT
server: uvicorn
content-type: application/json
x-process-time: 0.0004
```

读头：

- 第一行 `HTTP/1.1 204 No Content`——状态行自己就把话说完了：No Content。
- **没有 `content-length` 这一行**——没有 body 可量。第 7 条那个 404 是有 content-length 的。
- `content-type: application/json` 还在——**头可以有，body 必须没有**。
- `x-process-time` 在——DELETE 也走中间件后半段，头加得上（Day 6 第六节的结论对 204 一样成立）。

**204 的规矩只有一条：框架不序列化 body。** 你 `return None`，它不发 body；就算你返回一个 dict，
它也照样不发（所以 `response_model` 才被禁止——见下面那个炸的实验）。对比 Day 6 那个 200 + `None` →
`null` 的 `/strict`：**200 会把返回值序列化成 body，204 根本不给 body 这个机会。**

再做一个会炸的实验——**给 DELETE 挂上 `response_model`**。新建一个文件（终端 A）：


读法：**204 禁止声明 `response_model`**——你要的是「没话说」，`response_model` 却承诺「有话说，

### ⑦ 幂等：删两次，第二次到底该回什么

你刚亲眼看到：`DELETE /items/2` 第一次 204，第二次 404。这是「bug」吗？不是。

这里有两个不同的东西，别混：

1. **服务端的状态**：删一次，2 号没了；删十次，2 号**还是没了**——状态收敛到同一个终点。
   HTTP 管这个叫**幂等**：同一个请求打多少遍，服务端状态不变。DELETE 和 PUT 是幂等的，POST 不是
   （POST 打两遍，列表里两条）。
2. **响应码**：第二次 DELETE 回 404 还是 204，是另一个决定。两种都合理：

| 选择 | 第二次 DELETE 回 | 谁舒服 | 代价 |
|---|---|---|---|
| A. 找不到就 404 | `{"code":404,"msg":"没有这个 id"}` | 客户端能区分「删掉了」和「本来就不存在」 | 客户端得自己判断：404 也算成功 |
| B. 找不到也 204 | 204 | 重试型客户端（消息队列消费者、定时任务） | 客户端分不清两种结局 |

**今天的契约用 A**：和 GET / PUT 共用一个错误处理路径，代码里只有一种「找不到」的写法。
你只要知道 B 存在——将来给「会重试的调用方」写 API 时再选 B。

所以 ① 里三个猜测的答案：PUT/DELETE 对不存在的 id 都回 **404**（第 1 题）；
DELETE 打两次，第一次 204、第二次 404（第 2 题，契约 A）；PUT 的 body 照过 `ItemIn` 校验（第 3 题，是的）。

### ⑧ 隐藏的雷：删了再 POST，id 会撞车（先猜，再跑）

```python
def find_biggest():

    for it in items:
```


### ⑨ 对上 + 必答两句

| 你现在会的动词 | 成功码 | 找不到 | 参数/body 不对 | 方法没注册 |
|---|---|---|---|---|
| GET /items | 200 | —— | 422（query） | 405 |
| GET /items/{id} | 200 | 404 | 422（path） | 405 |
| POST /items | **201** | —— | 422（body） | 405 |
| PUT /items/{id} | 200 | 404 | 422（path 或 body） | 405 |
| DELETE /items/{id} | **204**（无 body） | 404 | 422（path） | 405 |

必答（说给空气听，说顺了算过）：

1. 「`DELETE /items/2` 打两次，第二次回 404，为什么不是 bug？」——答案在 ⑦：幂等约束的是**状态**不是**响应码**；我们选契约 A，和 GET/PUT 共用一条 404 路径。
2. 「`PUT /items/99` 为什么是 404 而不是 422？」——99 本身是合法 int，body 也合法；是**函数体**里找不到它才 404。422 只发生在参数或 body 没过校验时，比函数体更早。

### ① 先看今天要治的病

第二节结束时你 POST 过 fan（id=1）。现在**Ctrl+C 关掉服务，重新起一次**，然后 GET：

**为什么选文件、不选 sqlite3？** 昨天的承诺是「文件或 sqlite3，今天定一个」。定文件，三个理由：

1. **形状不变**：你的数据是 list[dict]，`json.dump` 存的就是 list[dict]，`json.load` 读回来还是
   list[dict]——代码里 `for it in items` 一行都不用改。sqlite 是「表 + SQL 语句」，那是一个新世界。
2. **看得见**：文件可以用 `cat` 直接看，出问题肉眼可见。数据库要开工具才能看。
3. **给 Day 16 留的形状是「数据在进程外」**：Day 16 你要上 Chroma（向量数据库）——它也是一个
   「进程外的、把数据落在磁盘上的东西」。今天的结论「**数据不跟进程走，服务启动时自己把数据接回来**」，
   到那天原样成立：换的只是 `save()` 和启动加载这两处。

### ② 文件读写的六个词（先不起服务，直接跑 python）

先在终端 A 用三行 python 把「文件读写」这件事本身看清楚——它和 FastAPI 没关系：

```bash
python3 - <<'PY'
import json
items = [{"id": 1, "name": "pen", "price": 3}]
with open("demo.json", "w") as f:
    json.dump(items, f)

PY
cat demo.json
```

真跑：

```
存完了
[{"id": 1, "name": "pen", "price": 3}]
```

然后把它读回来：

```bash
python3 - <<'PY'
import json

    items = json.load(f)
print("读回来", len(items), "条：", items)
PY
```

真跑：

```
读回来 1 条： [{'id': 1, 'name': 'pen', 'price': 3}]
```

六个词，逐个认：

| 词 | 读法 | 备注 |
|---|---|---|
| `open("demo.json", "w")` | 打开文件，`"w"` = 写入（write）。**文件不存在会新建，存在会清空重写** | `"w"` 是今天唯一的模式 |
| `with ... as f:` | 「这段用着 f，用完自动关掉」 | Day 6 的 `with` 只有这一种，没有例外 |
| `json.dump(数据, f)` | 把数据**存**进文件 f | 数据是 list/dict/数字/字符串都行；最后那个 `f` 是文件，不是格式 |
| `open("demo.json")` | 打开文件**读**（默认就是读） | 不写第二个参数 = 读 |
| `json.load(f)` | 从文件 f 把数据**读**回来 | 返回的东西和存进去的形状一模一样 |
| `import json` | 标准库，装 Python 那天就在 | Day 1 你查 `openapi.json` 用的就是它，今天第一次写它 |

两个**参数**（不是新词，是给 `json.dump` 的两个选项）：

```bash
python3 - <<'PY'
import json
items = [{"id": 1, "name": "笔", "price": 3}]
with open("demo2.json", "w") as f:
    json.dump(items, f, ensure_ascii=False, indent=2)
PY
cat demo2.json
```

真跑：

```
[
  {
    "id": 1,
    "name": "笔",
    "price": 3
  }
]
```

- `ensure_ascii=False`：不写成 `\u7b14` 那种转义，中文直接存中文。
- `indent=2`：每个元素换行缩进，人能直接读。没有它也能存能读，就是挤成一行。

> 读回来时不用写这两个参数——`json.load` 只负责读，文件里是什么样它都能读。
> 存的时候才需要操心「存成什么样」。

### ③ 把 `items` 从「写死的三条」改成「文件不在就读种子、在就读文件」

回到 `app.py`。现在文件里 `items` 是写死的三条 list。把它换成下面这一整段
（**位置不变，还是原来 `items` 那段的位置**，在 `pagination` 函数之前）：

```python
DB_FILE = "items.json"


def save():
    with open(DB_FILE, "w") as f:
        json.dump(items, f, ensure_ascii=False, indent=2)


try:
    with open(DB_FILE) as f:
        items = json.load(f)
except FileNotFoundError:
    items = [
        {"id": 1, "name": "pen", "price": 3},
        {"id": 2, "name": "cap", "price": 5},
        {"id": 3, "name": "box", "price": 10},
    ]
    save()
```

同时，文件第一行加 `import json`：

```python
import json
import time
```

读这段的四个问题，逐个答：

1. **`DB_FILE` 是什么？** 一个名字全大写的变量 = 「模块级常量」。把文件名写在一个地方，
   后面 `save()`、加载都引用它。今天文件名叫 `items.json`，`DB_FILE` 是给这个字符串起的名。
2. **为什么 `def save()` 写在 `try` 前面？** 模块的代码从上往下跑。`try` 的 `except` 分支里
   要调用 `save()`——如果 `save` 定义在 `try` 后面，跑到 `except` 时 Python 还没见过 `save` 这个名字，
   会报 `NameError`。**被调用的函数，得定义在被调用的位置之前。**
3. **`try` / `except FileNotFoundError` 在干什么？** 启动时试着读文件：文件在 → `items = json.load(f)`，
   服务用文件里的数据；文件不在（第一次运行，或文件被删了）→ `open` 抛 `FileNotFoundError`
   （名字就是意思：找不到这个文件）→ 走 `except`：**给 items 装回那三条种子，并立刻存一次盘**，
   让文件从第一次启动起就存在。
4. **为什么种子的三条要搬进 `except`？** 原来它们是无条件写死的；现在它们只是「没有文件时的默认值」。
   文件在的话，数据以文件为准——你昨天 POST 的 rug 才能在重启后回来。

> `save()` 函数体里用了 `items`，但 `def` 那行下面的 `items` 是在 `try` 里才赋值的——
> 没关系：**函数体里的名字是调用时才去查的**（Day 6 第一节那个 `read_key(store, key)` 同理）。
> `save()` 第一次被调用一定发生在 `items` 已经赋值之后（要么 `try` 读到了，要么 `except` 装好了种子）。

顺手把服务名也改了（现在它是昨天留下的 `day006`）：

```python
# read_root 里，把这一行：
    return {"service": "day006", "count": len(items)}
# 换成：
    return {"service": "day007", "count": len(items)}
```

### ④ 起服务，看第一次启动（终端 A）

### ⑤ 还差一步：写操作之后要存盘

现在只解决了「读」。POST / PUT / DELETE 改了内存里的 `items`，**文件还停在三条**——

```python
    return data
```

### ⑧ 写不进去的时候回几？（昨天预告兑现）

现在来点昨天预告的事故。把 items.json 改成**只读**（权限 444 = 只能读不能写），
然后 POST 一条——`save()` 要写盘，写不进去：

```bash
# 终端 B
chmod 444 items.json
curl -s -w ' [%{http_code}]\n' -X POST -H 'content-type: application/json' -d '{"name":"rug2","price":9}' http://127.0.0.1:8783/items
```

真跑（客户端这一面）：

```
{"code":500,"msg":"服务器内部错误"} [500]
```

**昨天问的「写不进去回几」，答案：500。** 但不是你写的 500——是三个保险丝接力接住的：

- `save()` 里的 `open(DB_FILE, "w")` 碰上只读文件 → 抛 `PermissionError`（名字就是意思：权限不够）。
- `PermissionError` 从 `create_item` 里冒出来 → 中间件的 `try` 逮住它 → 打印 `[崩了]`（保险丝一）。
- 中间件原样 `raise` → `@app.exception_handler(Exception)` 接住（保险丝二）→ 打印 `[兜底]` → 返回
  `{"code":500,"msg":"服务器内部错误"}`。

看终端 A，应该正好三行（`.venv` 内部的栈不算）：

```
[请求] POST /items
[崩了] PermissionError 用了 0.001
[兜底] PermissionError
```

**这就是 Day 6 第五节 ④ 那个 `KeyError` 要证明的事**：不管异常是什么类型、从哪一层冒出来，
只要没人提前接住，路径永远是「冒到中间件 → `[崩了]` → 交给 `[兜底]` → 500」。
今天的 PermissionError 和那天的 KeyError 走的是同一条路——**昨天的保险丝，今天验收合格**。

但事情没完。现在 GET 一下列表：

```bash
curl -s -w ' [%{http_code}]\n' 'http://127.0.0.1:8783/items?size=10'
```

真跑：

```
[{"id":1,"name":"pen","price":3},{"id":2,"name":"cap","price":5},{"id":3,"name":"box","price":10},{"id":4,"name":"rug2","price":9}] [200]
```

**rug2 在列表里！** 内存里加上了——`create_item` 是先 `append` 再 `save()`（⑤ 的顺序），
append 成功了，save 才失败。于是出现了 Day 5 那句话的现场版：**500 不等于什么都没发生。**
客户端收到 500，会以为这次 POST 失败了、重试一遍——而内存里其实已经有一条 rug2 了。

那磁盘呢？文件只读，`save()` 从没成功过。把权限改回来，重启，看真相：

```bash
# 终端 B
chmod 644 items.json
# 终端 A：Ctrl+C 再起
```

```bash
curl -s -w ' [%{http_code}]\n' 'http://127.0.0.1:8783/items?size=10'
```

真跑：

```
[{"id":1,"name":"pen","price":3},{"id":2,"name":"cap","price":5},{"id":3,"name":"box","price":10}] [200]
```

**rug2 蒸发了。** 内存是假象，磁盘才是真相——重启时数据从文件来，文件里没有 rug2。

三句话收进今天的笔记：

1. 写失败 → 500，不是 4xx：**这是服务器自己的错（磁盘/权限），不是请求的错**，归 5xx。
2. 「先改内存再存盘」的代价：**save 失败时，内存和磁盘已经不一致**——500 的响应告诉客户端失败了，
   但内存里改了。今天的契约接受这个代价（单进程、文件小、失败罕见）；
   等 Day 16 上真数据库，事务会解决「要么都成、要么都不成」。
3. 排查口诀：**凡是「重启就恢复原样」的怪问题，先怀疑数据根本没落盘。**

把权限和文件都还原（回到种子三条的干净状态）：

```bash

rm items.json
```
