## 一、今天要解释的现象：`uv sync` 把刚装的包删了

今天只有一个现象要解释。我把它做出来了，下面全是**真实输出**，不是设想：

在你的环境里装一个包，`import` 它，成功。然后跑一句 `uv sync`。**它被删了。**

这个现象我最早用 `cowsay`（一个打印会说谎的牛的小包）撞到的，
刚才又换 `ruff` 重做了一遍，**两次结果一模一样**——
挑哪个包根本不重要，这才说明它是机制，不是意外。

今天要把它讲透。透的标准是：你听完之后，能预判出下一次类似操作会发生什么。

下面用 `ruff` 从头走一遍，你可以逐字对照。

```bash
uv pip install ruff
```

```
Resolved 1 package in 1.48s
Installed 1 package in 6ms
 + ruff==0.16.6
```

装上了。三个信息：解析了 1 个包（ruff 没有别的依赖），装好了，版本 0.16.6。

```bash
uv run python -c "import ruff; print('ruff 在环境里')"
```

```
ruff 在环境里
```

一切正常。**记住这一刻——等下它会被 `uv sync` 抹掉。**
现在跑 `uv sync`：

```bash
uv sync
```

```

```

```bash
uv run python -c "import ruff"
```

```

```

**它没了。** 而且 `uv sync` 没报错，退出码 0，看起来一切正常。

## 二、npm 对照表，以及 `uv add` / `uv sync` / `uv pip install` 的差别

你写过前端，那这套东西你其实已经用过一遍了，只是换了名字。
**这张表是我给你的，不是让你填的**——你今天的任务是把它背进肌肉记忆，
因为后面 155 天你会不断在 Python 和 Node 之间来回跳。

| 你在前端熟悉的 | 这个仓库里的 | 它记的是什么 |
|---|---|---|
| `package.json` | `pyproject.toml` | 我**想要**什么。写的是范围：`fastapi>=0.141.1` |
| `package-lock.json` | `uv.lock` | 实际**定下来**什么。每个版本钉死，含所有平台分支 |
| `node_modules/` | `.venv/` | 磁盘上**真有的**那些文件 |
| `npm ci` | `uv sync` | 按 lock 复现，**多余的东西删掉** |
| `npm install <pkg> --save` | `uv add <pkg>` | 同时改声明和锁 |
| `npx <cmd>` | `uv run <cmd>` | 在项目环境里执行一条命令 |
| 手改 lock 文件 | 手改 `uv.lock` | 都能改，但都别改 |

**六个里面只有第五行是坑，也是今天全部的难点。**

`npm ci` 和 `npm install` 你分得清：`ci` 严格照 lock 装、多出来的清掉，
`install` 会**改写** lock。

Python 这边对得更干净：

| | 改 lock 吗 | 删掉 lock 里没有的东西吗 |
|---|---|---|
| `uv add` / `uv remove` | **改** | 不管 |
| `uv sync` | 不改 | **删** |
| `uv pip install` | 不改 | 不管 |

看第三行。`uv pip install ruff` 既不改 lock，也不删东西——
**它就是往 `.venv` 里偷偷塞了一个文件**。

所以 `uv sync` 眼里，ruff 是「一个 lock 里查无此包的东西」。删。

这就是那个问题的完整答案：**`uv pip install` 装的东西是临时的，`uv add` 装的才是正式的。**
前者像你在 `node_modules` 里手动拷了个目录进去，`npm ci` 一次就给你清了。

## 三、`uv add --dev ruff` 的实际结果

同一个包，换个命令，结果完全不同。我实跑了，输出是这样：

```bash
uv add --dev ruff
```

```
Resolved 110 packages in 3.43s
Downloading ruff (9.4MiB)
 Downloaded ruff
Prepared 1 package in 3.79s
Installed 1 package in 4ms
 + ruff==0.16.6
```

注意第一行：**Resolved 从 109 变成了 110**。它重新解析了整张依赖图，
因为你要的东西多了，锁文件必须重算。

然后三个文件全变了（我对着 `grep` 验过）：

```
pyproject.toml:22:    "ruff>=0.16.6",
requirements.txt:278:ruff==0.16.6
uv.lock: name = "ruff" 出现 3 次
```

再跑 `uv sync`：

```
Resolved 110 packages in 3ms
Checked 107 packages in 3ms
```

**`Checked`，不是 `Uninstalled`。** 因为 lock 里现在有它了。
`uv pip freeze` 从 106 涨到 107，`.venv` 从 372 MB 涨到 394 MB（ruff 是个 Rust 写的二进制，9.4 MB 压缩包，解开后更占地方）。

同一句 `uv sync`，两个命令两条命运。区别不在包，在**它进没进 lock**。

## 四、109 / 108 / 106：三个数字各自数的是什么

这三层的数字**永远不相等**，而且相等反而是坏事。原因有两个，都很具体。

**109 → 108**：解析图里有 109 个节点，其中一个是**这个项目自己**（`ai-agent-learning`）。
`pyproject.toml` 里没有 `[build-system]` 这一段，uv 就把它当 *virtual project*——
只装依赖，不把自己当包安装。所以导出 `requirements.txt` 时不列它。
（对应 Node 世界里：`package-lock.json` 的树根是你自己，但没人会把自己 `pip install` 进 `node_modules`。）

**108 → 106**：有 6 个包带着**平台条件**（叫 environment markers），
你的 Mac 只装其中 4 个。这 6 行是 `requirements.txt` 里所有带分号的行，我全贴出来：

```
colorama==0.4.6        ; os_name == 'nt' or sys_platform == 'win32'
hf-xet==1.6.0          ; platform_machine == 'AMD64' or ... or platform_machine == 'x86_64'
httpcore2==2.12.0      ; sys_platform != 'emscripten'
httpx2-jsfetch==1.0    ; sys_platform == 'emscripten'
truststore==0.10.4     ; sys_platform != 'emscripten'
uvloop==0.22.1         ; platform_python_implementation != 'PyPy' and sys_platform != 'cygwin' and sys_platform != 'win32'
```

你这台机器是 `darwin arm64 CPython`（想自己确认就跑
`uv run python -c "import sys,platform; print(sys.platform, platform.machine(), platform.python_implementation())"`）。
对着上面六行逐条判：

| 包 | 条件成立吗 | 装了吗 |
|---|---|---|
| `colorama` | `os_name=='nt'`？你是 `posix` → 不成立 | ✗ |
| `hf-xet` | `platform_machine=='arm64'` → 成立 | ✓ |
| `httpcore2` | `darwin != 'emscripten'` → 成立 | ✓ |
| `httpx2-jsfetch` | 只要浏览器 WASM → 不成立 | ✗ |
| `truststore` | 成立 | ✓ |
| `uvloop` | `darwin != 'win32'` → 成立 | ✓ |

`108 − 2 = 106`。我在你机器上数过，`uv pip freeze | grep -c "=="` 正好 **106**。

## 五、Windows 同事 `uv sync` 之后装到的不一样（environment markers）

现在假设一个 Windows 同事 clone 这个仓库，跑 `uv sync`。

按第四节的表重算一遍：

| 包 | Windows 上 |
|---|---|
| `colorama`（要 `win32`） | ✓ **装**（你没有） |
| `hf-xet`（`AMD64` 在列表里） | ✓ 装 |
| `httpcore2`（`!= emscripten`） | ✓ 装 |
| `httpx2-jsfetch` | ✗ 不装 |
| `truststore` | ✓ 装 |
| `uvloop`（明确排除 `win32`） | ✗ **不装**（你有） |

**他数出来的包数和你一模一样**（基线 106；你做完第 2 题是 107）。`uv sync` 成功，没有报错。

但他少了一个 `uvloop`，多了一个 `colorama`。

**这件事不用猜，也不用拿它去讲道理——我在你机器上直接证出来了。**
`uv pip compile` 可以按**别的平台**重新解析一份清单。不用找 Windows 同事，
你的 Mac 就能生成「他那份环境应该长什么样」：

```bash
uv pip compile requirements.txt \
  --python-platform x86_64-pc-windows-msvc \
  --python-version 3.13 --no-header --no-deps -o /tmp/win.txt

uv pip freeze | sed 's/==.*//' | sort > /tmp/mac.txt
sed -n 's/^\([A-Za-z0-9_.-]*\)==.*/\1/p' /tmp/win.txt | sort > /tmp/win2.txt
comm -3 /tmp/mac.txt /tmp/win2.txt
```

真实输出（刚在你机器上跑的）：

```
        colorama
uvloop
```

`comm -3` 只印两边各自独有的部分——**左列是你独有，右列是他独有**。
所以：你多了 `uvloop`，他多了 `colorama`，**而两边的包数完全相同**。

> **这一条是今天最值钱的结论：环境是否一致，从来不是靠数个数判断的。**
> 数字是摘要，摘要会骗人。真要比对，比的是**两份清单的集合差**。
> （对应前端：两份 `node_modules` 文件数一样，不代表版本树一样。）

`uvloop` 到底是什么、少了它代价多大，**今天不需要知道**，后面讲并发时它会回来。
今天只要立住一件事：**你有一种在自己机器上跑出「别人那份环境」的办法。**
以后碰到「我们数字一样啊」的争论，你不用参与争论，你直接生成清单。

顺带解释了你会遇到的一句话——为什么 CI 里都用 `uv sync --frozen`：
`--frozen` 意思是「lock 一个字都不许改，装不出来就报错」。
它把「重解析」这条路堵死了，才真正做到跨机器一致。

## 六、把一个传递依赖显式写进 `pyproject.toml`（httpx）

`httpx` 这个包，本来就在你的 `.venv` 里——不是你装的，
是 `langsmith` 作为传递依赖拖进来的。

我们把它显式写进了 `pyproject.toml`。结果：
Resolved 仍是 **109**，实装仍是 **106**。三层数字一个都没变。

**变的是什么？是「谁为它负责」。**

以前：`uv remove langsmith` → langsmith 没了 → 它拖进来的 httpx 也一起蒸发 → 你的代码当场崩。
现在：httpx 是你自己声明的，谁也带不走。

这条判断标准值得单独记住：

> **凡是你的代码里 `import` 过的东西，就必须出现在 `pyproject.toml` 里——
> 哪怕它已经躺在 `.venv` 里了。**
>
> 「现在能用」和「明天还在」是两件无关的事。传递依赖是别人借给你的，别人随时收回。

## 七、环境问题排查顺序表

从上往下，先查便宜的：

| 现象 | 先看哪一层 | 一条命令验证 |
|---|---|---|
| `import X` 报 `ModuleNotFoundError`，但 pyproject 里有 X | **第三层**：环境没同步，或者你用的不是这个 `.venv` | `uv sync` 然后 `uv run python` 而不是 `python` |
| pyproject 里没有 X，`uv sync` 之后 X 消失了 | **第二层**：它不在 lock 里，被清理了 | `grep -c 'name = "x"' uv.lock` |
| 你和同事包数一样但行为不同 | **第二层的 marker** | `grep ';' requirements.txt` 找出平台相关的包 |
| 改了 `requirements.txt`，什么都没发生 | **改错文件了**：它是产物 | `uv export --no-hashes --all-groups -o requirements.txt` |
| `uv add` 之后一个没碰过的包升级了 | **第一层写的是范围** | `git diff uv.lock` 看谁变了 |
