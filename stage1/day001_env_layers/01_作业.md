## 第 1 题 · 三个数字对不上（15 分钟）

**在哪**：仓库根目录（提示符结尾是 `AI-agent %`）。

**先后顺序**：本题设计在先做第 2 题**之前**跑。如果你已经做了第 2 题，
**不用回退**，直接往下跑，然后看下面那个引用块。

**做什么**：依次跑这四条，把输出**原样抄下来**。

```bash
uv sync
uv pip freeze | grep -c "=="
grep -c "==" requirements.txt
du -sh .venv
```

**你会看到**（基线，也就是你还没做第 2 题时）：

- 第 1 条：`Resolved 109 packages in ...`，后面可能跟 `Checked 106 packages`
- 第 2 条：`106`
- 第 3 条：`108`
- 第 4 条：`372M .venv`

> **如果你已经先做了第 2 题**（往 dev 组加了 `ruff`），你看到的是：
>
> ```
> Resolved 110 packages    |  freeze: 107  |  requirements: 109  |  394M
> ```
>
> **四个数各自 +1，你没做错任何事。** 而且这正好是本题想要的那个结论：
> 三个数字之间的**两个差额一点没变**——110→109 还是「项目自己算一个节点」，
> 109→107 还是「两个包被平台条件挡掉」。加一个包把三个绝对值全推上去了，
> **机制一格没动**。
>
> 所以以后你在任何一台机器上看到任意一组这三个数，都先去算差额，
> 而不是去比对数字本身。差额不变 = 机制相同。

**然后回答一句**（写在纸上或备忘录里，不用交）：

```
109、108、106 是三个不同的数。用「三层」的语言说，
每一个差是从哪一层到哪一层产生的？
答：
```

**过关标准**：你能说出**两个原因**，而不是三个数字。
一个是「项目自己也算一个节点」，一个是「有些包带平台条件，你这台机器不满足」。

这题不考你记不记得 106。下次你 `uv add` 一个包它就变 107 了，
**记住 106 没有任何价值，知道它为什么会变才有价值。**

## 第 2 题 · 主产物：把一个工具变成环境的正式成员（62 分钟）

**做什么**：挑**一个**你后面三个月真的会用的开发工具，把它装进环境，
并且走完「临时 → 正式」两条路，亲眼看到同一包的两种命运。
最后**保留**它——这是你今天留下的东西。

**挑包的标准**（三条都满足）：

1. 只在开发时用得到（所以进 `dev` 组，不是运行依赖）
2. 不带重型依赖（别拖 CUDA、别拖几百 MB 模型）
3. 你真的会用

给你三个候选，也可以自己找。**选包的标准不是「以后哪天用得上」，
而是「今天做完第 2 题，你能立刻验证它在工作」：**

| 包 | 干什么用 | 装完就能跑的验证 |
|---|---|---|
| `ruff` | 代码检查和格式化 | `uv run ruff check stage1` → `Found 22 errors.` |
| `pytest-cov` | 给 pytest 加覆盖率报告 | `uv run pytest --cov=tests -q` → 多出一张 `Name / Stmts / Missing` 表 |
| `ipykernel` | 让 Jupyter 能用这个 `.venv` | `uv run python -c "import ipykernel; print(ipykernel.__version__)"` → 一个版本号 |

**只有 `ruff` 那一行是我刚在你机器上真实跑出来的。** 另外两行没跑（跑它就得动你
刚做完的 dev 组），是按同类工具的常规行为写的预期——**你自己跑出来不一样，以你的屏幕为准。**

`Found 22 errors` 那 22 个**全在我写的 `check.py` 里**，不是你的代码。
你装的第一个工具，第一个报到的是我的错。这不是玩笑：它说明这类工具能看见肉眼漏掉的东西。

下面用 `<你的包>` 表示你选的那个，我拿 `ruff` 当示例填数字。

### 2A · 先走「临时」路线（预计 12 分钟）

**第一步：装，然后立刻证明它在。**

```bash
uv pip install <你的包>
uv run python -c "import <模块名>; print('装上了')"
```

**该看到**：`装上了`。

> **模块名不一定等于包名**——包名里的横杠在 import 时要换成下划线。
> `ruff` → `import ruff`，`ipykernel` → `import ipykernel`，
> 但 `pytest-cov` → `import pytest_cov`（写 `import pytest-cov` 是语法错误）。

**第二步：跑一句 `uv sync`，看它消失。**

```bash
uv sync
```

**该看到**：输出里有一行 `Uninstalled 1 package`，下面紧跟着 `- <你的包>==<版本号>`。

```bash
uv run python -c "import <模块名>"
```

**该看到**：`ModuleNotFoundError: No module named '<模块名>'`

**这两步的顺序不能颠倒**。先看到「在」，再看到「没了」，这个反差就是今天要讲的那件事。
只跑第二步你是看不出区别的——那时候「没装上」和「装上被删了」长得一模一样。

**记一句**：第一步它**确实在**，所以不是你做错了；是 `uv sync` 删的。**因为它不在 lock 里。**

### 2B · 再走「正式」路线（预计 20 分钟）

```bash
uv add --dev <你的包>
```

**该看到**（`ruff` 的真实输出）：

```
Resolved 110 packages in 3.43s
Downloading ruff (9.4MiB)
 Downloaded ruff
Prepared 1 package in 3.79s
Installed 1 package in 4ms
 + ruff==0.16.6
```

**盯住第一行的数字**。它从 `109` 变成了 `110` 或更大。
这就是教案里说的「`uv add` 会重新解析整张图」——你和 `uv pip install` 的
根本区别就在这一行上。

```bash
uv sync
```

**该看到**：`Checked 107 packages`。**不是 `Uninstalled`。** 这一字之差就是今天的全部课程内容。

（`107` 是 `ruff` 的数。你选的包拖了几个依赖，就是 106 加几个。
**要盯的是 `Checked` 这个词，不是那个数字**——数字下次就变，词才是机制。）

### 2C · 证明三层都留下了痕迹（预计 15 分钟）

```bash
grep -n "<你的包>" pyproject.toml
grep -c 'name = "<你的包>"' uv.lock
grep -n "^<你的包>==" requirements.txt
```

**该看到**：前两条有输出。

**第三条大概率没输出** —— 如果你没跑过 `uv export`，`requirements.txt` 还是旧的。

这不是你的错，这是本仓库最容易忘的一步。补上：

```bash
uv export --no-hashes --all-groups -o requirements.txt
grep -n "^<你的包>==" requirements.txt
```

这次应该有输出了，比如 `278:ruff==0.16.6`。

### 2D · 收尾验证（预计 15 分钟）

```bash
uv pip freeze | grep -c "=="
du -sh .venv
uv run pytest -q
```

**该看到**：包数比基线 `106` 多（多几个取决于你的包带几个依赖，`ruff` 是 107）；
`.venv` 比 `372M` 大；`7 passed`。

**过关标准**：`check.py` 前 4 项全绿（见末尾）。

**如果 `uv add` 之后 pytest 变红了**：说明它重新解析时顺手升级了别的包。
**不要慌，这是好事**——你今天第一次撞上了「范围允许变动」这个机制。
把 `git diff uv.lock` 的输出读一遍，找出哪个包版本变了，写在第 4 题 B 旁边。

## 第 3 题 · 同事的环境和你不一样，但数字相同（25 分钟）

**在哪**：还是仓库根目录。**这道题不用装任何东西，也不用找同事**——
你在自己的 Mac 上就能把「他那份环境长什么样」生成出来。

**第一步：看有哪几个包带平台条件。**

```bash
grep ';' requirements.txt
```

**你会看到 6 行**。逐条对着「他是 `win32` + `AMD64` + CPython，
你是 `darwin` + `arm64` + CPython」判断。

**第二步：按他的平台重新解析一份清单。**

```bash
uv pip compile requirements.txt \
  --python-platform x86_64-pc-windows-msvc \
  --python-version 3.13 --no-header --no-deps -o /tmp/win.txt
```

**该看到**：屏上刷出一大堆包名，最后一行是 `zstandard==0.25.0` 加一句 `# via -r requirements.txt`。
**别慌，你的 `requirements.txt` 一个字都没变**——它是输入，结果写进了 `/tmp/win.txt`。

```bash
grep -c '==' /tmp/win.txt
uv pip freeze | grep -c '=='
```

**该看到**：**两个一模一样的数**（基线 106 对 106；你做完第 2 题是 107 对 107）。

**第三步：不比数字，比集合。**

```bash
uv pip freeze | sed 's/==.*//' | sort > /tmp/mac.txt
sed -n 's/^\([A-Za-z0-9_.-]*\)==.*/\1/p' /tmp/win.txt | sort > /tmp/win2.txt
comm -3 /tmp/mac.txt /tmp/win2.txt
```

**该看到**（两行，**位置有讲究**）：

```
        colorama
uvloop
```

`comm -3` 只印各自独有的部分：**左列 = 你有他没有，右列（缩进那一行）= 他有你没有。**

**然后回答**：

```
1. 第二步两个数字相同，第三步却说环境不同。哪一步才是证据？为什么？
   答：

2. 你独有的是哪个包、他独有的是哪个包？（方向别搞反）
   答：

3. 为什么不会被 uv sync 报错、不会被 pytest 发现、
   也不会被「比一下包数量」拦下？
   答：
```

**过关标准**：

1. 说清「数量是摘要，摘要会骗人；**集合差才是证据**」
2. `uvloop` 你有、`colorama` 他有
3. 第 3 问答出「这三样都在比对**摘要**，没有一个在看**内容**」

**你不需要知道 `uvloop` 是干什么的。** 那是后面讲并发时的内容，
今天它就是一个符号——重点是**你拿到了两个不同的集合**。
