## 第 1 题 · 三层的数字

| 层 | 文件/位置 | 数量 | 它记的是什么 |
|---|---|---|---|
| 声明 | `pyproject.toml` | 8 运行 + 2 开发 | **范围**（`>=1.5.9`），不是具体版本 |
| 解析 | `uv.lock` | Resolved 109 | 精确版本 + 跨平台分支 |
| 实物 | `.venv/` | 106 个包 / 372 MB | 你这台机器上真正装了的 |

**三个数字为什么不一样**（这是本题的重点，不是 trivia）：

- `109 → 108`：解析图里包含项目自身 `ai-agent-learning`。它没有 `[build-system]`，
  是 uv 的 virtual project，只装依赖不装自己，所以导出时不列。
- `108 → 106`：两个包带平台标记，在 macOS 上不装：
  - `colorama ; os_name == 'nt' or sys_platform == 'win32'` —— Windows 终端颜色
  - `httpx2-jsfetch ; sys_platform == 'emscripten'` —— 浏览器 WASM 环境

在 Windows 上跑同一份 lock 会装出 107 个（多 colorama）。**lock 是跨平台的，
`.venv` 是单平台的**——这句话能解释你以后遇到的绝大多数「为什么我同事装的包跟我不一样」。

## 第 2 题 · 包为什么消失

因为 `uv sync` 的定义不是「补齐缺失」，而是**「让 `.venv` 精确等于 `uv.lock`」**。
`cowsay` 不在 lock 里 → 它是多余物 → 删。

关键句：**只有 `uv.lock` 有权决定 `.venv` 里有什么。**
你用 `uv pip install` 装的东西绕过了 lock，所以在下一次 sync 时不受保护。

## 第 3 题 · 两种办法的差别

| | 办法 A：`uv sync --inexact` | 办法 B：`uv add --dev cowsay` |
|---|---|---|
| 改了 `pyproject.toml` 吗 | 没有 | 改了（多一行 `"cowsay>=6.1",`） |
| 改了 `uv.lock` 吗 | 没有 | 改了 |
| 下次别人 clone 能拿到吗 | 不能 | 能 |
| 适用场景 | 临时试一个包 | 这个项目长期需要它 |

**这正是昨天 `pip` 的处理过程**：先是每次 `uv sync` 都把它删掉，
后来 `uv add --dev pip` 把它写进 lock，从此普通 `uv sync` 也不再动它。

清理三步缺一不可：`uv remove --dev cowsay` → `uv export ... -o requirements.txt` → `uv run pytest -q`。
漏掉第二步会让 `requirements.txt` 里留着 `cowsay`，也就是让导出物与 lock 失配——
`check.py` 的第 3 项就是查这个。

## 第 4 题 · Node 对照

| Python / uv | Node / npm | 说明 |
|---|---|---|
| `pyproject.toml` | `package.json` | 声明依赖范围 |
| `uv.lock` | `package-lock.json` | 精确版本，要提交 |
| `.venv/` | `node_modules/` | 实物，不提交 |
| `uv sync` | **`npm ci`** | 严格按 lock 装，**删掉多余的** |
| `uv add <pkg>` | `npm install <pkg> --save` | 同时改声明和锁 |
| `uv run <cmd>` | `npx <cmd>` | 在项目环境里执行 |

**陷阱在第 4 行**：多数人会对到 `npm install`。区别是——

- `npm install` 会**修改** `package-lock.json`（它同时是解析器）
- `npm ci` 只**读取** lock，装出精确一致的 `node_modules`，还会先删掉整个目录

`uv sync` 的行为对应 `npm ci`：它不改 lock（改 lock 的是 `uv add` / `uv lock`），
但会把 `.venv` 里多余的东西删掉。

## 第 5 题 · 计划与环境的失配

| 包 | 最早需要 | 到时候装它的命令 |
|---|---|---|
| `sentence-transformers` | Day 15 | `uv add sentence-transformers`（会拖 PyTorch，见加分题） |
| `langchain` | Day 38 | `uv add langchain`（注意：`langchain-core` 已经在了，是 langgraph 拖来的） |
| `llama-index` | Day 45 | `uv add llama-index` |
| `crewai` | Day 75 | `uv add crewai` |
| `python-jose` | Day 93 | `uv add "python-jose[cryptography]"` |

**不要提前装。** 每提前装一个，你的 `.venv` 就多几百 MB，
而 `uv add` 的时候它会重新解析全部依赖，可能顺手升级别的包——
在你还没用到它的时候制造出你现在无法理解的错误。

另外：计划里 Day 125-126 的 Docker 用的是 **CLI**（本机已装 29.4.3），
不需要 Python 的 `docker` SDK，除非你要在代码里控制容器。

### 加分题：Day 15 到底要不要 `sentence-transformers`

两条路的真实取舍：

- **chromadb 自带的默认 embedding function**：首次调用时下载一个 ONNX 小模型
  （约 80 MB，**这个数字我没实测**，是 chromadb 文档里的量级；下载一次后缓存本地）。
  模型是 `all-MiniLM-L6-v2`，384 维，**以英文为主**。
- **`sentence-transformers`**：拖进 PyTorch，`.venv` 会从 372 MB 涨到 2 GB 以上。
  好处是你能自己选模型，包括中文效果好的 BGE 系列。

**给你的判断依据**：你 Day 19 要做的是「基于私有文档做 RAG 问答」，
如果那些文档是**中文**（你的笔记大概率是），MiniLM 的检索质量会明显不够。
所以建议：Day 15-19 先用 chromadb 默认模型把链路跑通（便宜、快、能验证流程），
到 Day 20「RAG 优化」时再决定要不要换成 BGE 小模型——那时你已经能**用检索结果的好坏**
来判断值不值这 2 GB，而不是现在凭想象决定。

## 第 6 题 · 静默失效

`uv sync` 只读两个文件：`pyproject.toml` 和 `uv.lock`。
`requirements.txt` 对它而言是**仓库里一个恰好叫这个名字的文本文件**，跟 `README.md` 地位相同。

所以你追加的那一行：

- 不会报错（没有任何组件去解析它）
- 不会生效（环境仍是 106 个包）
- 会留在文件里（`grep` 得到），制造出「我以为改了」的错觉

这是本仓库里最容易白白浪费半小时的一个坑。恢复只需一条命令：

```bash
uv export --no-hashes --all-groups -o requirements.txt
```

**记住这条纪律**：`uv add` / `uv remove` 之后必须重新导出。
`check.py` 的第 3 项会替你盯着这件事。
