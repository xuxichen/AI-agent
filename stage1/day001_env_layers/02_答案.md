## 第 1 题 · 三个数字，两个原因

**不需要三个数字，需要两个原因。**

| 落差 | 原因 | 属于哪一层之间 |
|---|---|---|
| 109 → 108 | 解析图里有项目自己（`ai-agent-learning`）。没有 `[build-system]`，uv 当它是 virtual project，只装依赖不装自己 | 第 2 层 → 导出 |
| 108 → 106 | 两个包带平台条件，你这台 `darwin arm64` 不满足：`colorama`（要 win32）、`httpx2-jsfetch`（要 emscripten） | 导出 → 第 3 层 |

**为什么"记住 106 没价值"**：你今天 `uv add` 一个包它就变 107，明天 `uv remove` 一个就变回来。
数字是**状态的快照**，原因才是**可迁移的模型**。以后你在同事机器上看到 104，
你要能立刻想到「差的那几个是 marker 挡掉的」，而不是「我的 106 才是对的」。

顺带一个自查：如果你算出来 `108 − 2 = 106` 但 `uv pip freeze` 数出的是别的数，
说明你的 `.venv` 和 lock 不同步了。跑 `uv sync` 就会对上——
**这本身就是教案第七节排查表第一行的用法。**

## 第 2 题 · 参考操作与两种命运

拿 `ruff` 举例，我在你机器上跑过完整两轮，输出可以逐字对。

### 临时路线

```bash
uv pip install ruff
```
```
Resolved 1 package in 1.48s
Installed 1 package in 6ms
 + ruff==0.16.6
```
```bash
uv run python -c "import ruff; print('装上了')"
```
```
装上了
```

刚才我在你机器上又跑了一遍这句，确实打印「装上了」——`ruff` 的 wheel 里**是有 Python 包的**。
所以如果你在这一步看到 import 成功，**那是预期的**，不是命令敲错了。
（之前我在作业里写过一句「ruff 没有 Python 顶层模块」，那是错的，已改掉。）

```bash
uv sync
```
```
Resolved 109 packages in 3ms
Uninstalled 1 package in 1ms
 - ruff==0.16.6
```

`Resolved` 还是 **109**——`uv sync` 没有把 ruff 算进图里，因为它压根不认它。
它只认 lock，而 lock 里没有。

### 正式路线

```bash
uv add --dev ruff
```
```
Resolved 110 packages in 3.43s      ← 数字变了，这才是关键
Downloading ruff (9.4MiB)
 Downloaded ruff
Prepared 1 package in 3.79s
Installed 1 package in 4ms
 + ruff==0.16.6
```
```bash
uv sync
```
```
Resolved 110 packages in 3ms
Checked 107 packages in 3ms         ← Checked，不是 Uninstalled
```

**两条路线唯一的技术差别：`Resolved` 有没有从 109 变成 110。**
`uv pip install` 不改图，`uv add` 重画图并把结果写进 lock。

三层各留一处痕迹（`grep` 出来的真实行号）：

```
pyproject.toml:22:    "ruff>=0.16.6",
requirements.txt:278:ruff==0.16.6
uv.lock: name = "ruff" 出现 3 次
```

`.venv` 从 **372M → 394M**，`uv pip freeze` 从 **106 → 107**。

### 2C 那一步你大概率会漏

`requirements.txt` 里**没有** ruff——除非你专门跑过一次 `uv export`。
`uv add` 改 `pyproject.toml` 和 `uv.lock`，**不碰 `requirements.txt`**。

`check.py` 第 3 项就是专门盯这一步的。我实测过这个状态：

```
✓ 1. 你自己声明的 dev 包
✓ 2. 它在 uv.lock 里
✗ 3. 它已导出到 requirements.txt —— ['ruff'] 没进 requirements.txt —— 忘了重新导出
✓ 4. uv sync 不删它
✓ 5. 卫生
```

旧版 `check.py` 会在检查时顺手替你重导出一次，于是这项永远绿——
**那是替你把遗漏掩盖了**。现在的版本只查不改。

### 如果你 `uv add` 之后 pytest 变红了

**不要立刻回滚。** 那是你今天第一次真正撞上「`pyproject.toml` 写的是范围」这件事：

```bash
git diff uv.lock | grep '^\+name\|^\+version'
```

找出哪个包的版本被 `uv add` 触发的重解析改动了。范围（`>=`）意味着
「允许挑更新的满足者」，重新解析时它就真的挑了。

这正是第 4 题 B 的现场版。**撞上了比没撞上学到更多。**

## 第 3 题 · 数字相同，环境不同

**逐条判 case（他是 `win32` + `AMD64` + CPython）：**

| 包 | marker | Mac | Windows |
|---|---|---|---|
| `colorama` | `os_name=='nt' or sys_platform=='win32'` | ✗ | **✓** |
| `hf-xet` | `platform_machine` 在 `AMD64/aarch64/amd64/arm64/x86_64` 里 | ✓ | ✓ |
| `httpcore2` | `sys_platform != 'emscripten'` | ✓ | ✓ |
| `httpx2-jsfetch` | `sys_platform == 'emscripten'` | ✗ | ✗ |
| `truststore` | `sys_platform != 'emscripten'` | ✓ | ✓ |
| `uvloop` | `!= PyPy and != cygwin and != win32` | **✓** | ✗ |

**所以：他有你没有的是 `colorama`；你有他没有的是 `uvloop`。两边包数相同（106，或你做完第 2 题后的 107）。**

`108 − 2 = 106`，只是各自减掉了不同的一对。

### 第 1 问：哪一步才是证据

**第三步。** 第二步只证明了一件事：**摘要相同**。而摘要相同从来不能证明内容相同——
两个不同长度的字符串可以有相同的 MD5 前几位，两个不同的集合可以有相同的基数。

第三步把**内容**摊开了：两个集合，107 对 107，但 `uvloop` 和 `colorama` 一边一个。

一句话可以带走：

> **比数字只能证明「没看出差别」，比集合才能证明「没差别」。**

这也是为什么你前面习惯的「我们对一下装了几个包」根本不是一个验收动作——
它只能排除最粗糙的错误。

### 第 2 问：方向

**左列（顶格那行）= `uvloop`，你独有。右列（缩进那行）= `colorama`，他独有。**

`comm` 的输出很容易看反。判据不是记忆，是**回到第二步那份文件**：
`/tmp/win.txt` 是他那份，`colorama` 在里面而 `uv pip freeze` 里没有，
所以它是他独有。不确定就 `grep colorama /tmp/win.txt` 再看一眼——
**能从文件查出来的东西，不要靠记。**

### 第 3 问：为什么三道防线全都拦不住它

| 防线 | 为什么漏 |
|---|---|
| `uv sync` 不报错 | 它按 lock 忠实执行，marker 不满足是**预期行为**，不是错误 |
| `pytest` 全绿 | 没测试断言过「我这台机器上应该装到 `uvloop`」 |
| 比对包数量 | 107 == 107。**数量是摘要，摘要会骗人** |

三条合起来是同一件事：**它们比对的都是摘要，没一个在看内容。**
`uv sync` 看的是 lock 里每条 marker 算不算得开（这是内容），
但它**不会把结果报给你看**；pytest 和数个数都是摘要。

所以真验收得自己写一条：把两台机器的清单 diff 一下——就是你第三步刚做的那件事。

### `uvloop` 到底是什么

**今天不需要知道。** 它现在对你就是一个符号，作用是让两个集合不相等。
后面讲到并发时它会回来，到时你会直接看到「有它和没它跑同一份代码差多少」，
而不是今天听一段结论。

### 这条命令在生产里还有个正经用途

`--python-platform` 不只用来对同事。Docker **构建机是 x86、运行机是 ARM**
（或反过来）时，lock 必须对两个平台都解析得开，否则 CI 全绿、上线即挂。
今天这一条就是你以后处理那种事故的原型。

## 第 4 题 · 三个事故

判断格式统一是：**先定位到哪一层，再用一条命令证实**。
只说「哪一层」不说「怎么证实」，等于还在猜。

### 事故 A：声明里有，import 却失败

**先查第 3 层。** 声明是对的，所以第 1 层没问题——
一个「文件里明明写着」的东西，问题一定出在它下游的某一环。

```bash
uv sync                       # 最可能：环境没跟着 lock 更新
grep -c 'name = "chromadb"' uv.lock   # 如果是 0，问题在第 2 层（lock 没重算）
which python                  # 如果是 /usr/bin/python 而不是 .venv/...，你在用系统解释器
```

**最后那条最容易被忽略。** 你写 `python foo.py` 而不是 `uv run python foo.py` 时，
用的可能根本不是这个 `.venv`。表现和「包没装」一模一样，
但装一百遍都没用——**这是第 0 层：你连环境都没选对。**

### 事故 B：我没碰过的包自己变了

**先查第 1 层的语义**：`pyproject.toml` 里写的是**范围**（`fastapi>=0.141.1`），不是版本。

`uv add langchain` 会重画整张依赖图。重画时，所有「只有下界约束」的包
都可以合法地挑一个更新的满足者——**它没违反任何声明，它只是行使了声明给它的自由。**

```bash
git diff uv.lock        # 直接看谁从什么版本变到什么版本
```

修法有两种，选一种并知道为什么：

- **提交 lock**。`uv sync` 会严格按 lock 装，只要 lock 不变，环境就不变。
  （前提是你没跑 `uv add` / `uv lock`）
- **CI 里用 `uv sync --frozen`**：lock 和 pyproject 对不上就直接报错，
  把「悄悄重解析」这条路堵死。

对照你熟的东西：这就是为什么前端 CI 用 `npm ci` 而不是 `npm install`。**同一个理由。**

### 事故 C：改了 `requirements.txt`，什么都没发生

答案在教案第七节排查表的第四行，但你今天应该亲手撞一次：

```
1. uv sync 报错了没有？    —— 没有。它压根没读那个文件。
2. freeze 还是 106 吗？     —— 是（或你第 2 题之后的那个数）。环境一动没动。
3. 你加的那行还在吗？       —— 在。grep 得到。
4. 少了什么？              —— 少了一个「会去读 requirements.txt 的人」。
```

**第 4 问才是重点**：`uv sync` 只读 `pyproject.toml` 和 `uv.lock`。
`requirements.txt` 对它而言就是**一个恰好叫这个名字的文本文件**，
和 `README.md` 地位相同。

所以你那行：不报错（没人解析它）、不生效（环境没变）、**还留在文件里**（`grep` 得到）。
这三件事合起来制造了一个完美的错觉：「我改了，而且系统确认了（没报错）」。

这是本仓库最容易白白浪费半小时的坑。恢复一条命令：

```bash
uv export --no-hashes --all-groups -o requirements.txt
grep this-package requirements.txt    # 应该无输出，grep 退出码 1
```

**做完这步再跑 `check.py`**——第 5 项会替你盯着残留。

## 第 5 题 · 参考措辞

> 1. 不是 uv 有 bug，是 `uv sync` **删的**，而且这是它的正确行为。
> 2. 你 `pip install` 的东西只躺在 `.venv` 里，等于手改 `node_modules`——
>    它没进 `package-lock.json`（这里是 `uv.lock`）。
> 3. `uv sync` 的语义是「让 `.venv` 精确等于 lock」，
>    查无此包的就是多余物，删。这活对应你的 `npm ci`，不是 `npm install`。
> 4. 你没敲命令，但 IDE 打开项目时 uv 插件会**自动 sync**——这就是「我没动任何东西」的真相。
> 5. 改成 `uv add <包>` 就永久解决：它同时写 `pyproject.toml` 和 `uv.lock`，sync 就认它了。

**为什么第 4 句不能省**：他原话里的「我没动过任何东西」是他真正困惑的点。
一句只解释机制、不回答他困惑的话，等于没解释。
（**这才是费曼：讲清楚，意思是让对方不用再问第二个问题。**）

如果你的版本没提「IDE 自动 sync」这条触发路径，那第 4 句就是空的——
回去把教案第二节末尾那张三行小表再读一遍。

## 今天的三件可带走的东西

1. **`uv pip install` 是临时的，`uv add` 才是正式的。**
   判据只看一件事：`uv sync` 那行输出是 `Checked` 还是 `Uninstalled`。
2. **凡是代码里 `import` 过的，必须出现在 `pyproject.toml` 里。**
   「现在能跑」和「明天还在」是两件无关的事——传递依赖是借的。
3. **环境是否一致，不靠数个数。** 106 对 106（你现在的 107 对 107）可以是两套环境。
   要比对，用 `uv pip compile --python-platform` 生成另一侧的清单来 diff——你今天已经跑过了。

## 今天真正长在身上的是一个动作

不是那三个数字，是一条可重复的流程：

> **拿到两份清单 → 比集合而不是比个数 → 把差异归到某一层的命令上。**

以后任何「我这明明好的啊」的场合，你都有条件把这句话变成可查的东西，
而不是两个人对着各自的终端发愣。
