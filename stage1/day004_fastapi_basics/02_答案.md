## 第 1 题 · 九条，其中三条是坑

### 判据（一句话一条）

| # | 打的 | 回什么 | 一句话理由 |
|---|---|---|---|
| 1 | `GET /orders/recent` | `{"handler":"recent_orders"}` [200] | 字面量那条**先登记**，它先命中就到它 |
| 2 | `GET /orders/5` | `{"handler":"get_order","oid":5}` [200] | 第 1 条只匹配 `recent` 这一个词，`5` 不符，往下走 |
| 3 | `GET /orders/abc` | 422 `int_parsing` `loc:["path","oid"]` | 命中第 2 条了，`"abc"` 转不成 `int` |
| 4 | `GET /users/3/orders/7` | `{"handler":"get_user_order","uid":3,"oid":7}` [200] | 两段都转成了 `int` |
| 5 | `GET /users/3/orders/x` | 422 `loc:["path","oid"]` `input:"x"` | **`uid` 已经转成功了，就不出现在报错里** |
| 6 | `GET /orders/5?oid=9` | `{"handler":"get_order","oid":5}` [200] | **`?oid=9` 被整个丢掉**，回显里是 5 |
| 7 | `PUT /orders/5` | `{"detail":"Method Not Allowed"}` [405] | 路径有、方法没有 |
| 8 | `GET /orders` | `{"detail":"Method Not Allowed"}` [405] | **不是 404**：`/orders` 这个路径存在，只是只登记了 `post` |
| 9 | `POST /orders` + JSON | `{"handler":"create_order","got":{"item":"pen"}}` [200] | `payload: dict` 原样收到 |

真跑的九行，逐字（和作业里那份是同一次跑出来的）：

```
{"handler":"recent_orders"} [200]
{"handler":"get_order","oid":5} [200]
{"detail":[{"type":"int_parsing","loc":["path","oid"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"abc"}]} [422]
{"handler":"get_user_order","uid":3,"oid":7} [200]
{"detail":[{"type":"int_parsing","loc":["path","oid"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"x"}]} [422]
{"handler":"get_order","oid":5} [200]
{"detail":"Method Not Allowed"} [405]
{"detail":"Method Not Allowed"} [405]
{"handler":"create_order","got":{"item":"pen"}} [200]
```

### 三条问答的答案

**1. 第 6 条：`?oid=9` 被静默忽略了，回显里 `oid` 是 5。**
路径参数的名字和查询参数的名字**撞了也不打架**——FastAPI 先看你的函数签名：
`def get_order(oid: int)` 里的 `oid` 因为在**路径模板 `{oid}`** 里出现过，就被当成路径参数，
剩下的 `?oid=9` 是一个「函数签名里没有对应物、又不在路径里」的东西，跟第三节那个 `?q=x` 一样直接扔了。

**这就是这一题最想让你撞的一条**：以后你把查询参数名和路径参数名写重了，
**不会有任何警告**，你只会得到一个「过滤好像没生效」的 200。

**2. 第 5 条只报 `oid` 不报 `uid`：报错只说第一个失败的地方。**
`uid=3` 已经转换成功，FastAPI 没有理由提它。
读 422 的正确姿势是**只看 `loc` 和 `input`**，不要以为「回显里没提的字段就是它也想说的」。

**3. 三个状态码各说什么：**

| | 它在说 | 谁判的 |
|---|---|---|
| 404 | 这个**路径**我压根没登记过 | 路由表走完没匹配 |
| 405 | 路径我**有**，但你用的**方法**我没登记 | 匹配到了 path，方法对不上 |
| 422 | 路由我进了，但**你给的值不符合我的函数签名** | 你的类型注解（`int`）拒了它 |

第 8 条（`GET /orders` → 405）是三个里最容易被记错的：**「405 比 404 更精确」**，
它证明这个路径确实存在于你的服务里，只是没为 `GET` 开门。

### 参考实现

```bash
from fastapi import FastAPI

app = FastAPI()

checks = []


@app.get("/health")
def health():

@app.get("/ping")
def ping():
    checks.append(1)
```

```bash
uv run uvicorn hw02_health:app --port 8732
```

真跑（作业里那八条，同一次）：

```
{"status":"ok","uptime_checks":0} [200]
{"status":"ok","uptime_checks":1} [200]
{"status":"ok","uptime_checks":2} [200]
{"status":"ok","uptime_checks":3} [200]
{"status":"ok","uptime_checks":3} [200]
{"you_sent":"hello","type":"str"} [200]
{"you_sent":"42","type":"str"} [200]
{"you_sent":"2.5","type":"str"} [200]
```

### 两个必答

**1. 第 5 条 `/health` 回 3，因为它读的是同一个 list。**
`checks = []` 写在**模块顶层**：这个模块被 import 时执行一次，`checks` 就绑上了一个 list 对象。
`/health` 和 `/ping` 两个函数**共享它**——`/ping` 往里 `append`，`/health` 只是 `len`。
所以 `/health` 一次都没塞，却看见 3。

这和第八节 `items` 从 4 掉回 3 是**同一件事的两面**：
正着说「模块顶层的东西跨请求活着，所以能当计数器」，
反着说「热重载一次，模块重新 import，它又变回空 list，计数器归零」。

要是把 `checks = []` 缩进进函数里，它就变成**每次请求新建一个**，`/ping` 会永远回 1。

**2. 把 `word: str` 改成 `word: int`，那三条变成这样（真跑）：**

```
$ curl -s -w ' [%{http_code}]' http://127.0.0.1:8732/echo/hello
{"detail":[{"type":"int_parsing","loc":["path","word"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"hello"}]} [422]
$ curl -s -w ' [%{http_code}]' http://127.0.0.1:8732/echo/42
{"you_sent":42,"type":"int"} [200]
$ curl -s -w ' [%{http_code}]' http://127.0.0.1:8732/echo/2.5
{"detail":[{"type":"int_parsing","loc":["path","word"],"msg":"Input should be a valid integer, unable to parse string as an integer","input":"2.5"}]} [422]
```

**改一个字母级别的东西（`str` ↔ `int`），九条路由请求里三条的命运就翻面。**
注意 `42` 那一条：改成 `int` 之后回显是 `42`（JSON 数字，没有引号）、`type` 是 `int`；
原来是 `"42"`（字符串，带引号）、`type` 是 `str`。**引号的有无就是类型的证据。**

顺带一条容易看漏的：`/echo/2.5` 在 `str` 下是 **200**，在 `int` 下是 **422**。
第二节那六条边界里 `2.5` 是 422——同一个值，两种命运，**区别只在你的注解上**。

## 第 3 题 · 五行，两个 0.001、一个 1.70、一个 3.70、一个 2.00

### 判据：只有两种「睡法」

| 端点 | 睡法 | 睡的时候事件循环在干嘛 |
|---|---|---|
| `/a` | `await asyncio.sleep(2)` | **让出去了**，循环空着 |
| `/b` | 普通 `def` + `time.sleep(2)` | 函数根本不在循环里跑（被丢去工作线程），循环空着 |
| `/c` | 不等 | —— |
| `/d` | `async def` + `time.sleep(2)` | **按死了**，循环动不了 |

所以：`/a` 和 `/b` 是「不挡别人」的两条不同路，`/d` 是那条挡人的。
**判据只有一句：睡的时候，事件循环手上还有没有活。**

| # | 后台睡 | 打 | 实测 | 怎么算出来的 |
|---|---|---|---|---|
| 1 | `/a` | `/c` | 0.001265s | 循环空着，`/c` 立刻进 |
| 2 | `/b` | `/c` | 0.001232s | `time.sleep` 在工作线程里，循环空着 |
| 3 | `/d` | `/c` | 1.699832s | 循环被按死到 t=2.0，`/c` 从 t=0.3 起等 → **2.0 − 0.3** |
| 4 | `/d` | `/a` | 3.699923s | 先等 1.7 才能开始，再自己睡 2.0 → **1.7 + 2.0** |
| 5 | `/a` | `/b` | 2.004814s | 没被挡，**它自己那 2.0 秒**（工作线程里） |

### 五问的答案

**1. 不是同一个原因。**
A 组（`/quick` 在 `/sleepy` 睡觉时 0.001 秒）靠的是**框架把普通 `def` 丢进工作线程**；
第 1 行的 `/a` 靠的是 **`await` 本身就是让出**。
两者都让事件循环空着，但一个是「你这个函数压根没在循环里跑」，一个是「我在循环里，但我主动撒手」。
昨天的判据在这里原样生效：**`await` 是「我等，你们先走」**。

**2. 少的 0.3 秒 = 后台那条 curl 先跑了 0.3 秒。**
`/d` 的 2 秒是从**它自己被服务端接进去**那一刻起算的，`/c` 是在 0.3 秒后才到的，
所以 `/c` 只需要再等 1.7。第五节 B 组那个 1.698 是同一个算式。
**如果你没写 `sleep 0.3`，这一格就会变成 2.00**——那是两条同时到，不是 `/c` 变慢了。

**3. 3.70 = 1.7（排队等循环空出来）+ 2.0（`/a` 自己那 `await asyncio.sleep(2)`）。**
这一行是整张表里唯一能证明「`/a` 确实被挡了」的数字：
如果没被挡，它应该是 2.00。

**4. `/b` 是自己睡的，不是被挡的。**
判据是**它在等的时候别人进不进得来**，不是它自己几秒。
`/a` 睡的时候循环是空的，`/b` 从 t=0.3 起就能被接进去丢到工作线程，那 2.004 是它自己的 `time.sleep`。
**要区分「被挡」和「自己慢」，永远看同一时刻那个 0 秒端点（`/c`）是几秒**——
这就是为什么表里第 1、2、3 行都打 `/c`：它是这个服务的**探针**。

**5. ruff 只指 `/d`（也就是函数 `d`），不指 `/b`。** 真跑：

```bash
uv run ruff check hw03_blocking_table.py
```

```
ASYNC251 Async functions should not call `time.sleep`
  --> hw03_blocking_table.py:28:5
   |
26 | @app.get("/d")
27 | async def d():
28 |     time.sleep(2)
   |     ^^^^^^^^^^
29 |     return {"who": "d", "kind": "async def + time.sleep"}
   |

Found 1 error.
```

因为 `/b` 是普通 `def`，它整个函数根本不在事件循环里跑（被丢去工作线程），
`time.sleep` 卡的是一个线程不是循环——**不是错**。`/d` 才是。
**linter 的这条判断，和那张表里只有第 3、4 行变慢完全一致。**
两套完全不同的工具（计时和 lint）指同一条规则，这条规则就不是背出来的了。

**今天最该带走的一条**：`async def` 不是「会变快」，`async def` 是
**「我承诺不霸占循环，除非你写了不让出的东西」**。一个 `time.sleep` 就把它降级成 `/d`。

## 第 4 题 · `hw04_library.py` 参考实现

```bash
cd stage1/day004_fastapi_basics
cat > code/python/hw04_library.py <<'PY'
from fastapi import FastAPI

app = FastAPI()

books = [
    {"id": 1, "title": "Dune", "year": 1965},
    {"id": 2, "title": "Neuromancer", "year": 1984},
    {"id": 3, "title": "Snow Crash", "year": 1992},
]


@app.get("/")
def root():
    return {"service": "hw04_library", "total": len(books)}


@app.get("/books")
def list_books(year_from: int = 0):
    found = []
    for it in books:
        if it["year"] >= year_from:
            found.append(it)
    return {"count": len(found), "books": found}


@app.get("/books/{bid}")
def read_book(bid: int):
    for it in books:
        if it["id"] == bid:
            return it
    return {"error": "没有这本书", "bid": bid}


@app.post("/books")
def create_book(payload: dict):
    books.append(payload)
    return {"total": len(books)}
PY
```

### 三条问答的答案

**1. 差在 `for` 走到哪儿就停了。**
`/books/1` 第一轮 `it` 是 `{"id": 1, ...}`，`it["id"] == 1` 成立，**`return it` 当场离开函数**，
那条缺 `id` 的第 4 项根本没被碰到。
`/books/99` 要**走完整个 list** 才知道没有——于是它必须逐项读 `it["id"]`，
读到第 4 项那个没有 `id` 的 dict，`KeyError`。
**「找不到」这条路，是这条 for 里唯一会遍历到最后一项的路。** 所以只有它撞得上脏数据。

**2. `KeyError: 'id'`，就是我写的 `if it["id"] == bid:` 那一行。**
终端 A 里那一段的尾巴（真跑，`.venv` 那三十帧我删了，留的是最后两帧和你该看的那三行）：

```
  File ".../fastapi/routing.py", line 354, in run_endpoint_function
    return await run_in_threadpool(dependant.call, **values)
  File "/Users/admin/Desktop/DELECTED/AI-agent/stage1/day004_fastapi_basics/code/python/hw04_library.py", line 29, in read_book
    if it["id"] == bid:
       ~~^^^^^^
KeyError: 'id'
```

**看栈的规矩和第五节一样：从下往上第一个不含 `.venv` 的行，就是你的锅。**

**3. 因为 `list_books` 读的是 `year`，而那条脏数据**有** `year`。**
我 POST 的是 `{"title": "Old Mans War", "year": 2005}`——缺 `id`、不缺 `year`。
要求 4 那个 `if` 判的是 `it["year"]`，要求 5 那个 `if` 判的是 `it["id"]`：
**同一条脏数据，只毒得死读它的那一个端点。**

这一条可以自己验完（真跑）：再 POST 一条缺 `year` 的——

```
$ curl -s -w ' [%{http_code}]' -X POST -H 'content-type: application/json' -d '{"id":9,"title":"NoYear"}' http://127.0.0.1:8734/books
{"total":5} [200]
$ curl -s -w ' [%{http_code}]' 'http://127.0.0.1:8734/books?year_from=1984'
Internal Server Error [500]
```

这回栈里是 `line 21, in list_books` / `KeyError: 'year'`。
**先崩哪个端点，取决于你 POST 的那条缺哪个键。**

### 这一题最可能被写错的四处

1. **`GET /books/{bid}` 里 `return it` 写成了 `return {"book": it}`** → 第 5 条对不上。
   要求 5 说的是「返回那一条本身」。
2. **用 `if bid in ...` 或 `books.get(...)` 想绕开崩** → 不算对。这两个东西这四天没教过，
   而且它们恰好就是明天 Day 5 要正式请回来的那位。今天只许 `for` + `if` + `return`。
3. **把 `year_from: int = 0` 写成 `year_from: int`** → 第 2 条 `GET /books` 会回 422 `missing`。
   第三节④你自己撞过一模一样的。
4. **`POST` 用 `curl -d` 但没带 `-H 'content-type: application/json'`** → 422 `dict_type`。
   第六节那四种坏法的第一种。
