# Day 4 · 参考答案

> 今天全部现象可以用一句话概括：**FastAPI 在启动时读你的函数签名和注册顺序，
> 把「谁匹配、参数必填吗、类型转什么」全部定死了**，请求到来时只是查表。

---

## 第 1 题 · 6 个请求

```
/items/5         200 {"item_id": 5, "q": null}
/items/5?q=x     200 {"item_id": 5, "q": "x"}
/items/abc       422 {"detail": [{"type": "int_parsing", "loc": ["path", "item_id"], ...}]}
/items           404 {"detail": "Not Found"}
/good/me         200 {"got": "me"}
/bad/me          422 {"detail": [{"type": "int_parsing", "loc": ["path", "bid"], "input": "me"}]}
```

第 5 与第 6 的差别只在于**两行定义的先后**：

- `/good/me` 注册在 `/good/{gid}` **之前** → 请求先命中字面量路由 → 200
- `/bad/me` 注册在 `/bad/{bid}` **之后** → `/bad/{bid}` 先命中，`bid = "me"` → 转 int 失败 → 422

注意第 6 个的 `loc` 是 `["path", "bid"]` 而**不是** `["path", "me"]` 之类——
它明确告诉你「出错的是 `bad_id` 那个函数的 `bid` 参数」，
这就是你能反推出「我被上面那条路由截住了」的线索。

**`/openapi.json` 里两条路由都在**（实测 `['/bad/me', '/bad/{bid}', ...]`）。
所以「文档里有」不等于「能命中」——文档是**注册表**，不是**匹配顺序表**。

## 第 2 题 · 参考实现

```python
from fastapi import FastAPI
from fastapi.testclient import TestClient

app = FastAPI()


@app.get("/notes/mine")                 # 必须注册在 {note_id} 之前
async def my_notes():
    return {"note": "mine"}


@app.get("/notes/{note_id}")
async def read_note(note_id: int, q: str | None = None):
    return {"note_id": note_id, "q": q}


@app.get("/search")
async def search(keyword: str):         # 没有默认值 = 必填
    return {"keyword": keyword}


if __name__ == "__main__":
    client = TestClient(app)
    for url in ("/notes/mine", "/notes/7?q=hello", "/notes/abc",
                "/search?keyword=x", "/search", "/nope"):
        print(f"{url:18} {client.get(url).status_code}")
```

三处不能改的地方：

1. `my_notes` 在 `read_note` **上面**——顺序就是今天的核心
2. `note_id: int` 的注解不能省——省了就变成字符串 `"7"`，`check.py` 第 2 项会红
3. `keyword: str` **不能有默认值**——给了就变可选，第 4 项会红

`if __name__ == "__main__":` 这个守卫是必要的：`check.py` 会 import 你的模块，
没有守卫的话那些 print 会在 import 时跑一遍，污染 check.py 的输出。

## 第 3 题 · 422 的四个字段

```json
{
  "detail": [
    {
      "type": "int_parsing",
      "loc": ["path", "note_id"],
      "msg": "Input should be a valid integer, unable to parse string as an integer",
      "input": "abc"
    }
  ]
}
```

| 字段 | 作用 | 给谁看 |
|---|---|---|
| `type` | 机器可判的错误码（`int_parsing` / `missing` / `value_error`…） | **程序**：前端按它分流 |
| `loc` | 出错位置，`[来源, 字段名]`，来源是 `path` / `query` / `body` / `header` | 人 + 程序 |
| `msg` | 人类可读描述 | **人**：可以直接展示给用户 |
| `input` | 收到的**原始值**，转换失败前的样子 | 人：知道到底传了什么 |

`detail` 是**列表**，因为一个请求可能同时有多个错误——
比如 `/search` 既缺 `keyword` 又传了个类型错的 `note_id`，会返回两项。
前端应该遍历整个列表，而不是只取 `detail[0]`。

缺必填参数时的形状：

```json
{"type": "missing", "loc": ["query", "keyword"], "msg": "Field required", "input": null}
```

`input` 是 `null`（因为压根没传），`type` 是 `missing`。
**`type` 区分「缺了」和「错了」，这是前端做表单提示时最需要的信息。**

## 第 4 题 · 为什么是 422 不是 404

因为**路由匹配成功了**。

匹配阶段只看路径形状：`/notes/mine` 符合 `/notes/{note_id}` 的模式（一段 + 一段），
于是 FastAPI 认定「就是这个处理函数」，把 `"mine"` 作为 `note_id` 传进去。
接下来才是**参数校验阶段**，`"mine"` 转 int 失败 → 422。

404 只在**没有任何路由的形状能匹配**时出现，比如 `/notes`（少一段）或 `/nope`。

所以这两个状态码把问题分成了两段：

```
请求进来
  ├─ 形状能匹配某条路由吗？── 否 ──→ 404（查：路径拼写、注册顺序、有没有少一段）
  └─ 是 → 参数能按注解转换/校验吗？── 否 ──→ 422（查：传的值、注解写错了没）
```

**顺序 bug 之所以难查，正是因为它落在第二段**：你以为是 404 类问题（路由没生效），
实际收到 422（路由生效了，是错的那条）。看到 422 就该往「参数」方向想，
而这里真正的原因是「命中了错误的处理函数」——`loc` 里的字段名 `note_id` 是唯一线索。

## 第 5 题 · 费曼任务参考措辞

> 1. **404 说明没有任何路由的形状匹配上**，先查路径拼写，
>    再查路由注册顺序（字面量路径被通配路径截住时也会表现异常）。
> 2. **422 说明路由已经命中了**，是参数没过校验，
>    所以别怀疑路由，去看传进来的值和函数签名的类型注解。
> 3. 判据很硬：404 的 `detail` 是**字符串** `"Not Found"`，
>    422 的 `detail` 是**列表**，每项带 `loc`（哪来的、哪个字段）和 `type`（缺了还是错了）。

反问「422 的 detail 怎么用」时的答案：
遍历整个列表（可能有多个错误），用 `loc` 定位字段、`type` 判断错误种类、`msg` 直接展示给用户。

## 第 6 题 · 四个框架的匹配策略

| 框架 | 匹配策略 | 定义顺序重要吗 |
|---|---|---|
| FastAPI | 注册顺序，第一条命中即赢 | **重要** |
| Express | 注册顺序，`app.get` 依次匹配，靠 `next()` 决定是否继续 | **重要** |
| Next.js App Router | 文件系统路由，静态段优先于动态段（`about` > `[slug]`） | 不重要，文件位置决定 |
| React Router v6 | 给所有路由打分（rank），精确度高的赢 | 不重要 |

**为什么后端不做「精确优先」**：因为它要**一遍扫完就决定**，不做全局排序。
Express/FastAPI 的路由表是有序列表，命中即返回，这是 O(n) 线性扫描的最优形态。
前端路由能做打分，是因为路由数量少（几十个）且可以在构建期预计算；
后端可能有几百条路由，还要支持中间件顺序，就只能用注册顺序这个简单契约。

**你从前端带来的直觉需要改一处**：在 React Router / Next.js 里，
「我把 `/users/me` 写在 `/users/:id` 后面也没事」是对的；
在 FastAPI / Express 里，这**一定会出 bug**，而且出的是 422 不是 404，很难联想到顺序。

**纪律（写进你的肌肉记忆）**：同一个前缀下，**字面量路径全部写在通配路径之前**。

（说明：FastAPI 与 422/404 的行为我本机实测过；Express / Next.js / React Router
三条来自各框架文档与通行实现，我没在本机跑——你手边有前端项目的话值得自己验一次。）
