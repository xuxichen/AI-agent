# Day 4 · 这个 URL 到底会命中哪个路由

> 计划里这一天是「FastAPI 基础：路由与端点、请求参数与路径参数、Pydantic 模型入门、JSON 响应」。

## 今日问题

本机实测，同一个 app，两个 URL：

```python
@app.get("/bad/{bid}")
async def bad_id(bid: int): return {"got": bid}

@app.get("/bad/me")
async def bad_me():        return {"got": "me"}
```

```
GET /bad/me   →  422  {"detail":[{"type":"int_parsing","loc":["path","bid"],
                    "msg":"Input should be a valid integer...","input":"me"}]}
```

`/bad/me` 这个路由**明明定义了**，`/openapi.json` 里也能看到它，
但请求压根没走到 `bad_me()`——它被上面的 `/bad/{bid}` 截住了，
然后因为 `"me"` 转不成 `int` 而报 422。

**为什么？以及：404 和 422 分别告诉你什么不同的事？**

---

## 学习目的

两条：

1. **FastAPI 按注册顺序匹配路由，第一条命中的就赢**——它不会因为「另一条更精确」而回头。
2. **404 和 422 是两种完全不同的诊断信号**，会看这两个就能省掉大量瞎猜。

---

## 学习内容

### 一、注册顺序优先（不是精确优先）

把上面两条调换顺序，`/bad/me` 立刻返回 200。

这一点和 Express 一致（`app.get` 也是注册顺序），
但和你更熟的**前端路由相反**：

| 框架 | 匹配策略 |
|---|---|
| Express / FastAPI | **注册顺序**优先，第一条命中即赢 |
| Next.js App Router | 文件系统路由，**静态段优先于动态段** |
| React Router v6 | 给路由**打分**，精确度高的赢，与定义顺序无关 |

（这三条是各框架文档里的行为，我没在本机跑 Express/Next 验证——但 FastAPI 这条是实测的。）

所以你在 React Router 里养成的习惯「顺序无所谓，写清楚就行」在 FastAPI 里会直接坑你。
**纪律：所有字面量路径写在同前缀的通配路径之前。**

### 二、类型注解就是校验器

你不需要写任何校验代码：

```python
@app.get("/notes/{note_id}")
async def read(note_id: int, q: str | None = None):
    return {"note_id": note_id, "q": q}
```

实测四种输入：

| 请求 | 状态码 | 响应体 |
|---|---|---|
| `/notes/5` | 200 | `{"note_id": 5, "q": null}` |
| `/notes/5?q=x` | 200 | `{"note_id": 5, "q": "x"}` |
| `/notes/abc` | 422 | `{"detail":[{"type":"int_parsing","loc":["path","note_id"],...}]}` |
| `/notes` | 404 | `{"detail":"Not Found"}` |

注意 `note_id` 拿到的是 **int `5`**，不是字符串 `"5"`——FastAPI 按注解转换了。
JS 那边 `req.params.id` 永远是字符串，你得自己 `parseInt`。
**这是 FastAPI 相比 Express 最实在的一处省事。**

### 三、可选 vs 必填，取决于有没有默认值

```python
q: str | None = None      # 可选：不传就是 None
keyword: str              # 必填：不传直接 422
```

规则很硬：**有默认值 = 可选，没默认值 = 必填**。没有第三种写法。
这和 Day 2 那条「Python 在定义时就把东西确定了」是同一个味道——
FastAPI 在**启动时**读你的函数签名，就决定了这个参数必填还是可选，
不是等到请求来了才判断。

漏传必填参数的 422 长这样，`loc` 指向 `query` 而不是 `path`：

```json
{"detail":[{"type":"missing","loc":["query","keyword"],"msg":"Field required","input":null}]}
```

### 四、404 与 422：形状都不一样

这是今天最该记住的一条：

| | 404 | 422 |
|---|---|---|
| 含义 | **没有路由**匹配这个路径 | 路由匹配了，但**参数不合法** |
| `detail` 类型 | **字符串** `"Not Found"` | **列表**，每项一个错误 |
| 有 `loc` 吗 | 没有 | 有，`["path", ...]` 或 `["query", ...]` |
| 第一步查什么 | 路径拼写、路由注册顺序 | 传进来的值、类型注解 |

`detail` 一个是字符串一个是列表——**这个形状差异本身就能帮你秒判**。
写前端时你可以直接 `typeof detail === "string"` 分流。

## 费曼任务

向同事解释：**你收到一个 404 和一个 422，分别第一步查什么，为什么。**

不超过 3 句，必须包含「422 说明路由已经命中了」这层意思。写进 `01_作业.md` 第 5 题。

如果他反问「那 422 的 detail 怎么用」，你要能立刻答：
读 `loc` 定位是 path 还是 query 的哪个字段，读 `type` 知道是缺了还是类型错了。
