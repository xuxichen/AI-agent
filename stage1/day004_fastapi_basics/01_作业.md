## 第 1 题 · 先预测 6 个请求的结果

**做什么**：**不要运行任何代码**。先在下表的空列里填上你认为的状态码。

| # | 请求 | 你预测的状态码 |
|---|---|---|
| 1 | `GET /items/5` | |
| 2 | `GET /items/5?q=x` | |
| 3 | `GET /items/abc` | |
| 4 | `GET /items` | |
| 5 | `GET /good/me` | |
| 6 | `GET /bad/me` | |

对应的 app 是：

```python
@app.get("/items/{item_id}")
async def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}

@app.get("/good/me")
async def good_me(): return {"got": "me"}
@app.get("/good/{gid}")
async def good_id(gid: int): return {"got": gid}

@app.get("/bad/{bid}")
async def bad_id(bid: int): return {"got": bid}
@app.get("/bad/me")
async def bad_me(): return {"got": "me"}
```

填完再运行验证：

```bash
uv run python - <<'PY'
import json
from fastapi import FastAPI
from fastapi.testclient import TestClient

app = FastAPI()

@app.get("/items/{item_id}")
async def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}

@app.get("/good/me")
async def good_me(): return {"got": "me"}
@app.get("/good/{gid}")
async def good_id(gid: int): return {"got": gid}

@app.get("/bad/{bid}")
async def bad_id(bid: int): return {"got": bid}
@app.get("/bad/me")
async def bad_me(): return {"got": "me"}

c = TestClient(app)
for url in ["/items/5", "/items/5?q=x", "/items/abc", "/items", "/good/me", "/bad/me"]:
    r = c.get(url)
    print(f"{url:16} {r.status_code} {json.dumps(r.json(), ensure_ascii=False)}")
PY
```

**验收结果**（本机实测，一字不差）：

```
/items/5         200 {"item_id": 5, "q": null}
/items/5?q=x     200 {"item_id": 5, "q": "x"}
/items/abc       422 {"detail": [{"type": "int_parsing", "loc": ["path", "item_id"], "msg": "Input should be a valid integer, unable to parse string as an integer", "input": "abc"}]}
/items           404 {"detail": "Not Found"}
/good/me         200 {"got": "me"}
/bad/me          422 {"detail": [{"type": "int_parsing", "loc": ["path", "bid"], "msg": "Input should be a valid integer, unable to parse string as an integer", "input": "me"}]}
```

**过关标准：6 个里至少对 5 个，且第 5、6 两个必须全对。**

第 5 和第 6 的唯一差别是**两行定义的先后顺序**，结果一个是 200 一个是 422。
如果你预测这两个一样，说明你以为路由匹配是「精确优先」——那是 React Router 的规则，不是 FastAPI 的。

**验收结果**——填出这四个字段的含义：

| 字段 | 值 | 它告诉你什么 |
|---|---|---|
| `type` | `int_parsing` | |
| `loc` | `["path", "item_id"]` 或 `["path", "note_id"]` | |
| `msg` | `Input should be a valid integer...` | |

四格都填对的标准：你能说出 **`loc[0]` 区分 path 还是 query**、

## 第 5 题 · 费曼任务：3 句话讲清 404 与 422

**做什么**：同事问你「接口报错了，404 和 422 我分别先查什么」。不超过 3 句回答。

```

3.
```

**验收结果**——对照这 3 条：

1. 404 = **没有路由匹配**，查路径拼写和**路由注册顺序**
2. 422 = **路由已经命中了**，是参数不合法，查传进来的值和类型注解
3. 给出可操作的判据：404 的 `detail` 是**字符串**，422 的 `detail` 是**列表**且带 `loc`

**自测**：同事反问「那 422 的 detail 怎么用」，你要能不假思索答：
`loc` 定位是哪个字段、在 path 还是 query；`type` 判断是缺了（`missing`）还是类型错了（`int_parsing`）。

**验收结果**：

| 框架 | 匹配策略 | 顺序重要吗 |
|---|---|---|
| FastAPI | 注册顺序，第一条命中即赢 | **重要** |
| Express | 同上 | **重要** |
| Next.js App Router | 文件系统路由，静态段优先于动态段 | 不重要（文件位置决定） |
| React Router v6 | 路由打分，精确度高的赢 | 不重要 |

**这题的收获是最后一行结论**（写下来）：
你从前端带来的直觉是「顺序无所谓」，因为 React Router 和 Next.js 都替你做了精确度排序。
**后端这两个框架不替你做**，所以字面量路径必须写在通配路径前面。
