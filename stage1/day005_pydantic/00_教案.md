# Day 5 · 同一个 `tags: list = []`，三种命运

> 计划里这一天是「Pydantic 数据校验：BaseModel、Field 验证器、嵌套模型、与 FastAPI 集成」。
> 本日的主线是**承接 Day 2**：你在 Day 2 见过普通类和 `dataclass` 对可变默认值的两种态度，
> 今天看 Pydantic 的第三种——它能补上那张表。

---

## 今日问题

Day 2 你见过这两段：

```python
class Plain:
    tags = []          # 所有实例共享，静默出错

@dataclass
class DC:
    tags: list = []    # ValueError: mutable default <class 'list'> ...
```

现在第三段：

```python
from pydantic import BaseModel

class Note(BaseModel):
    tags: list[str] = []       # ← 一样的写法，不报错

a, b = Note(id=1), Note(id=2)
a.tags.append("x")
print(a.tags, b.tags)
```

本机实测输出：

```
['x'] []
```

**既不报错，也不共享。** Pydantic 做了什么？为什么它能做到而普通类不能？

---

## 学习目的

一句话：**Pydantic 模型不是「加了类型注解的类」，而是一台装在系统边界上的翻译机。**

它干两件事，一件在入口一件在出口：

| 方向 | 机制 | 作用 |
|---|---|---|
| 入口 | `BaseModel` 构造 / FastAPI 请求体 | 校验 + **转换**外部数据 |
| 出口 | `response_model` | **过滤**掉不该给出去的数据 |

学完你要能写出一组 `NoteIn` / `Note` / `NoteOut` 三件套，
并说清为什么需要三个而不是一个。

---

## 学习内容

### 一、三种可变默认值的待遇（补完 Day 2 那张表）

| 写法 | `tags = []` 会怎样 | 为什么 |
|---|---|---|
| 普通 `class` | 所有实例**共享**，静默出错 | 类体只求值一次，产物挂在类上 |
| `@dataclass` | **定义时报错** `ValueError` | 它读注解，看到可变默认值直接拒绝 |
| `BaseModel` | 每个实例**独立**，正常用 | 它把默认值存起来，每次实例化时**深拷贝一份** |

Pydantic 的做法是：`[]` 仍然只在定义时创建一次（这点和 Python 语义没冲突），
但**每次实例化都拷贝一份**给新对象。所以你写 `a.tags.append("x")` 改的是 a 自己的副本。

这是三种设计哲学：

- 普通类：**不管你**（性能最好，坑最深）
- dataclass：**禁止你**（要求你写 `field(default_factory=list)`，显式表达「每次新建」）
- Pydantic：**替你办**（默认值自动深拷贝，你写起来最省事）

`dataclass` 的严格和 Pydantic 的体贴都不算错，区别在于**Pydantic 是为「不可信输入」设计的**，
它本来就假设每个实例的数据来自外部，天然要隔离。

### 二、一次报全部错误，不是遇错即停

```python
class Note(BaseModel):
    id: int
    title: str = Field(min_length=1, max_length=50)
    tags: list[str] = []

Note(id="abc", title="", tags="nope")
```

本机实测，**一次抛出 3 个错误**：

```
错误数: 3
  int_parsing ('id',) | Input should be a valid integer, unable to parse string as an integer
  string_too_short ('title',) | String should have at least 1 character
  list_type ('tags',) | Input should be a valid list
```

这一点对你写前端很关键：**用户可以一次性看到全部字段的问题**，
而不是「改一个、提交、再发现下一个」。JS 那边 zod / yup 的行为一致，
但手写的 `if (!x) throw` 校验通常是遇错即停的。

错误结构和 Day 4 的 422 是**同一套**（`type` / `loc` / `msg` / `input`）——
因为 FastAPI 的 422 就是把 `ValidationError.errors()` 塞进 `detail`。

### 三、它会转换，不只是拒绝

```python
n = Note(id="7", title="hi")
print(type(n.id), n.id)     # <class 'int'> 7
```

字符串 `"7"` 被转成了 int `7`。这就是 Day 4 路径参数为什么能拿到 int——
**FastAPI 不自己做类型转换，它把注解交给 Pydantic**。

但注意 `"abc"` 和 `"nope"` 都被拒了。**能转就转，转不了才报错**：

| 输入 | 结果 |
|---|---|
| `id="7"` | 转成 `7` ✓ |
| `id="abc"` | `int_parsing` ✗ |
| `tags="nope"` | `list_type` ✗（不会把字符串拆成字符列表） |

第三行值得记一下：字符串在 Python 里本来是可迭代的，
一个宽松的实现可能会把 `"nope"` 变成 `['n','o','p','e']`。Pydantic **不这么干**，
它要求 `list` 就得是真的 list（或 JSON 数组）。这类「不做过度聪明的猜测」是它可靠的原因。

### 四、`response_model` 是出口过滤器

这是今天最实用的一条。同一个返回值，两种路由声明：

```python
@app.get("/n", response_model=NoteOut)     # NoteOut 只有 id、title
async def with_filter():
    return Note(id=1, title="t", tags=["secret-tag"])

@app.get("/n2")                            # 没写 response_model
async def without_filter():
    return Note(id=1, title="t", tags=["secret-tag"])
```

本机实测：

```
有 response_model: {'id': 1, 'title': 't'}
无 response_model: {'id': 1, 'title': 't', 'tags': ['secret-tag']}
```

**函数返回的是同一个对象，出去的 JSON 不一样。** `response_model` 在响应序列化时
按目标模型**裁掉**了没声明的字段。

这就是为什么你需要三个模型而不是一个：

| 模型 | 用途 | 字段 |
|---|---|---|
| `NoteIn` | 请求体（入口） | 用户**能**提供的字段，不含 `id` |
| `Note` | 内部流转 | 全部字段，含 `id`、含内部数据 |
| `NoteOut` | 响应（出口） | 用户**该**看到的字段，不含密码/内部标记 |

真实事故长这样：数据库模型里有个 `password_hash` 字段，
你偷懒直接 `return db_user`，前端就收到了哈希值。
`response_model=UserOut` 是一行代码的防线，而且它**同时更新了 OpenAPI 文档**——
文档里也不会出现那个字段，前端同事压根不知道它存在。
