# Day 5 · 参考答案

> 今天全部规则可以用一条原则概括：**Pydantic 只在「目标类型的信息已经完整存在于输入里」时才转换，
> 否则拒绝。** 「无损」是唯一的判据。

---

## 第 1 题 · 三种待遇

```
普通类: ['x'] ['x']        ← 共享
dataclass: ['x'] []        ← 隔离（用了 default_factory）
Pydantic: ['x'] []         ← 隔离（直接写 [] 就行）
```

| 写法 | 对可变默认值的态度 | 机制 |
|---|---|---|
| 普通 `class` | **不管你** | 类体求值一次，产物挂在类对象上 |
| `@dataclass` | **禁止你** | 定义时检测到可变默认值就 `ValueError`，要求你显式写 `field(default_factory=list)` |
| `BaseModel` | **替你办** | 默认值仍只求值一次，但**每次实例化深拷贝一份** |

三种设计哲学对应三种使用场景：普通类追求性能与自由，`dataclass` 追求显式，
Pydantic 追求「面对不可信输入也不出错」。Pydantic 本来就假设数据来自外部，
所以隔离是它的默认前提，不需要你操心。

## 第 2 题 · 参考实现

```python
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field


class NoteIn(BaseModel):
    title: str = Field(min_length=1, max_length=50)
    tags: list[str] = []


class Note(BaseModel):
    id: int
    title: str
    tags: list[str] = []
    owner: str = "secret-owner"      # 内部字段，不该出去


class NoteOut(BaseModel):
    id: int
    title: str
    tags: list[str]


app = FastAPI()


@app.post("/notes", response_model=NoteOut)
async def create_note(payload: NoteIn):
    return Note(id=1, **payload.model_dump())


@app.post("/notes/leaky")            # 对照组：故意不写 response_model
async def create_note_leaky(payload: NoteIn):
    return Note(id=1, **payload.model_dump())


if __name__ == "__main__":
    client = TestClient(app)
    body = {"title": "hi", "tags": ["a"]}
    print("有 response_model:", client.post("/notes", json=body).json())
    print("无 response_model:", client.post("/notes/leaky", json=body).json())
```

**不要图省事写继承**：

```python
class NoteIn(Note):        # ✗ 会把 id 和 owner 全带进来
    pass

class NoteOut(Note):       # ✗ 同上，owner 过滤不掉
    pass
```

继承会让 `check.py` 第 2、3 项直接红。三个模型**各自独立声明字段**，
虽然啰嗦，但每个模型的字段集合是**一眼可审**的——这在安全边界上是值得的。
真要去重，用 `class NoteBase(BaseModel)` 放公共字段，再让三者各自继承并**只加自己该有的**。

## 第 3 题 · 一次报全部错误

```
错误数: 3
  int_parsing ('id',) | Input should be a valid integer...
  string_too_short ('title',) | String should have at least 1 character
  list_type ('tags',) | Input should be a valid list
```

`loc` 是元组，嵌套时变长。`tags=["a", 1]` 的实测结果：

```
嵌套 loc: string_type ('tags', 1)
```

`('tags', 1)` 精确指出「`tags` 列表的第 1 号元素（从 0 数）」。

**这里那个不对称值得停下来想**：

| 声明 | 输入 | 结果 |
|---|---|---|
| `xs: list[int]` | `"2"` | **转换**成 `2` ✓ |
| `tags: list[str]` | `1` | **拒绝** `string_type` ✗ |

原因见第 6 题的统一原则。

## 第 4 题 · 数据泄露三问

```
有 response_model: {'id': 1, 'title': 'hi', 'tags': ['a']}
无 response_model: {'id': 1, 'title': 'hi', 'tags': ['a'], 'owner': 'secret-owner'}
```

**1. 两个端点返回的是同一个 Note 对象吗？**

是。两个函数的函数体一字不差，都 `return Note(id=1, **payload.model_dump())`，
都构造了一个**含 `owner` 的完整 Note 对象**。差别不在你的代码里。

**2. 那为什么 JSON 不一样？过滤发生在哪一步？**

发生在 FastAPI **序列化响应的那一步**，在你的函数返回之后。

流程是这样的：

```
你的函数 return Note(...)          ← 完整对象，含 owner
        ↓
FastAPI 看路由签名上的 response_model=NoteOut
        ↓
用 NoteOut 当模具，把 Note 往里倒     ← 装不进去的字段留在外面
        ↓
序列化成 JSON                        ← 只有 id/title/tags
```

没写 `response_model` 时，第三步没有模具，FastAPI 直接把对象整个序列化。

**3. 换成 `password_hash` 会怎样？**

用户注册后调 `GET /users/me`，响应里带着密码哈希。攻击者拿到哈希就能离线爆破，
或者直接在别的站点撞库（很多人复用密码）。**而这个 bug 不会让任何测试失败**——
接口返回 200，数据"正确"，功能完全正常。

`response_model` 的价值就在于它是**声明式的防线**：写在签名上，
新加端点时漏写会在 code review 里很显眼（`response_model=` 缺席），
而"记得在返回前删掉敏感字段"这种命令式约定，总有人会忘。

**OpenAPI 文档的差别**：`/notes` 的 200 schema 指向 `NoteOut`，
`/notes/leaky` 指向 `Note`。所以前端同事在 `/docs` 里就能看到 `owner` 这个字段——
**泄露在文档阶段就暴露了**，这是第二道防线。

## 第 5 题 · 费曼任务参考措辞

> 1. `NoteIn` 是**入口校验**模型，只声明用户**能提供**的字段——
>    它没有 `id`，因为 id 必须由服务端生成。
> 2. 如果 `id` 出现在入口，用户就能在 PUT 时传一个别人的 id 直接覆盖他人记录；
>    `owner` 出现在入口更糟，他能把自己伪装成资源的主人。
> 3. `NoteOut` 是**出口过滤**模型，只声明用户**该看到**的字段——
>    `owner` / `password_hash` / 内部状态标记都留在 `Note` 里出不去。
> 4. 中间的 `Note` 是内部流转用的全量模型，三个各司其职；
>    而且 `response_model=NoteOut` 会同步收敛 OpenAPI 文档，
>    前端在 `/docs` 里压根看不到那些字段。

反问「一个模型加 `exclude` 不行吗」时的答案：
`exclude` 要在**每个端点、每次返回**都记得写，是命令式的、易漏的；
`response_model` 写在函数签名上，是声明式的、漏了一眼能看出来，
而且它同时决定了文档。防线要放在不容易忘的地方。

## 第 6 题 · 无损 vs 有损

```
{'n': '7', 'xs': [1, '2'], 'flag': 'yes'}   → OK  n=7 xs=[1, 2] flag=True
{'n': 'abc', ...}                           → ERR int_parsing @ ('n',)
{'n': 7.9, ...}                             → ERR int_from_float @ ('n',)
{'n': 7, 'xs': 'nope', ...}                 → ERR list_type @ ('xs',)
```

**统一原则**：Pydantic 只在「**目标类型的信息已经完整存在于输入里**」时转换。

| 输入 → 目标 | 判定 | 理由 |
|---|---|---|
| `"7"` → `int` | **接受** | 字符串里的信息就是一个完整的 7，转换**无损** |
| `"yes"` → `bool` | **接受** | 这是约定俗成的布尔字面量，无损 |
| `7.9` → `int` | **拒绝** | 转成 7 要**丢掉 0.9**，有损。Pydantic 不替你决定该舍还是该入 |
| `1` → `str` | **拒绝** | 数字和字符串是**不同的语义类别**，`1`（数量）和 `"1"`（编号）不是一回事 |
| `"abc"` → `int` | **拒绝** | 压根没有数字信息可提取 |
| `"nope"` → `list` | **拒绝** | 字符串虽然可迭代，但把它拆成字符列表是**猜测意图** |

**补一个边界**：`7.0` → `int` 是**接受**的（本机实测 `n=7`），因为它无损——
`7.0` 的小数部分是 0，丢掉它不损失任何信息。
所以判据不是「类型不同就拒绝」，而是**「转换会不会丢信息」**。

**为什么这个设计对你重要**：Day 9 之后你要用 Pydantic 定义大模型的请求/响应结构。
LLM 返回的 JSON 经常是脏的——该给数字的地方给了字符串、该给数组的地方给了单个对象。
Pydantic 的这套「无损才转」策略恰好合适：它会自动收拾 `"7"` 这种无害的脏数据，
但会在 `7.9` 这种**可能掩盖了真实错误**的地方拦住你，让你去看模型到底返回了什么。

如果它什么都转，你会拿到一堆静默失真的数据，然后在三天后某个奇怪的地方崩溃。
