## 今日问题

你在终端里敲这三行：

```python
def add(n, log=[]):
    log.append(n)
    return log

x = add(1)
y = add(2)
z = add(3)
print(x)
print(y)
print(z)
```

三行输出**一模一样**：

```
[1, 2, 3]
[1, 2, 3]
[1, 2, 3]
```

你明明调用了三次，传的是 1、2、3。为什么 `x`（第一次调用的返回值）里会有 2 和 3？

更怪的是——把这三行改成边调边印：

```python
print(add(1))
print(add(2))
print(add(3))
```

输出变成 `[1]` / `[1, 2]` / `[1, 2, 3]`，看着又"正常"了。**同一份代码，只是换了打印的位置，现象就不一样。**

今天要把这两件事一起讲透。透的标准是：你能一眼看出**你写过的 JavaScript 里为什么从来没有这个 bug**。

## 二、主现象：那个列表是**同一个**列表

先做一个能让你亲眼看到「是不是同一个对象」的实验。Python 判断两个名字指的是不是同一个东西，
用 `is`：

```python
x = add(1)
y = add(2)
z = add(3)
print(x)
print(y)
print(z)
print("x is y :", x is y)
```

我跑过的真实输出：

```
[1, 2, 3]
[1, 2, 3]
[1, 2, 3]
x is y : True
```

**`x is y` 是 `True`。** 它们不是"内容碰巧一样的两个列表"，是**同一个列表被印了三遍**。
`add` 每次 `return` 的都是同一个对象。

那这个对象存在哪里？存在函数自己身上。每个函数都有一个 `__defaults__`：

```python
print(add.__defaults__)
```

```
([1, 2, 3],)
```

**注意这个元组里的内容：它就是那个一直在长大的列表。**
`x`、`y`、`z`、`add.__defaults__[0]` —— 四个名字，一个对象。

### 为什么会这样

Python 里 `def` **是一条语句，不是一段声明**。

解释器从上往下执行，执行到 `def add(n, log=[]):` 这一行时，它做了三件事：

1. 建一个函数对象
2. **在这一刻，把 `[]` 这个空列表建出来，塞进函数的 `__defaults__` 里**
3. 把这个函数绑定到名字 `add`

第 2 步是关键。`[]` 只在 **`def` 那一行执行时求值一次**。
之后你调用 `add()` 一百次，Python 都从 `__defaults__` 里把**同一个**列表拿出来用。

你调用的时候它不再新建列表，它只是「取那个已经建好的」。

### 顺手解释第二个怪事

为什么改成边调边印就变成 `[1]` / `[1, 2]` / `[1, 2, 3]` 了？

因为打印的时机不同。先存后印时，三次调用**全都跑完**了才第一次打印，
于是三个名字（同一个对象）上都是最终状态。

再试一个更狠的，把它全写在一行：

```python
print(add(1), add(2), add(3))
```

真实输出（**一行**，不是三行）：

```
[1, 2, 3] [1, 2, 3] [1, 2, 3]
```

为什么是一行三个？因为 `print` 也遵循同一条规则：**它的全部参数在 `print` 自己被调用之前就求值完了**。
三个 `add(...)` 全跑完，`print` 才开始干活，那时候三个值已经是最终状态。

你可以亲眼看到"参数先求值完"这件事：

```python
def tag(s):
    print(f"   [求值 {s}]")
    return s

print(tag("a"), tag("b"), tag("c"))
```

真实输出：

```
   [求值 a]
   [求值 b]
   [求值 c]
a b c
```

**三行 `[求值 x]` 全部出现在 `a b c` 之前。** 外层 `print` 一直等着，直到三个参数都算完。

这条规则你在 JS 里也见过——`console.log(f(), g())` 一样是先算完再打印。
**这不是 Python 的怪癖，这是"函数调用"这个动作的通用语义。**

## 三、为什么你的 JavaScript 从来没有这个 bug

这是今天最值钱的一条对照。同一个语义，两个语言的做法**相反**：

| | Python | JavaScript |
|---|---|---|
| 默认值 `[]` 什么时候求值 | **`def` 那一行执行时，一次** | **每次调用时，重新求值** |

我在你这台机器上跑了 JS 版：

```javascript
function add(n, log = []) {
  log.push(n);
  return log;
}
const a = add(1), b = add(2), c = add(3);
console.log(a, b, c, a === b);
```

真实输出：

```
[ 1 ] [ 2 ] [ 3 ] | a===b : false
```

**JS 给你一个全新的数组，每次调用都是新的。** 所以 `a === b` 是 `false`，
这个 bug 在 JS 里**根本写不出来**。

> 你十年前端经验里之所以从没见过这个坑，**不是因为你小心，是因为这门语言不会犯这个错。**
> 这就是为什么移植代码时"我在 JS 里一直这么写的"不是一条理由。

### 那 Python 里怎么修

标准写法只有一个，叫 **`None` 哨兵**：

```python
def add(n, log=None):
    if log is None:
        log = []
    log.append(n)
    return log
```

跑同样的三次调用：

```
[1] [2] [3]
__defaults__ : (None,)
d is e       : False
```

**`__defaults__` 里现在存的是 `None`（不可变，存多少次都是它），
真正的列表在函数体里、每次调用新建一个。**

一句话记住修法：**把"每次都要新东西"这件事，从 `def` 那一行搬到函数体里面去。**

## 四、同一件事在类上的版本：类属性是共享的

```python
class Note:
    tags = []

n1, n2 = Note(), Note()
n1.tags.append("x")
print(n1.tags, n2.tags)
print("n1.tags is n2.tags :", n1.tags is n2.tags)
```

真实输出：

```
['x'] ['x']
n1.tags is n2.tags : True
```

**你往 `n1` 里塞的东西，出现在了 `n2` 身上。** 而且 `Note.tags` 本身也是 `['x']`——
因为三个名字指向的还是那一个列表，规则和第二节完全一样：
`tags = []` 写在**类体**里，类体是一条条执行的语句，那一行只跑一次。

搬进 `__init__` 就对了：

```python
class Note2:
    def __init__(self):
        self.tags = []
```

```
['x'] []
m1.tags is m2.tags : False
```

### 和 JS 对照（这次三个都要看）

| 写法 | 每个实例独立吗 | 真值 |
|---|---|---|
| Python `class C: tags = []` | **不独立**（共享） | `['x'] ['x']` |
| Python `class C: def __init__(self): self.tags = []` | 独立 | `['x'] []` |
| JS `class C { tags = [] }` | 独立 | `['x'] []` |
| JS `class C { static tags = [] }` | 独立，但**实例读不到** | 实例 `undefined`，类上 `['y']` |

**这张表今天最容易被记错，所以我只给一个记法：**

> **Python 的类体 ≈ JS 的 `static`；Python 的 `__init__` ≈ JS 的类字段。**
>
> 你觉得"我什么都不写在类体里就行"的那个写法（JS 类字段），在 Python 里对应的不是类体，是 `__init__`。

想清楚你要哪个：

- 要**每个对象一份**（绝大多数情况）→ Python 写在 `__init__` 里 `self.xxx = []`
- 要**全类共享一份**（真需求很少）→ 写在类体里，或者 JS 的 `static`

## 五、装饰器：它跑在 `def` 的那一刻，不是调用的那一刻

装饰器经常被当成"黑魔法"，其实它**只是一个人人都认识的赋值语句**。

```python
@w
def my_func():
    ...
```

**完全等价于**：

```python
def my_func():
    ...
my_func = w(my_func)
```

一旦你看出这一点，它的所有行为都好解释了：既然那行赋值发生在 `def` 之后**立刻**执行，
那装饰器里的代码当然也在**定义时**就跑。

我把时刻全打印出来了：

```python
print("   A 装饰器定义之前")

def w(fn):
    print("   B 装饰器体内（定义时就跑）")
    def inner(*args, **kw):
        print("   C 调用时才跑")
        return fn(*args, **kw)
    return inner

@w
def my_func():
    print("   D 函数体")

print("   E 定义完成、还没调用")
my_func()
```

真实输出：

```
   A 装饰器定义之前
   B 装饰器体内（定义时就跑）
   E 定义完成、还没调用
   C 调用时才跑
   D 函数体
```

**`B` 出现在 `E` 前面。** 你还没调用任何函数，装饰器已经跑完了。

### 代价：它吃掉了你的名字

```python
print(my_func.__name__)
```

不加 `functools.wraps` 的真实输出：

```
inner
```

**你写的函数叫 `my_func`，装饰完它就叫 `inner` 了。** `repr()` 也变成
`<function w.<locals>.inner at 0x...>`。

这件事在纯 Python 世界里就足够疼了，不用扯别的：

- 你在调试时按名字搜函数，搜不到
- 任何拿 `__name__` 做日志、做注册、做分发的代码，全都拿到一个假名字
- 报错栈里出现一堆 `inner`，分不清是谁

修法也是标准动作，加一行 `@functools.wraps(fn)`：

```python
import functools

def w(fn):
    @functools.wraps(fn)
    def inner(*args, **kw):
        return fn(*args, **kw)
    return inner
```

真实输出（我拿一个带 docstring 的函数验的）：

```
加 wraps   -> __name__ : kept | docstring : 我是 kept 的文档。
```

`__name__` 和 `__doc__` 都被原样搬回来了。

### JS 侧为什么没有"帮你修回来"的东西

JS 到今天**没有内建的 `@` 语法**（还是个提案）。你在 JS 里做同样的事只能手写：

```javascript
greet = wrap(greet);
```

也就是说 **JS 连"吃掉名字"这件事都不会自动帮你修**——Python 至少还有 `functools.wraps` 这个标准件。
所以这条纪律对你是新增的，不是复习：

> **写装饰器，`@functools.wraps(fn)` 是必写的一行，不是可选的礼貌。**

## 六、`@dataclass` 在这件事上比你自己严

`@dataclass` 是个装饰器（第五节的内容你刚学会），它帮你自动生成 `__init__`。
那么可变默认值交给它，会怎样？

```python
from dataclasses import dataclass

@dataclass
class Bad:
    tags: list = []
```

真实输出——**它直接拒绝定义**：

```
ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory
```

它没等你踩坑，它在 `class` 那一行就崩了。正确写法是把"怎么造一个新的"交给它：

```python
from dataclasses import dataclass, field

@dataclass
class Good:
    tags: list = field(default_factory=list)
```

跑两个实例：

```
default_factory : ['a'] [] | is : False
```

**三种对待可变默认值的态度，今天你已经见全了两种：**

| 谁 | 你怎么写 `[]` | 它的反应 |
|---|---|---|
| 普通函数 / 普通 class | 直接写 | **不管你**，静默共享，等你线上炸 |
| `@dataclass` | 直接写 | **禁止你**，当场 `ValueError` |
| 需要每次新建 | `field(default_factory=list)` | 替你每次新建一个 |

第一行是今天全部内容的教训：**默认不管 = 最危险**，因为它不报错。

## 七、同一个道理在文件尺度上：`if __name__ == "__main__"`

第五节你刚学过 `__name__` 是**函数**身上的一个字符串。今天最后一件事：
**一个 .py 文件本身也是一个对象，它身上也挂着一个 `__name__`。**

建 `/tmp/mod.py`（`cat > … <<'PY'` 那套你第 1 题就会了）：

```python
print("顶层语句：被求值了")


def f():
    print("  函数体：只有被调用才跑")


if __name__ == "__main__":
    print("if 块里：只有直接跑这个文件才有")
    print("__name__ 的值是 :", repr(__name__))
```

**先猜再跑。** 两种拿法，输出不一样：

```bash
python3 /tmp/mod.py
cd /tmp && python3 -c "import mod; print('外部看到 mod.__name__ =', repr(mod.__name__))"
```

真实输出，**原样粘贴，没有修饰**：

```
# 直接跑
顶层语句：被求值了
if 块里：只有直接跑这个文件才有
__name__ 的值是 : '__main__'

# 被 import —— 注意只剩两行
顶层语句：被求值了
外部看到 mod.__name__ = 'mod'
```

把它接回今天那张表，你就有了它的**文件尺度版本**：

| 这段代码 | 什么时候跑 |
|---|---|
| `def` 的函数体 | 被**调用**时 |
| `if __name__ == "__main__":` 里面 | 被**直接运行**时 |
| 文件顶层 | 被**拿起来**时——运行和 import 都算 |

所以这行**不是模板、不是「Python 的规矩」**，它是一个开关：
让你自己决定哪几行只在「我在命令行里点名要跑这个文件」时才动。

### 你的 JS 里有一行逐字等价的

node 实测，两种行为完全对齐：

| 拿法 | Python | Node |
|---|---|---|
| 直接跑文件 | 顶层 + if 块里 | 顶层 + if 块里 |
| 被别的文件拿起 | **只有**顶层 | **只有**顶层 |
| 那个判断长什么样 | `__name__ == "__main__"` | `require.main === module` |

这行你不用记，它是你已经会的东西换了个写法。

### 它和你今晚要写的 `calculator.py` 有一个硬关系

`check.py` **不运行**你的 `calculator.py`，它把你的文件**拿起来**（`exec` 你的顶层）。
于是有一件你**一定会撞到**的事，我先让它当场发生一次。

我把第 6 题那几行验收装置**带开关**和**不带开关**各真跑了一遍 `check.py`。

**不裹开关**——你的八行顶层打印全堆在判卷结果前面：

```
-> add
-> sub
5 3
c1.history : [5, 3]
c2.history : []
[1, 3, 6]
[9]
['a'] []
-> add
-> add
-> sub
✓ 1. 写法 · 没有可变默认参数（……）
```

**裹住开关**——那八行没了：

```
-> add
-> add
-> sub
✓ 1. 写法 · 没有可变默认参数（……）
```

两个版本都是六项全绿、退出码 0。差别只是那八行——
**它们全是你自己的顶层在 `check.py` 拿起你文件那一刻跑的。**

**但别把裹住后剩下的那三行也当成 bug。**
那是 `check.py` 为了验你的第 4、5 项，自己去调用了 `c.add(5)`，
你的装饰器当然会印。这三行拦不住，也不该拦。

所以那个开关管的是**「我自己那些演示打印」**，
不管**「别人正常调用我的函数时，我的函数该做的事」**。
这个区分你以后写任何库都要用。

`check.py` 报错时那句提示，现在你读得懂了：

