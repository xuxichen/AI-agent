## 二、可变默认参数（默认值在 `def` 那一行只求值一次）

### ① 建文件

这一节的文件稍长，**50 行，分 A B C D 四段**。四段用的是**四个不同的函数**，
这不是啰嗦——`add` 跑过一次之后它那个默认列表就被污染了，
你拿它去做第二个实验就会看到假结果。**每个实验要一个干净的新函数**，这个纪律今天贯穿到底。

```bash
cd stage1/day002_python_core
cat > code/python/02_shared_default.py <<'PY'
def add(n, log=[]):
    log.append(n)
    return log


print("=== A 先把三次调用的返回值存进三个名字，最后一起印 ===")
x = add(1)
y = add(2)
z = add(3)
print(x)
print(y)
print(z)
print("x is y :", x is y)
print("add.__defaults__ :", add.__defaults__)
print("x is add.__defaults__[0] :", x is add.__defaults__[0])

print()
print("=== B 换一个全新的函数 add_b，边调边印 ===")


def add_b(n, log=[]):
    log.append(n)
    return log


print(add_b(1))
print(add_b(2))
print(add_b(3))

print()
print("=== C 再换一个全新的函数 add_c，三个调用写在同一行 ===")


def add_c(n, log=[]):
    log.append(n)
    return log


print(add_c(1), add_c(2), add_c(3))

print()
print("=== D 亲眼看到「参数先全部算完，外层才开始干活」 ===")


def tag(s):
    print(f"   [求值 {s}]")
    return s


print(tag("a"), tag("b"), tag("c"))
PY
cd ../..
```

### ② 先猜再跑

**猜这四段各自印出什么**，尤其是 A 段的最后两行和 C 段。猜完记下来，再跑：

```bash

```

### ③ 真实输出，一字不差

```

=== B 换一个全新的函数 add_b，边调边印 ===
[1]
[1, 2]
[1, 2, 3]

=== C 再换一个全新的函数 add_c，三个调用写在同一行 ===
[1, 2, 3] [1, 2, 3] [1, 2, 3]

=== D 亲眼看到「参数先全部算完，外层才开始干活」 ===
   [求值 a]
   [求值 b]
   [求值 c]
a b c
```

### ④ 逐行对上

#### A 段：三个名字，一个对象

`x`、`y`、`z` 是**三个名字**，分别接住第一次、第二次、第三次调用 `add` 的返回值。
三次都印 `[1, 2, 3]`，说明它们**不是**"内容碰巧一样的三个列表"。

`is` 是 Python 判断"**是不是同一个东西**"的运算符（JS 里的 `===` 对对象干的是同一件事）：

```
x is y : True
```

**`True`。** 它是同一个列表被印了三遍。`add` 每次 `return` 的都是同一个对象。

那这个对象**存在哪里**？存在函数自己身上。每个函数对象都带一个叫 `__defaults__` 的属性，
它就是"这个函数的默认值们"：

```
add.__defaults__ : ([1, 2, 3],)
x is add.__defaults__[0] : True
```

第一行：`([1, 2, 3],)` 是一个**元组**（Python 里用逗号分隔、不可变的那串东西，JS 里没有对应物），
里面装着 `add` 的默认值——`n` 没有默认值，`log` 有，所以元组里只有一个元素。

第二行：`add.__defaults__[0]` 是那个元组的第 0 个元素，也就是那个列表。**`x` 和它就是同一个对象。**

所以今天第一个结论：

> **`x`、`y`、`z`、`add.__defaults__[0]` —— 四个名字，一个对象。**

#### 为什么会这样

Python 里 `def` **是一条语句，不是一段声明**。

解释器从上往下执行，执行到 `def add(n, log=[]):` 这一行时，它做了三件事：

1. 建一个函数对象
2. **在这一刻，把 `[]` 这个空列表建出来，塞进函数的 `__defaults__` 里**
3. 把这个函数绑定到名字 `add`

第 2 步是关键。`[]` 只在 **`def` 那一行执行时求值一次**。
之后你调用 `add()` 一百次，Python 都从 `__defaults__` 里把**同一个**列表拿出来用。
它不新建，它只是"取那个已经建好的"。

#### B 段：为什么边调边印看着"正常"

因为**打印的时机**不同。A 段是三次调用全跑完才第一次打印，
于是三个名字（同一个对象）上都是最终状态 `[1, 2, 3]`。
B 段每调用一次立刻印一次，所以你看到的是那个列表**生长的过程**：`[1]` → `[1, 2]` → `[1, 2, 3]`。

**列表从头到尾只有一个。** B 段没有"修好"任何东西，它只是让你看见了同一个东西在变大。

#### C 段：一行之内三次调用

```
[1, 2, 3] [1, 2, 3] [1, 2, 3]
```

**是一行，不是三行**（三个值被同一个 `print` 用空格隔开印出来）。

为什么？因为 `print` 也遵循同一条规则：**它的全部参数在 `print` 自己被调用之前就求值完了**。
三个 `add_c(...)` 全跑完，`print` 才开始干活，那时候三个值都已经是最终状态。

#### D 段：把这条规则拍给你看

`tag` 是一个故意"多嘴"的函数——它每被求值一次，就先印一行 `[求值 x]` 再返回那个字符串：

```python
def tag(s):
    print(f"   [求值 {s}]")
    return s
```

（`f"..."` 是 Python 的模板字符串，等价于 JS 的 `` `...${s}...` ``，只是用 `{s}` 而不是 `${s}`。）

跑出来：

```
   [求值 a]
   [求值 b]
   [求值 c]
a b c
```

**三行 `[求值 x]` 全部出现在 `a b c` 之前。** 外层 `print` 一直等到三个参数都算完才开始印。

这条规则你在 JS 里也见过——`console.log(f(), g())` 一样是先算完再打印。
**这不是 Python 的怪癖，这是"函数调用"这个动作的通用语义。**

## 三、JS 默认参数的对照，与 `None` 哨兵写法

这是今天最值钱的一条对照。同一个语义，两个语言的做法**相反**：

| | Python | JavaScript |
|---|---|---|
| 默认值 `[]` 什么时候求值 | **`def` 那一行执行时，一次** | **每次调用时，重新求值** |

### ① 建 JS 文件并跑

```bash
cd stage1/day002_python_core
cat > code/js/03_default_args.js <<'JS'
function add(n, log = []) {
  log.push(n);
  return log;
}

const a = add(1);
const b = add(2);
const c = add(3);

console.log(a, b, c);
console.log("a === b :", a === b);
JS
cd ../..
```

**在哪跑**：仓库根目录。

```bash
node stage1/day002_python_core/code/js/03_default_args.js
```

### ② 真实输出

```
[ 1 ] [ 2 ] [ 3 ]
a === b : false
```

（node 印数组时里面会带空格，所以是 `[ 1 ]` 不是 `[1]`，别以为不一样。）

**JS 给你一个全新的数组，每次调用都是新的。** 所以 `a === b` 是 `false`，
这个 bug 在 JS 里**根本写不出来**。

> 你十年前端经验里之所以从没见过这个坑，**不是因为你小心，是因为这门语言不会犯这个错。**
> 所以移植代码的时候，"我在 JS 里一直这么写的"不算理由。

### ③ 那 Python 里怎么修

标准写法只有一个，叫 **`None` 哨兵**：

```bash
cd stage1/day002_python_core
cat > code/python/03_none_sentinel.py <<'PY'
def add(n, log=None):
    if log is None:
        log = []
    log.append(n)
    return log


d = add(1)
e = add(2)
f = add(3)

print(d, e, f)
print("add.__defaults__ :", add.__defaults__)
print("d is e           :", d is e)
PY
cd ../..
```

**说明这里出现的每一行**：

- `log=None` —— 默认值换成了 `None`。`None` 是**不可变**的（整个程序里只有这一个 `None`），
  所以"只建一次"对它毫无影响。
- `if log is None: log = []` —— 真正的新列表在**函数体里**建，函数体每次调用都重新执行。
- `d`、`e`、`f` —— 三个**新名字**，分别接住第一、二、三次调用的返回值。
  （A/B/C 那三个字母在第二节已经用完了，这里换一套，免得你以为它们还是同一个列表。）

### ④ 该看到

```bash
uv run python stage1/day002_python_core/code/python/03_none_sentinel.py
```

```
[1] [2] [3]
add.__defaults__ : (None,)
d is e           : False
```

**`__defaults__` 里现在存的是 `None`**（不可变，存多少次都是它），
真正的列表在函数体里、每次调用新建一个。所以 `d is e` 是 `False`——三个**不同的**列表。

一句话记住修法：

> **把"每次都要新东西"这件事，从 `def` 那一行搬到函数体里面去。**

## 四、类属性共享，与 JS 的类字段（每个实例一份）

第二节讲的是**函数**：`def` 那一行只执行一次。
现在讲**类**：`class` 里面的那些行，也**只在 `class` 语句执行时跑一次**。

### ① 建文件

```bash
cd stage1/day002_python_core
cat > code/python/04_class_attr.py <<'PY'
print("=== A tags 裸写在类体里 ===")


class Note:
    tags = []


n1 = Note()
n2 = Note()
n1.tags.append("x")

print(n1.tags, n2.tags)
print("n1.tags is n2.tags :", n1.tags is n2.tags)
print("Note.tags          :", Note.tags)

print()
print("=== B 搬进 __init__ ===")


class Note2:
    def __init__(self):
        self.tags = []


m1 = Note2()
m2 = Note2()
m1.tags.append("x")

print(m1.tags, m2.tags)
print("m1.tags is m2.tags :", m1.tags is m2.tags)
PY
cd ../..
```

**这里每一个新面孔**：

- `class Note:` —— 定义一个叫 `Note` 的类。类是"造对象的图纸"。
- `Note()` —— 按图纸**造一个对象**出来（JS 里是 `new Note()`，Python **不需要 `new`**）。
- `n1`、`n2` —— 两个新名字，各接住一个 `Note` 对象。
- `n1.tags` —— 读这个对象身上的 `tags`。你没在 `n1` 上放过 `tags`，
  那 Python 就去它的类 `Note` 身上找——**这正是坑的来源**。
- `__init__(self)` —— 名字前后各两个下划线，是 Python 的固定约定，
  意思是"造对象之后立刻自动调这一个"。`self` 就是"正在被造的这个对象自己"（JS 里的 `this`）。
- `m1`、`m2` —— B 段的两个新名字，故意和 A 段的 `n1`、`n2` 不同，
  这样你绝不会把两段的结果看混。

### ② 先猜再跑

猜 B 段会不会和 A 段一样。

```bash
uv run python stage1/day002_python_core/code/python/04_class_attr.py
```

### ③ 真实输出

```
=== A tags 裸写在类体里 ===
['x'] ['x']
n1.tags is n2.tags : True
Note.tags          : ['x']

=== B 搬进 __init__ ===
['x'] []
m1.tags is m2.tags : False
```

### ④ 对上

**A 段：你往 `n1` 里塞的东西，出现在了 `n2` 身上。**

而且第三行 `Note.tags : ['x']` 是今天这个实验最狠的一句——
**连图纸本身都被改了。** 因为 `n1.tags`、`n2.tags`、`Note.tags` 三个名字指向的还是那**一个**列表，
规则和第二节完全一样：`tags = []` 写在**类体**里，类体是一条条执行的语句，那一行只跑一次。

**B 段：搬进 `__init__` 就对了。**
`self.tags = []` 在函数体里，每造一个对象都重新执行一次，所以每个对象一个独立列表。

### 和 JS 对照：下面四条全要看

```bash
cd stage1/day002_python_core
cat > code/js/04_class_fields.js <<'JS'
class A {
  tags = [];
}

const a1 = new A();
const a2 = new A();
a1.tags.push("x");
console.log("类字段（每个实例一份）:", a1.tags, a2.tags);

class S {
  static tags = [];
}

const s1 = new S();
console.log("实例上读得到吗       :", s1.tags);
S.tags.push("y");
console.log("挂在类上              :", S.tags);
JS
cd ../..

node stage1/day002_python_core/code/js/04_class_fields.js
```

真实输出：

```
类字段（每个实例一份）: [ 'x' ] []
实例上读得到吗       : undefined
挂在类上              : [ 'y' ]
```

现在四行对照表里每一格的**出处**都在上面了：

| 写法 | 每个实例独立吗 | 出处 |
|---|---|---|
| Python `class Note: tags = []` | **不独立**（共享） | `04_class_attr.py` A 段：`['x'] ['x']` |
| Python `def __init__(self): self.tags = []` | 独立 | 同上 B 段：`['x'] []` |
| JS `class A { tags = [] }` | 独立 | `04_class_fields.js` 第一段：`[ 'x' ] []` |
| JS `class S { static tags = [] }` | 独立，但**实例读不到** | 同上第二段：`undefined` / `[ 'y' ]` |

**这张表今天最容易被记错，所以我只给一个记法：**

> **Python 的类体 ≈ JS 的 `static`；Python 的 `__init__` ≈ JS 的类字段。**
>
> 你觉得"我什么都不写在类体里就行"的那个写法（JS 类字段），在 Python 里对应的不是类体，是 `__init__`。

想清楚你要哪个：

- 要**每个对象一份**（绝大多数情况）→ Python 写在 `__init__` 里 `self.xxx = []`
- 要**全类共享一份**（真需求很少）→ 写在类体里，或者 JS 的 `static`

## 五、装饰器的执行时机与 `functools.wraps`

装饰器常被说成"黑魔法"，其实它**就是一个你天天在写的赋值语句**。

`@` 后面跟一个函数的名字，加在 `def` 上面：

```python
@w                    # w 是一个函数
def my_func():
    ...
```

**它完全等价于**这个你看得懂的东西：

```python
def my_func():
    ...
my_func = w(my_func)   # 把 my_func 交给 w，再用 w 的返回值覆盖同名变量
```

**`@` 不是新机制，它只是这行赋值的简写。** 一旦你看出这一点，它所有行为都好解释了：
那行赋值发生在 `def` 之后**立刻**执行，那装饰器里的代码当然也在**定义时**就跑。

### ① 建文件

这个文件有点长，因为它一次做完**五件事**。每一件我都在代码里用 `print` 标出来：

```bash
cd stage1/day002_python_core
cat > code/python/05_decorator.py <<'PY'
```

### ④ 对上：这段输出里的四个关键点

#### 一、`B` 出现在 `E` 前面

**你还没调用任何函数，装饰器已经跑完了。**
`@w` 那行一执行，Python 就把 `my_func` 交给 `w`、拿回 `inner`、覆盖掉 `my_func`。
到 `print("E ...")` 的时候，`my_func` 这个名字**已经不是原来那个函数了**。

#### 二、`inner` 是什么？是约定的吗？

**不是语法，也不是规定，它就是我随手起的一个名字。**

`inner` 定义在 `w` 的**里面**（缩进在 `w` 的函数体里），所以叫它"里面的那个"。
它叫什么都行。我不信你会信这句话，所以我在文件里做了第三个实验——
把 `w2` 里的内层函数改名叫 **`sandwich`**（三明治，一个和"内部"毫无关系的词）：

```
renamed.__name__ : sandwich
```

**内层函数叫什么，被装饰完的函数就叫什么。** 我写 `inner`，你就看到 `inner`；
我写 `sandwich`，你就看到 `sandwich`。社区常见的两个名字是 `wrapper` 和 `inner`，
**都是习惯，不是语法**。你不喜欢，改掉就行——但记得下一条会因此变。

#### 三、`repr()` 是什么？怎么用？

`repr` 是一个**内建函数**（不需要 `import`，直接就能用），
`repr(任何对象)` 返回一个字符串，是"**给程序员看的**"那个表示形式。

它和 `print` 的分工：

```python
print(x)      # 给用户看：[1, 2, 3]
repr(x)       # 给程序员看：'[1, 2, 3]'  ← 带引号，你一眼知道它是字符串
```

（JS 里你熟的那个是 `console.log`，`repr` 更接近你在浏览器里 hover 一个对象看到的东西。）

`print(repr(my_func))` 打出来的是：

```
<function w.<locals>.inner at 0x107d0f600>
```

三段，一段一段读：

| 段 | 意思 |
|---|---|
| `function` | 这个对象的类型是函数 |
| `w.<locals>.inner` | 名字叫 `inner`，`<locals>` 是限定符，读作「**定义在函数 `w` 的局部作用域里的**那个 `inner`」。顶层函数没有这段——第二节里的 `add` 就是 `<function add at 0x...>` |
| `at 0x107d0f600` | 它在内存里的地址。**每次运行都可能不同，永远不要拿它做比较或判断** |

所以 `<function w.<locals>.inner ...>` 这一串，就是在明明白白告诉你：
**"你现在手上这个叫 `my_func` 的名字，其实指向的是 `w` 里面那个 `inner`。"**

#### 四、代价，和那一行修法

你的函数原本叫 `my_func`，装饰完它就叫 `inner` 了。**光是这件事本身就够你麻烦**：

- 你在调试时按名字搜函数，搜不到
- 任何拿 `__name__` 做日志、做注册、做分发的代码，全都拿到一个假名字
- 报错栈里出现一堆 `inner`，分不清是谁

修法是一个标准动作，加一行 `@functools.wraps(fn)`：

```python
def w3(fn):
    @functools.wraps(fn)      # ← 就这一行
    def inner(*args, **kw):
        return fn(*args, **kw)
    return inner
```

文件里我拿一个**带文档字符串**的函数验了它（`"""我是 kept 的文档。"""` 那一行就是文档字符串，
它是函数身上 `__doc__` 这个属性的值，JS 里没有对应东西）：

```
加 wraps   -> __name__ : kept | __doc__ : 我是 kept 的文档。
不加 wraps -> __name__ : inner | __doc__ : None
```

`__name__` 和 `__doc__` 都被原样搬回来了。**`wraps` 干的事就是：把被包掉的那个函数的名字和文档，抄回新函数身上。**

### JS 侧的 `@`：编译期语法，运行时不存在

**你没看错，是我那句话说不全。** 我在你这台机器上实测了 `node v20.20.2`：

```bash
cd stage1/day002_python_core
cat > code/js/05_rejects_decorator.js <<'JS'
function obs(target, name, descriptor) {
  return descriptor;
}

class S {
  @obs x = 1;
}
JS
node code/js/05_rejects_decorator.js
cd ../..
```

（这个文件**预期就是报错**，报错才算跑对了。）

**报错，原样：**

```
.../code/js/05_rejects_decorator.js:6
  @obs x = 1;
  ^

SyntaxError: Invalid or unexpected token
    at wrapSafe (node:internal/modules/cjs/loader:1464:18)
```

（第一行那个路径末尾的 `:6` 是行号，你机器上路径不一样但行号应该也是 6。
同样的代码用 `import` 方式跑 ESM 也是这一句 `SyntaxError`，我两种都试了。）

所以准确的结论是这个：

> **JS 的引擎不认 `@`，但编译器认。**

你项目里那些 `@observable`、`@inject`，是 **TypeScript 编译器或 Babel 插件在打包前把它们翻译掉了**，
产物里根本没有 `@`——翻译成的正是 `x = obs(x)` 这种普通赋值。
所以那行 `@` 只活在**编译前**，Python 的 `@` 活在**运行时**。

这也顺手解释了为什么 JS 从来不需要 `wraps` 这种东西：
它那个 `@` 在编译阶段就被换成了别的写法，最后变成什么全由编译器决定，
**运行时根本不存在"名字被盖掉"这件事**。

> 所以今天这条纪律对你是**新增**的，不是复习：
> **写装饰器，`@functools.wraps(fn)` 这一行必须写。加不加不是风格问题，不加就真的会出事。**

## 六、`@dataclass` 与 `field(default_factory=...)`

第五节你已经知道 `@dataclass` 就是个装饰器（`@` + 一个叫 `dataclass` 的函数）。
它帮你自动生成 `__init__`，你就不用手写那堆 `self.xxx = xxx`。

那么"可变默认值"交给它，会怎样？

### ① 建文件

```bash
cd stage1/day002_python_core
cat > code/python/06_dataclass.py <<'PY'
from dataclasses import dataclass, field

print("=== A 普通 class 里裸写 = [] ，没人管你 ===")


class Plain:
    tags: list = []


p1 = Plain()
p2 = Plain()
p1.tags.append("z")
print(p1.tags, p2.tags, "| is :", p1.tags is p2.tags)

print()
print("=== B 换成 @dataclass，同一个写法 ===")


@dataclass
class Good:
    tags: list = field(default_factory=list)


g1 = Good()
g2 = Good()
g1.tags.append("a")
print(g1.tags, g2.tags, "| is :", g1.tags is g2.tags)
print("Good.__init__ 是 dataclass 帮你生成的 :", Good.__init__.__name__)
PY
cd ../..
```

**新面孔**：

- `tags: list = []` 里那个 `: list` 叫**类型注解**，读作"这个字段我宣称是 list"。
  **它在运行时基本只是个标签，不拦你做任何事**——第四节的所有规则它一条都不改。
- `from dataclasses import dataclass, field` —— 从标准库的 `dataclasses` 模块里拿两个东西出来用。
- `field(default_factory=list)` —— 不是"默认值是 list"，是"**每次要建新的时候，调用 `list` 这个函数去建一个**"。
  `list` 你第二节就见过了，`list()` 返回一个新的空列表。

### ② 跑

```bash
uv run python stage1/day002_python_core/code/python/06_dataclass.py
```

真实输出：

```
=== A 普通 class 里裸写 = [] ，没人管你 ===
['z'] ['z'] | is : True

=== B 换成 @dataclass，同一个写法 ===
['a'] [] | is : False
Good.__init__ 是 dataclass 帮你生成的 : __init__
```

A 段：**普通 class 完全不拦你**，静默共享，第四节那个坑原样复现。
B 段：`g1`、`g2` 是 `Good` 的两个对象。`g1.tags.append("a")` 之后 `g2.tags` 还是 `[]`——
`default_factory` 每次造对象都调一次 `list()`，所以每个对象一个新列表。

### ③ 改坏一次：把 `default_factory` 换回 `= []`

B 段用的是 `field(default_factory=list)`。**你把那一行改回 `= []`**：

```python
@dataclass
class Good:
    tags: list = []          # ← 把 field(default_factory=list) 改成这个
```

保存后再跑同一条命令。真实输出（我把上面 A 段的输出也留着，你对照自己看）：

```
=== A 普通 class 里裸写 = [] ，没人管你 ===
['z'] ['z'] | is : True

=== B 换成 @dataclass，同一个写法 ===
Traceback (most recent call last):
  File ".../code/python/06_dataclass.py", line 19, in <module>
    @dataclass
     ^^^^^^^^^
  ...（中间几行是标准库内部的调用链，你今天不用读）...
ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory
```

最后一行退出码是 `1`（`echo $?` 能验）。

### ④ 报错时机：编辑器还是运行时

先给结论：**运行时报错**。而且你的编辑器不该拦它——多数编辑器也确实没拦。
三条证据，你自己在机器上就能重做前两条：

```bash
uv run python -m py_compile stage1/day002_python_core/code/python/06_dataclass.py && echo "语法检查：通过（没有任何错）"
```

**语法检查通过。** 意思是 `tags: list = []` 这行在 Python 的语法规则里**完全合法**，
编辑器和解释器都没有任何理由在你敲下去的那一刻拦你。

第二条，看输出：`=== A 普通 class ...` 和 `['z'] ['z']` 这些行**全都印出来了**，
才轮到 B 段炸。说明解释器是**活着执行到了那里**才发现问题的。

第三条，看 traceback 的箭头指哪一行：

```
  File ".../06_dataclass.py", line 19, in <module>
    @dataclass
     ^^^^^^^^^
```

**箭头指在 `@dataclass` 上，不是指在 `tags: list = []` 上。**

把三条串起来，就是一句你今天已经会解释的话（第五节）：
`@dataclass` 等价于 `Good = dataclass(Good)`，
**抛错的是这一次函数调用**。`dataclass` 这个函数在检查你交给它的那个类，
一看有个字段的可变默认值，**它当场拒绝**。

它没等你踩坑，它在 `class` 那一行执行时（= 被 `@dataclass` 处理的那一刻）就崩了。

**三种态度加一条出路，今天你已经见全了：**

| 谁 | 你怎么写 `[]` | 它的反应 | 你在哪看到的 |
|---|---|---|---|
| 普通函数（第三节） | 直接写 | **不管你**，静默共享 | `02_shared_default.py` |
| 普通 class（第四节） | 直接写 | **不管你**，静默共享 | `04_class_attr.py`、`06_dataclass.py` A 段 |
| `@dataclass`（本节） | 直接写 | **禁止你**，运行时 `ValueError` | `06_dataclass.py` 改坏那次 |
| `default_factory` | 交给它一个函数 | 每次替你新建一个 | `06_dataclass.py` B 段 |

今天全部内容的教训在第一、二行：**默认不管 = 最危险**，因为它不报错。

## 七、模块入口：`if __name__ == "__main__"`

前六节你看到的都是"**一个函数/一个类**身上，哪一刻执行"。
最后一节把镜头拉到最大：**一个 .py 文件本身，也有"哪一刻执行"这个问题。**

而你在第一节就已经知道 `__name__` 是**函数**身上的一个字符串（`my_func.__name__`）。
今天最后一件事：**一个 .py 文件也是一个对象，它身上也挂着一个 `__name__`。**

### 这个文件为什么不按节号命名

我先给你看它为什么必须破例：

```bash
uv run python -c "import 07_test"
```

真实报错：

```
  File "<string>", line 1
    import 07_test
             ^
SyntaxError: invalid decimal literal
```

**`import` 后面要跟一个标识符，而标识符不能以数字开头。**
所以前面那六个 `0X_` 文件都**只能被运行、不能被 import**。
这一个需要被 import，所以它不编号。

### ① 建文件

```bash
cd stage1/day002_python_core
cat > code/python/mod_two_faces.py <<'PY'
print("顶层语句：被求值了")


def f():
    print("  函数体：只有被调用才跑")


if __name__ == "__main__":
    print("if 块里：只有直接跑这个文件才有")
    print("__name__ 的值是 :", repr(__name__))
PY
cd ../..
```

`if __name__ == "__main__":` 读作：**"如果我的 `__name__` 这个属性，等于字符串 `"__main__"`，就跑下面缩进的这几行。"**

### ② 两种跑法：直接运行 / 被 import

**这里就是"先猜再跑"的全部意思**：同一个文件，你用两种不同的方式让它开始执行，
**它跑的代码行数不一样**。两种我都写了命令，你两条都跑：

**方式一：你直接点名要跑它**

```bash
cd stage1/day002_python_core/code/python
uv run python mod_two_faces.py
```

**方式二：另一个程序把它"拿起来"（`import` 它），但一行都不跑**

```bash
uv run python -c "import mod_two_faces; print('外部看到 mod_two_faces.__name__ =', repr(mod_two_faces.__name__))"
cd ../../../..
```

（`-c` 里面那句 `import mod_two_faces` 只有在**你当前就站在那个目录里**时才找得到文件，
所以这一段前面要先 `cd` 进去，跑完 `cd ../../../..` 回仓库根。）

### ③ 真实输出（两次的行数不同）

方式一，三行：

```
顶层语句：被求值了
if 块里：只有直接跑这个文件才有
__name__ 的值是 : '__main__'
```

方式二，**只有两行**：

```
顶层语句：被求值了
外部看到 mod_two_faces.__name__ = 'mod_two_faces'
```

### ④ 对上

| 名字 `__name__` 的值 | 什么时候 |
|---|---|
| `'__main__'` | **你直接点名跑它**（`python 那个文件.py`） |
| `'mod_two_faces'`（= 文件名） | **它被别人 import 起来** |

而 `if __name__ == "__main__":` 里面那几行，只在**上面那一行**才成立、才跑。

把它接回今天那张表，你就有了它的**文件尺度版本**：

| 这段代码 | 什么时候跑 |
|---|---|
| `def` 的函数体 | 被**调用**时 |
| `if __name__ == "__main__":` 里面 | 被**直接运行**时 |
| 文件顶层（不在任何 `def` / `if` 里） | 被**拿起来**时——直接运行和 import 都算 |

所以这行**不是模板、不是"Python 的规矩"**，它是一个开关：
让你自己决定哪几行只在「我在命令行里点名要跑这个文件」时才动。

### JS 对照：`require.main === module`

不是近似，是逐字。node 实测（我跑了）：

```bash

  console.log("if 块里：只有 node 直接跑才有");

JS
```

真实输出：

| 拿法 | Python | Node |
|---|---|---|
| 直接跑文件 | 顶层 + if 块里 | 顶层 + if 块里 |

这行你不用记，它是你已经会的东西换了个写法。

### 与 `calculator.py` 的关系：`check.py` 会把你的顶层跑一遍

`check.py` **不运行**你的 `calculator.py`，它把你的文件**拿起来**
（用 `exec` 执行你的顶层）。于是有一件你**一定会撞到**的事。

我把作业第 4 题那段验收装置**带开关**和**不带开关**各真跑了一遍 `check.py`：

**它们全是你自己的顶层在 `check.py` 拿起你文件那一刻跑的。**

**但别把裹住后剩下的那三行也当成 bug。**

### ④ 逐行对上

**第 1 段：`for n in nums:` 干什么。**
每跑一轮，它把 `nums` 里的下一个元素绑到名字 `n` 上，然后跑一遍**缩进的那两行**。
`nums` 里有三个东西，所以缩进块跑了三轮。你把缩进块里那两条 `print` 全删掉、
只留 `total = total + n`，最外层结果仍然是 `6`（我跑了）——
**打印是为了看见循环在动，不是循环本身需要的**。

`total = total + n` 这一行的左右两边**不是同一个值**：
右边是「进这一轮之前」的 total，左边是「出这一轮之后」的新 total。
JS 里你写 `total = total + n` 也是同一件事，`total += n` 是它的缩写（今天不用）。

**第 2、3 段：`range` 的两个形状。**

| 你写 | 它给的数 | 几轮 |
|---|---|---|
| `range(3)` | 0、1、2 | 3 |
| `range(1, 4)` | 1、2、3 | 3 |

**右边界永远拿不到。** 这就是 JS 那个 `i < 4`：

```js
for (let i = 1; i < 4; i++) console.log(i);   // 1 2 3
```

`range(1, 4)` 和上面那行**一模一样**，`4` 就是那个 `<` 右边的数。
你觉得 `range(1, 4)` 该给四个数，是因为你把它读成了「从 1 到 4」；它其实是「从 1 开始，取 3 个」。

**第 4 段：负索引，两边真的不同。**
Python 的 `nums[-1]` 是**最后一个**，`nums[-2]` 是倒数第二个。
JS 里 `nums[-1]` 是 `undefined`（那里 `nums[-1]` 是在找一个名叫 `-1` 的属性）。
这一条值得单独记：你在 JS 里习惯的「取最后一个」是 `nums[nums.length - 1]`，
Python 直接给 `nums[-1]`。

**第 5 段：这就是 `running_total` 的循环体。**
`so_far` 是「加到哪了」的账，`acc` 是「每一轮结束时把账抄一份进去」。
`acc.append(so_far)` 这个动作你已经会了（第二节），只是现在它被放在了一个跑三轮的块里。
把这两行的顺序换一下（先 `append` 再 `so_far = so_far + n`），`acc` 就变成 `[0, 1, 3]`——
**循环体里语句的顺序会改结果，这个你从第二节就知道了，只是今天换了个地方咬人。**

> **今天用到这块地基只有两处**：`02_答案.md` 里的 `running_total`（`for` 加 `acc[-1]`），
> 和作业第 1 题里的 `items[0]`（就是上面第 4 段那个正索引）。
> 你要是那两段看得含糊，就回到这一节重跑第 5 段，别往前翻。
