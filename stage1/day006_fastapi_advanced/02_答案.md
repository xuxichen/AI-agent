## 第 1 题 · 9 步排序

```
['mw2-in', 'mw1-in', 'dep_a', 'dep_b', 'acquire', 'handler', 'mw1-out', 'mw2-out', 'release']
```

三条关键：

1. **`mw2-in` 在最前**：后注册的中间件在外层。`mw1` 先定义 → 在内层。
2. **`dep_a` 在 `dep_b` 前**：依赖按拓扑序解析，与 `ok(b=..., res=...)` 的参数书写顺序无关。
   `acquire` 排在 `dep_b` 之后，是因为 `dep_resource` 在参数列表里排在后面——
   **同层（互相没有依赖关系）的依赖才按参数顺序执行**。
3. **`release` 在最后**：`yield` 依赖的退出由 exit stack 管理，
   它在响应穿过整个中间件链、发给客户端**之后**才关闭。

## 第 2 题 · 参考实现

```python
from fastapi import BackgroundTasks, Depends, FastAPI, HTTPException
from fastapi.responses import JSONResponse
from fastapi.testclient import TestClient

TRACE: list[str] = []
app = FastAPI()


@app.middleware("http")
async def mw1(request, call_next):          # 先定义 → 内层
    TRACE.append("mw1-in")
    response = await call_next(request)
    TRACE.append("mw1-out")
    return response


@app.middleware("http")
async def mw2(request, call_next):          # 后定义 → 外层
    TRACE.append("mw2-in")
    response = await call_next(request)
    TRACE.append("mw2-out")
    return response


def dep_a():
    TRACE.append("dep_a")
    return "a"


def dep_b(a=Depends(dep_a)):
    TRACE.append("dep_b")
    return "b"


def dep_resource():
    TRACE.append("acquire")
    try:
        yield "res"
    finally:
        TRACE.append("release")


class Oops(Exception):
    pass


@app.exception_handler(Oops)
async def on_oops(request, exc):
    TRACE.append("handler-for-oops")
    return JSONResponse(status_code=418, content={"caught": str(exc)})


@app.get("/ok")
async def ok(b=Depends(dep_b), res=Depends(dep_resource)):
    TRACE.append("handler")
    return {"b": b, "res": res}


@app.get("/boom")
async def boom(b=Depends(dep_b), res=Depends(dep_resource)):
    TRACE.append("boom")
    raise Oops("炸了")


@app.get("/http404")
async def http404():
    raise HTTPException(status_code=404, detail="自己抛的")


@app.get("/bg")
async def bg(tasks: BackgroundTasks):
    TRACE.append("bg")
    tasks.add_task(TRACE.append, "后台任务")
    return {"ok": True}


if __name__ == "__main__":
    client = TestClient(app)
    for url in ("/ok", "/boom", "/http404", "/bg"):
        TRACE.clear()
        r = client.get(url)
        print(f"{url:9} {r.status_code} {r.json()}")
        print(f"    {TRACE}")
```

`/boom` 端点也声明了 `dep_b` 和 `dep_resource`——这是必要的，
否则你看不到「异常路径下 `release` 提前」这个现象（没有资源可释放）。

## 第 3 题 · 调换中间件定义顺序后

把 `mw2` 写在上面、`mw1` 写在下面，实测四条 TRACE：

```
/ok      ['mw1-in', 'mw2-in', 'dep_a', 'dep_b', 'acquire', 'handler', 'mw2-out', 'mw1-out', 'release']
/boom    ['mw1-in', 'mw2-in', 'dep_a', 'dep_b', 'acquire', 'boom', 'release', 'handler-for-oops', 'mw2-out', 'mw1-out']
/http404 ['mw1-in', 'mw2-in', 'mw2-out', 'mw1-out']
/bg      ['mw1-in', 'mw2-in', 'bg', 'mw2-out', 'mw1-out', '后台任务']
```

两条结论：

1. **中间件记录全部翻转**，包括 in 和 out。函数名里的 `1`、`2` 没有任何语义，
   决定内外层的**只有定义顺序**。所以给中间件起名时用职责（`auth_mw` / `logging_mw`），
   不要用序号——序号会误导读代码的人。
2. **`dep_a` `dep_b` `acquire` `handler` `release` 的相对位置完全不变**，
   `release` 依然在两条路径下各自的位置上。
   **中间件链和依赖链是两套独立的顺序规则**，改一个不影响另一个。

## 第 4 题 · 两条路径的 `release`

```
/ok   : ... acquire, handler, mw1-out, mw2-out, release
/boom : ... acquire, boom,    release, handler-for-oops, mw1-out, mw2-out
```

**1. 两条路径里 `release` 都执行了吗？`finally` 可靠吗？**

都执行了，**可靠**。这正是把清理写在 `finally` 里的意义：
不管处理函数是正常返回还是抛异常，退出栈都会跑一遍清理。

如果你把 `release` 写在 `yield` 后面而**不用** `try/finally`：

```python
def dep_resource():
    yield "res"
    TRACE.append("release")     # ✗ 异常时这行不会执行
```

那 `/boom` 的 TRACE 里就没有 `release`——资源泄漏了。
`check.py` 第 6 项静态检查 `finally` 关键字，就是拦这个。

**2. `release` 相对于「响应处理」的位置有什么不同？**

- 正常路径：`release` 在 **`mw1-out` `mw2-out` 之后** —— 响应已经发给客户端了
- 异常路径：`release` 在 **`handler-for-oops` 之前**，也在两个 `mw*-out` 之前

**这个不对称的原因是**：异常在路由层就被捕获了，
FastAPI 立即关闭退出栈（释放资源），然后把异常交给 `exception_handler` 生成响应，
这个响应再往外穿过中间件链。
而正常路径下，响应对象先生成、先往外走，退出栈在整个请求处理的最后才关闭。

**3. 在 `exception_handler` 里重建资源安全吗？在中间件 out 阶段呢？**

- **`exception_handler` 里：安全。** `release` 已经跑过了，资源确实已经释放，
  你可以放心地重连数据库、重建客户端、写补偿记录。
- **中间件 out 阶段：不安全。** 正常路径下 `mw*-out` 执行时 `release` **还没跑**，
  资源仍被占用。你在这里检查「连接都归还了吗」会得到错误答案，
  在这里尝试「重建连接池」会和仍在使用的连接打架。

这就是教案里那条纪律的来源：**中间件不该关心依赖的生命周期**，
它们是两套独立机制，只在时间上恰好交错。

## 第 5 题 · 费曼任务参考措辞

> 1. `yield` 依赖的 `finally` **两条路径都会执行**，可靠性没问题——
>    前提是你真的用了 `try/finally`，而不是把清理裸写在 `yield` 后面。
> 2. 但**时间点不同**：正常请求下，清理发生在响应已经穿过中间件、
>    发给客户端**之后**，所以它是整条链的最后一步。
> 3. 异常请求下正好相反，清理发生在**异常处理器之前**——
>    FastAPI 先关退出栈释放资源，再生成错误响应往外走。
> 4. 所以写代码时的纪律是：**在 `exception_handler` 里可以假设资源已释放**，
>    但在**中间件里不能**，那时清理还没发生。

反问「中间件里能不能读到清理后的状态」时的答案：**不能**。

再追问「清理代码很慢会不会拖慢响应」时的答案：
**不会拖慢用户感知的响应时间**（响应已经发出去了），
**但会占用 worker**——那段清理时间里 worker 不能处理别的请求，
所以并发吞吐照样下降。真要异步清理，用 `BackgroundTasks`
（它也在响应之后，但你可以控制它做什么），或者干脆丢给任务队列。

## 第 6 题 · logging 与 auth 谁后注册

**答案：`auth_mw` 先定义，`logging_mw` 后定义。**

```python
@app.middleware("http")
async def auth_mw(request, call_next): ...      # 先定义 → 内层

@app.middleware("http")
async def logging_mw(request, call_next): ...   # 后定义 → 外层，包住一切
```

**为什么**：后注册的在外层。`logging_mw` 在外层意味着**每个请求都要先经过它**，
包括那些会被内层 `auth_mw` 拒掉的。它的 `call_next` 拿到 401 响应后，
照样能记录状态码和耗时。

**写反了的后果**：`logging_mw` 在内层，`auth_mw` 直接返回 401 时压根不会调用 `call_next`，
**请求进不到 `logging_mw`**。现象是——

- 监控面板显示 QPS 正常、错误率 0（因为 401 没被记录）
- 有人在暴力试探 token，你的日志里**一条痕迹都没有**
- 等你从别的渠道（网关日志、云厂商访问日志）发现时，攻击已经持续了几天

**这是「日志必须在外层」这条纪律的真实代价。**

### 加分题：怎么不把这个搞混

Express 是**先注册先执行**，FastAPI 是**后注册先执行**。
同时维护两边时，我的建议是**别靠记忆，靠命名和注释**：

```python
# FastAPI —— 注意：后定义的在外层，所以日志放最后
@app.middleware("http")
async def auth_mw(...): ...

@app.middleware("http")
async def logging_mw(...): ...   # ← 最外层：所有请求都经过这里
```

```javascript
// Express —— 先注册的在外层
app.use(loggingMw);   // ← 最外层
app.use(authMw);
```

**纪律：在每个中间件定义的旁边写一行注释，标明它是「最外层」还是「内层」。**
注释描述的是**角色**（谁包住谁），不是序号，所以两边读起来是一致的。

更彻底的做法：把顺序写进测试。像今天 `check.py` 那样，
断言一次请求的完整执行顺序——顺序被人改错时测试会红，
这比任何注释都可靠。Day 7 的 CRUD 整合会把这套 TRACE 断言简化后保留下来。
