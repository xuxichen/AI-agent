## 第 1 题 · 同一个 500，分三段修

### 判据（一句话一条）

1. 函数没 `return`（返回 `None`）撞上装饰器上的 `response_model`，**出门时才崩**，客户端拿到 500。
2. 这种 500 的正解不是处理器，是**在函数里 `raise HTTPException(404)`**——它压根不让异常发生。
3. 处理器只管**形状**，而且只管**冒得到它那一层**的东西：`KeyError` 和 422 它一条都不接。

### 三条问答的答案（作业 ③）

1. 第 3 条最后一屏是 `fastapi.exceptions.ResponseValidationError: 1 validation error:`，
   底下挂着 `{'type': 'model_attributes_type', 'loc': ('response',), ...}` 和出错那个函数 `line 24, in read_order`；
   第 5 条是 `KeyError: 'qty'`，函数是 `line 33, in create_order`。
   **一个报在 `response`，一个报在你取键的那一行**——同一份文件里两屏栈读出来的结论是两件完全不同的事。
2. 靠 `read_item` 底下那一句 `raise HTTPException(status_code=404, detail="没有这个 id")`。
   **注意它不是靠处理器**：第八节里 500 的形状统一了，但如果没那句 `raise`，那条请求会变成「`Exception` 处理器接管的 500」，
   状态码是 500 而不是 404。**形状能被处理器改，状态码不能被它猜。**
3. 该你背的是**第 5 条**。第 6 条客户端把 `abc` 塞进一个声明为 `int` 的路径参数，
   框架在门口就判了 422，`loc` 里写清了是 `["path","oid"]`，**他会自己改，你一行代码都不用写**。
   第 5 条是客户端少给了一个 `qty`，而你的代码用 `payload["qty"]` 直接去取——
   框架不知道 `payload` 里该有什么（`dict` 没有字段表，Day 5 第四节那条老规矩），所以它没拦，
   轮到你函数里才炸。**「他请求得不对」和「你没考虑到他会请求得不对」是两回事**，后者才是 500。

### 两个必答的答案（作业 ⑥）

1. **理由不一样，两条都得说。**
   - 第 2 条（`KeyError` → 500）：**类型不在你写的范围里**。`KeyError` 不是 `HTTPException`，
     它就是一个普通的 Python 意外，`@app.exception_handler(HTTPException)` 这张表里那一格跟它无关。
     接管它要么注册 `Exception`（第四节），要么回到函数里 `except`（第一节）。
   - 第 3 条（422）：**它压根没冒到你这一层**。422 的类型是 `RequestValidationError`，
     框架自带一个处理器在**离端点更近的地方**就把它变成了 `{"detail": [...]}`（四 ⑦ 第 5 条）。
     四 ⑥ 那个实验证明它**能**被接管——但那要注册 `RequestValidationError`，不是把范围写大。
2. 我能想到的三种，**今天我停在第一种**：
   - **A. 再注册一个 `@app.exception_handler(Exception)`**：把剩下的 500 也变成 `{"code","msg"}`（第八节 `on_other` 就是这个）。
     代价最小，但 422 仍然不一致，而且状态码只能写死 500。
   - **B. 再接管 `RequestValidationError`**：三种形状统一成一种。
     代价是 `exc.errors()` 那一整串默认不进 `content`——**`loc` 没了**，前端不能再告诉你哪个字段不对（四 ⑥ 就是这个实验）。
     要留住 `loc`，得自己把 `errors()` 排进 `content`，那是十几行的活。
   - **C. 不改代码，改约定**：让前端认 `detail` 也算一种 `msg`。
     代价一行代码都不写，但 `detail` 是**列表**、`msg` 是**字符串**，前端还是两套分支。
   **A 是今天教过的、够用的；B 是等你哪天真要统一公司错误格式那天再做的；C 是把成本推给下游。**

## 第 2 题 · 从零写的中间件

### 判据（一句话一条）

1. 中间件里 `await call_next(request)` 只有两种结局：**拿到一个响应**，或者**抛出异常**。
2. `raise HTTPException(403)` 给你的是**前者**——403 在框架眼里是一个已经写好的正常响应；`1 / 0` 给你的是后者。
3. `[出]` 印不印、`X-Day` 有没有，**不是两件事，是同一件事的两个面**：都排在 `call_next` 后面。

### 参考实现

```bash
cd stage1/day006_fastapi_advanced
cat > code/python/hw02_answer.py <<'PY'
import time

from fastapi import FastAPI, HTTPException, Request

app = FastAPI()


@app.middleware("http")
async def stamp(request: Request, call_next):
    start = time.perf_counter()
    print("[入]", request.method, request.url.path)
    response = await call_next(request)
    cost = round(time.perf_counter() - start, 4)
    print("[出]", response.status_code, cost)
    response.headers["X-Day"] = "6"
    return response


@app.get("/ok")
def ok():
    return {"done": True}


@app.get("/no")
def no():
    raise HTTPException(status_code=403, detail="不给看")


@app.get("/die")
def die():
    return 1 / 0
PY
```

五条要求逐条对上：`async def` + 中间件（第 9 行）、`[入]` 带方法和路径（11）、
`[出]` 带状态码和 `round(..., 4)` 的耗时（13–14）、每个响应加头（15）、没有任何处理器（全文没有 `exception_handler`）。
三个端点全是同步 `def`。**中间件签名里那个 `request: Request` 不是可选的**——你写了注解就得 import 它（第五节 ① 那条），少了就是启动期 `NameError`。

### 两个必答的答案

1. `/no`：`raise HTTPException` 冒到框架自带的处理器那儿，**在它这一层就变成了一个真的 `Response` 对象**，

2. **改 `call_next` 那一行：把它包进 `try`，并且在 `except` 里自己造一个响应**（六 ⑤ + ⑥ 合成一条）。

   框架最外层那个「替你 except」再也没看到它（六 ⑥ 实验二同一条）——
   **参数值、哪一行、什么类型，从此只能靠 `[吞了]` 那一行猜。**

   七 ④ 那句「`?size=99` → 400：`pagination` 跑了，`list_names` 一行都没跑」是它的正版本，这里是反版本。
   至于 `status_code=201` 为什么没赢：第三节那条判决——**装饰器说的是「没事的时候几」，`raise` 说的是「现在就是事」**。
   所以第 4 条同时用了两节的知识：`print` 归第一节，409 盖掉 201 归第三节，而**`raise` 是一条单向的分界线。**
   顺带第 6 条：`?nope=1` 是 Day 4 第二节那条老规则，多余的查询参数**根本没人看它**，
   `badge` 拿的还是默认值 `level=1` / `tag="free"`，所以它和第 1 条回得一模一样。

## 第 4 题 · 三处错，每处只许改一行

### 判据（一句话一条）

1. 三处错分别是**三种「该谁负责」**：(1) 你的 `return` 形状不对、(2) 你接管的范围写窄了、(3) 你少写一个参数。
2. `Exception` 这个范围**比你想的大**（连 `ResponseValidationError` 都接），但**不是最大**（`HTTPException` 它接不到）。
3. 处理器改得了形状，改不了「这条路有没有走完」——**`[出]` 少那一次就是证据。**

### 三处的一行修法

import time

from fastapi import Depends, FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field

app = FastAPI()


class TodoIn(BaseModel):
    title: str = Field(min_length=3)
    done: bool = False


class TodoOut(BaseModel):
    id: int
    title: str
    done: bool

    {"id": 1, "title": "写作业", "done": False},
    {"id": 2, "title": "倒垃圾", "done": True},

def todo_page(page: int = 1, size: int = 2):
    if page < 1:
        raise HTTPException(status_code=400, detail="页码从 1 开始")
    return {"skip": (page - 1) * size, "size": size}

    start = time.perf_counter()
    print("[入]", request.url.path)
    response = await call_next(request)

    found = []
    n = 0
    for t in todos:
        if n >= pg["skip"]:
            if len(found) < pg["size"]:

        n = n + 1
    return found

### 三条问答的答案（这题真正要交的东西）

1. 见上面那张一行修法表。改完第 4、5、7 条分别变成：

   ```
   4 → {"detail":"没有这条待办"} [404]
   5 → {"code":500,"msg":"出错了"} [500]
   7 → {"id":3,"title":"买牛奶","done":false} [201]
   ```

   只有第 5 条走了处理器。**第 4 条的形状仍然是 `detail`**——因为你只注册了 `Exception`，
   `HTTPException` 归框架自带的那个（这就是作业 ⑤ 第 3 问，也是排错对照表第 4 行）。
2. **处理器在你的中间件的更外面。** 证据就是那个计数：`[出]` 从「少两次」变成「少一次」，
   少的那一次正是 `/boom`——客户端已经拿到 `{"code":500,"msg":"出错了"}` 了，
   可 `timer` 里的 `print` 还是没跑到。
   说明那个响应**不是在你的中间件往外交回去的**，是在它外面（框架最外层）造出来的；
   你的 `timer` 早在 `call_next` 抛异常那一刻就退出了，`response` 这个变量根本没被赋值。
   对照 `/todos/99` 那条 404：它 `[出]` 印得出来，因为 `HTTPException` 在**更里面**就被解决成响应了。
   **一句话：中间件只看得见「已经成形的响应」，处理器在响应还没成形的地方工作。**
3. **因为 `HTTPException` 冒不到 `Exception` 这一层。** 你在依赖里 `raise` 的那条 400 是 `HTTPException`，
   框架自带的 `HTTPException` 处理器在离端点很近的一层就把它变成了 `{"detail": "页码从 1 开始"}`，
   这条路到此结束，外面那个「范围是 `Exception`」的处理器**根本没看见它**。
   所以「`Exception` 是个范围」这句话要补后半句：**它是「剩下所有的」而不是「所有的」**——
   已经被更里面解决掉的东西，范围写得再宽也轮不到。
   要 4xx 也统一形状，就得**再注册一个 `@app.exception_handler(HTTPException)`**（第 1 题 ⑤ 那四行、第八节 `on_http` 那个）。

### 这一题最可能被写错的三处

1. **把第 (2) 处理解成「越宽越好」，于是把 `KeyError` 那行留着、再补一行 `Exception`。**
   两行都能跑，但你会以为自己在管 `KeyError`——`Exception` 已经把它包进去了，
   **留着一行永远轮不到的代码，比少写一行更糟**（读代码的人会以为这里有个专门的分支）。
2. **把第 (1) 处改成「从 `TodoOut` 里把字段删掉」或者「给 `TodoOut` 加一个 `error` 字段」。**
   能跑，那是**改考卷**：`GET /todos` 从此也能返回一条只有 `error` 的东西，
   字段表就不再是字段表了（Day 5 第四节 `isAdmin` 那条规矩）。
3. **第 (3) 处不改装饰器，改成函数里 `raise HTTPException(status_code=201)` 或 `return JSONResponse(status_code=201, content=data)`。**
   前者根本不可能——正常路径不该 `raise`（而且 `raise` 出去会被当成异常，201 变 201 但走的是错误通道）。
   后者能跑但**绕开了 `response_model`**（第八节那条「出门前套模型」的路你不走了，
   以后 `TodoOut` 加了字段你不会报错，只会静默漏出去）。**装饰器上多写一个参数就解决的事，别用十行去换。**

## 今天可带走的四句

1. **`raise` 是一条单向分界线**：它之前的都跑过了（第 3 题那个 `[端点] p2`），它之后的全都不算，
   装饰器上写的 `status_code=` 也算（三 ①）。所以「什么时候该 `raise`」的第一条判断是：**这条请求本来就不该成功。**
2. **404 干净、500 脏**：`raise HTTPException(404)` 让异常压根不发生（栈从 2 屏变成 0 屏）；
   处理器只把一个已经发生的意外换个形状。**能用 `raise` 解决的，永远不要留给处理器。**
3. **范围这件事**：`Exception` 接得住 `KeyError`、`ZeroDivisionError`、`ResponseValidationError`，
   但接不住 `HTTPException`，也接不住 422——**不是它不够大，是那些东西在更里面就已经被解决了。**
4. **中间件是「每个请求都跑两遍，但崩掉的请求只跑前一遍」**：`call_next` 之后的一切，
   在真崩溃的请求上都不存在。**头和栈你今天只能要一个。**
