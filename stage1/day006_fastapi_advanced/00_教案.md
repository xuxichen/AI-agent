# Day 6 · 资源到底在哪一行被释放

> 计划里这一天是「FastAPI 进阶：依赖注入、中间件、异常处理、后台任务」。
> 这四个东西你都能查文档学会写法。本日只讲**它们的执行顺序**——
> 因为顺序错了不会报错，只会让你的连接池泄漏、日志缺失、事务提交在响应之后。

---

## 今日问题

本机实测，一个 app 里有 2 个中间件、1 条依赖链、1 个 `yield` 依赖、1 个自定义异常处理器。
打两次请求，记录每一步：

```
GET /ok    200 {'b': 'b', 'res': 'res'}
  ['mw2-in', 'mw1-in', 'dep_a', 'dep_b', 'acquire', 'handler',
   'mw1-out', 'mw2-out', 'release']

GET /boom  418 {'caught': '炸了'}
  ['mw2-in', 'mw1-in', 'dep_a', 'dep_b', 'acquire', 'boom',
   'release', 'handler-for-oops', 'mw1-out', 'mw2-out']
```

三个反直觉的地方：

1. `mw1` 先定义，但 **`mw2-in` 排在最前面**
2. `/ok` 里 **`release` 排在所有中间件 out 之后**——响应都发出去了，资源才释放
3. `/boom` 里 **`release` 排在 `handler-for-oops` 之前**——和上面那条**不对称**

**这三条各自为什么？第三条的不对称会带来什么实际后果？**

---

## 学习目的

记住四条顺序规则，全是实测的：

| 规则 | 内容 |
|---|---|
| 中间件 | **后注册的在外层**，先进后出 |
| 依赖 | 按**依赖拓扑序**，被依赖的先执行 |
| `yield` 依赖的清理 | 正常路径：**响应发出之后**；异常路径：**异常处理器之前** |
| `BackgroundTasks` | **全部中间件之后**，是整条链的最后一步 |

---

## 学习内容

### 一、中间件是倒序洋葱

定义顺序 `mw1` → `mw2`，执行顺序 `mw2-in` → `mw1-in` → …… → `mw1-out` → `mw2-out`。

**后注册的包在外面。** 记忆法：中间件像套娃，你每 `@app.middleware("http")` 一次，
就往**最外面**套一层。所以最后套的那层最先碰到请求。

实践推论（这条会咬人）：

```python
@app.middleware("http")
async def logging_mw(request, call_next): ...      # 想记录耗时

@app.middleware("http")
async def auth_mw(request, call_next): ...         # 想在鉴权失败时直接返回 401
```

`auth_mw` 后注册 → 在外层 → **鉴权失败的请求压根不会进 `logging_mw`**。
如果你的日志想覆盖所有请求（包括被拒的），`logging_mw` 必须**后注册**。

Express 的 `app.use()` 正相反：**先注册的先执行**。这是你从 JS 带过来最容易错的一处。

### 二、依赖按拓扑序，不是按参数顺序

```python
def dep_a(): ...
def dep_b(a=Depends(dep_a)): ...

@app.get("/ok")
async def ok(b=Depends(dep_b), res=Depends(dep_resource)):
```

实测顺序：`dep_a` → `dep_b` → `acquire`。

`dep_b` 声明依赖 `dep_a`，所以 `dep_a` 先跑——**即使你在参数列表里把 `b` 写在前面**。
FastAPI 会先把整棵依赖树解析出来，再按拓扑序执行。

**同一个依赖在一次请求里只执行一次**（默认缓存）。所以 `dep_a` 被三个地方依赖也只跑一次。
这在 Day 9 很关键：你会把「创建 LLM 客户端」做成依赖，多个子依赖共用同一个客户端实例。

### 三、`yield` 依赖的清理时机（今天最该记住的）

```python
def dep_resource():
    TRACE.append("acquire")
    try:
        yield "res"
    finally:
        TRACE.append("release")
```

`finally` 一定会跑——两条路径都跑，这点是可靠的。**但跑的时间点不一样**：

| 路径 | 实测顺序 | 含义 |
|---|---|---|
| 正常 | `handler → mw1-out → mw2-out → release` | 响应**已经发给客户端了**，资源才释放 |
| 异常 | `boom → release → handler-for-oops → mw1-out` | 资源**在异常处理器之前**就释放了 |

**为什么正常路径这么晚**：FastAPI 用退出栈（exit stack）管理 `yield` 依赖，
响应对象先原路返回穿过中间件链，退出栈最后才关闭。

**两条实践推论**：

1. **在中间件里不要假设资源已释放。** 正常路径下 `mw*-out` 跑的时候 `release` 还没执行。
   比如你想在中间件里统计「数据库连接是否都归还了」，会得到错误答案。
2. **在 `exception_handler` 里可以安全假设资源已释放。** 异常路径下 `release` 先跑。
   所以异常处理器里可以放心地重连、重试、写补偿记录。

**还有第三条，最容易踩**：正常路径下 `release` 在响应发出之后，
所以**清理代码里的耗时不会被计入用户感知的响应时间**，
但**会占用 worker**——如果你的 `release` 里有个慢的网络调用，并发能力照样下降。

### 四、异常处理器的分工

实测两种异常：

```
GET /boom    → 418 {'caught': '炸了'}          ← 自定义 Oops + @app.exception_handler(Oops)
GET /http404 → 404 {'detail': '自己抛的'}       ← HTTPException，FastAPI 内置处理器
```

分工很清晰：

| | `HTTPException` | 自定义异常 + `exception_handler` |
|---|---|---|
| 用途 | **预期内**的错误（没找到、没权限、参数冲突） | **预期外**的错误（下游炸了、数据不一致） |
| 写法 | 直接 `raise`，不用注册处理器 | 要写 `@app.exception_handler(YourError)` |
| 谁看到 | 客户端，`detail` 会原样返回 | 客户端看到你构造的响应 |
| 会不会进日志 | 默认不会 | 你可以在处理器里记 |

**`/http404` 的 TRACE 只有 4 项中间件记录**：
`['mw2-in', 'mw1-in', 'mw1-out', 'mw2-out']`——
因为那个端点没声明任何依赖，而且 `HTTPException` 在路由层就被接住了。
**中间件照常跑完了 in 和 out**，说明异常没有跳过中间件链。

### 五、BackgroundTasks 是整条链的最后一步

```
/bg → ['mw2-in', 'mw1-in', 'bg', 'mw1-out', 'mw2-out', '后台任务']
```

`后台任务` 排在**所有中间件 out 之后**。

这意味着：**客户端已经收到完整响应了，你的后台任务才开始跑。**
所以它适合发通知、写审计日志、清理临时文件。

**但它不适合任何需要可靠性的事**：进程被杀、机器重启，任务就没了，
没有重试、没有持久化、没有失败记录。Day 30 之后你需要真正的任务队列
（Celery / ARQ / dramatiq），那才是「后台任务」的生产级形态。

还有一个坑：后台任务里**拿不到请求上下文**（依赖已经清理完了，
上面那条 `release` 已经跑过），所以别在里面用数据库连接。

## 费曼任务

向同事解释：**为什么 `yield` 依赖的 `finally` 在正常请求和异常请求里执行时机不同，
以及这个差别在写代码时要怎么应对。**

不超过 4 句，必须包含「正常路径下响应已经发出去了」这一层。写进 `01_作业.md` 第 5 题。

如果他反问「那我在中间件里能不能读到清理后的状态」，你要能立刻答：
**不能**，正常路径下中间件 out 阶段清理还没发生。
